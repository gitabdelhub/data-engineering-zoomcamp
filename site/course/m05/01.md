@@ brief
- Jusqu'ici, chaque étape avait son outil : **dlt** ou un script Python pour ingérer, **dbt** pour transformer, **Airflow** pour orchestrer, et des tests à part pour la qualité.
- **Bruin** réunit ces quatre rôles dans un seul projet, avec une seule ligne de commande : l'ingestion, les transformations SQL ou Python, l'ordre d'exécution et les contrôles qualité.
- Un **asset** est un fichier qui crée ou met à jour une table. Les **dépendances** entre assets forment le **lignage** (*lineage*) : Bruin s'en sert pour savoir dans quel ordre tout lancer.
- Bruin est **open source** (la CLI) ; **Bruin Cloud** est l'offre payante qui fait tourner les mêmes pipelines sur des serveurs gérés.

@@ predict-answer
Trois choses : **ce que le fichier produit** (le nom de sa table), **ce dont il a besoin** (ses dépendances), et **comment l'exécuter** (SQL sur quelle base, ou Python avec quels paquets). Bruin met ces informations dans un bloc de configuration en haut de chaque fichier, entre `@bruin` et `@bruin`. Avec ça, il construit le graphe des dépendances, comme dbt, et il l'exécute, comme Airflow.

@@ hints
- L'orchestration, dans Bruin, c'est surtout `depends:` dans chaque asset et `schedule:` dans `pipeline.yml`.
- La qualité : les `checks:` sur les colonnes, et les `custom_checks:` pour une requête à toi. Ils ressemblent aux tests de dbt.
- Un inconvénient possible : moins de place pour choisir le meilleur outil à chaque étape, ou la dépendance à un seul projet open source.

@@ solution
Un exemple de tableau, à comparer avec le tien :

| Rôle | Dans le cours | Dans Bruin |
| --- | --- | --- |
| Ingérer | un script Python avec pandas (module 1), dlt (workshop) | un asset Python qui renvoie un DataFrame, ou un asset `ingestr` en YAML |
| Transformer | les modèles SQL de dbt (module 4) | des assets SQL, avec un bloc `@bruin` en tête |
| Orchestrer | un DAG Airflow et ses `>>` (module 2) | `depends:` dans chaque asset, `schedule:` dans `pipeline.yml`, `bruin run` |
| Contrôler | les tests de dbt (module 4) | `checks:` sur les colonnes et `custom_checks:` |

Avantages : un seul fichier par table, avec son code, sa configuration et ses contrôles ; un seul outil à installer et à apprendre pour toute l'équipe. Inconvénient : si Bruin ne sait pas faire quelque chose, on ne peut pas changer seulement une brique. On garde des outils séparés quand ils sont déjà en place et maîtrisés, ou quand une étape a besoin d'un outil spécialisé, comme Spark au module 6 pour de très gros volumes.
