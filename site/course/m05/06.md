@@ brief
- Le **staging** nettoie la couche brute : il dédoublonne, joint la table des paiements et ne garde que les colonnes utiles.
- La stratégie `time_interval` met à jour **seulement la fenêtre** du run : Bruin efface les lignes dont `incremental_key` tombe dans la fenêtre, puis insère le résultat de ta requête. Les autres mois ne bougent pas.
- Ta requête doit donc filtrer **exactement la même fenêtre** que l'effacement, sinon tu crées des doublons ou des trous.
- Les **contrôles** (`checks:`) se mettent sur les colonnes : `not_null`, `unique`, `positive`, `non_negative`, `accepted_values`… Un `custom_checks:` est une requête à toi qui doit renvoyer une valeur donnée.
- Au tout premier run, la table n'existe pas encore : `--full-refresh` la crée. Sans lui, l'effacement échoue.

@@ codespaces
- `bruin render` affiche le SQL d'un asset après Jinja, y compris l'effacement que prépare `time_interval`. C'est le moyen le plus sûr de vérifier ta fenêtre avant de lancer.
- La page officielle des assets montre une syntaxe `@bruin.asset(...)` en tête des fichiers : elle n'existe pas dans Bruin 0.11. La bonne forme est celle de ton modèle, le bloc `/* @bruin ... @bruin */`.

@@ constraints
- L'asset `staging.trips`, de type `duckdb.sql`, dépend des deux assets d'ingestion
- Matérialisé en table, stratégie `time_interval` sur `pickup_datetime`, granularité `timestamp`
- La requête filtre la fenêtre du run avec **les mêmes bornes** que l'effacement de Bruin
- Un seul exemplaire de chaque trajet, défini par ses dates, ses zones, son prix et son type de taxi ; en cas de doublon, on garde le plus récemment téléchargé
- Le nom du paiement vient de `ingestion.payment_lookup`, et un code inconnu ne fait pas disparaître le trajet
- `not_null` sur `pickup_datetime`, et un contrôle personnalisé qui prouve qu'il n'y a aucun doublon
- `bruin render` montre ta fenêtre, et le run de janvier passe avec ses contrôles

@@ guide
### 1. Regarde ce que Bruin va faire

Complète d'abord le bloc `@bruin` (le nom, le type, les dépendances, la matérialisation), puis :

~~~bash
cd /workspaces/data-engineering-zoomcamp/mon-travail/module-05
bruin render mon-pipeline/pipeline/assets/staging/trips.sql --start-date 2019-01-01 --end-date "2019-01-31 23:59:59.999999"
~~~

La première ligne est l'effacement, avec ses deux bornes. Note leur forme.

### 2. La même fenêtre dans ta requête

Bruin te donne plusieurs variables de dates. Celles qui ont exactement la forme de l'effacement : `{{ start_timestamp }}` et `{{ end_timestamp }}`. Exemple, sur une autre table :

~~~sql
WHERE sold_at BETWEEN '{{ start_timestamp }}' AND '{{ end_timestamp }}'
~~~

`BETWEEN` inclut ses deux bornes, comme l'effacement. Relance `bruin render` et compare les deux lignes.

### 3. Le dédoublonnage

Comme au module 4, `QUALIFY ROW_NUMBER() OVER (PARTITION BY ... ORDER BY ...) = 1` garde une ligne par groupe. Trie par `extracted_at` décroissant pour garder le chargement le plus récent.

### 4. Le contrôle personnalisé

Un `custom_checks:` a un `name`, une `query` qui renvoie **une seule valeur**, et la `value` attendue. Pour les doublons : le nombre de lignes moins le nombre de combinaisons distinctes doit valoir 0.

### 5. Le premier run

~~~bash
bruin run mon-pipeline/pipeline/assets/staging/trips.sql --start-date 2019-01-01 --end-date "2019-01-31 23:59:59.999999"
~~~

Lis l'erreur, puis relance avec `--full-refresh`.

@@ hints
- `depends:` liste des **noms d'assets** (`ingestion.trips`), pas des chemins de fichiers.
- `COUNT(DISTINCT (a, b, c))` compte les combinaisons distinctes de plusieurs colonnes en DuckDB.
- `LEFT JOIN` sur la table des paiements, et `COALESCE(p.payment_type_name, 'unknown')` pour les codes absents.
- Si `bruin render` affiche `{{ start_timestamp }}` tel quel, le nom de la variable est mal écrit : Jinja ne remplace que les noms qu'il connaît.

@@ solution
`mon-pipeline/pipeline/assets/staging/trips.sql` :

~~~sql
/* @bruin
name: staging.trips
type: duckdb.sql

depends:
  - ingestion.trips
  - ingestion.payment_lookup

materialization:
  type: table
  strategy: time_interval        # efface la fenêtre, puis insère la requête
  incremental_key: pickup_datetime
  time_granularity: timestamp

columns:
  - name: pickup_datetime
    type: timestamp
    description: "Prise en charge"
    nullable: false               # pas primary_key : deux trajets partent souvent à la même seconde
    checks:
      - name: not_null
  - name: fare_amount
    type: double
    description: "Prix au compteur"

custom_checks:
  - name: aucun_doublon
    description: "Une seule ligne par trajet"
    query: |
      SELECT COUNT(*) - COUNT(DISTINCT (pickup_datetime, dropoff_datetime, pickup_location_id, dropoff_location_id, fare_amount, taxi_type))
      FROM staging.trips
    value: 0
@bruin */

SELECT
    t.pickup_datetime,
    t.dropoff_datetime,
    t.pickup_location_id,
    t.dropoff_location_id,
    t.fare_amount,
    t.taxi_type,
    COALESCE(p.payment_type_name, 'unknown') AS payment_type_name
FROM ingestion.trips t
LEFT JOIN ingestion.payment_lookup p
    ON t.payment_type = p.payment_type_id
-- La même fenêtre que le DELETE de time_interval : bornes incluses
WHERE t.pickup_datetime BETWEEN '{{ start_timestamp }}' AND '{{ end_timestamp }}'
QUALIFY ROW_NUMBER() OVER (
    PARTITION BY t.pickup_datetime, t.dropoff_datetime,
                 t.pickup_location_id, t.dropoff_location_id, t.fare_amount, t.taxi_type
    ORDER BY t.extracted_at DESC   -- le chargement le plus récent gagne
) = 1
~~~

Le premier run, sans `--full-refresh` :

~~~text
Internal: Catalog Error: Table with name trips does not exist!
Did you mean "ingestion.trips"?

LINE 2: DELETE FROM staging.trips WHERE pickup_datetime BETWEEN '2019-01-01T00:00:00.000000Z'...
~~~

Avec `--full-refresh`, Bruin crée la table au lieu d'effacer, et le contrôle passe : `PASS staging.trips ..`.

Le modèle officiel filtre avec `>= '{{ start_datetime }}'` et `< '{{ end_datetime }}'`. Cette variable n'a pas les microsecondes : pour la fenêtre de janvier, elle s'arrête à `2019-01-31T23:59:59` et la dernière seconde du mois n'est pas réinsérée. `BETWEEN` avec les variables `_timestamp` a exactement les bornes de l'effacement.
