@@ brief
- Un **projet** Bruin est un dépôt Git qui contient un ou plusieurs pipelines. Bruin exige Git : c'est ainsi qu'il trouve la racine du projet.
- `.bruin.yml`, à la racine, définit des **environnements** (`default`, `prod`…). Chaque environnement a ses **connexions**, avec leurs chemins, leurs identifiants et leurs secrets.
- Le code ne cite qu'un **nom** de connexion (`duckdb-default`). Le même nom pointe vers une base différente selon l'environnement : `bruin run --environment prod` change de base sans changer une ligne de code.
- `default_environment` choisit l'environnement quand tu n'en donnes pas. On y met celui de développement, pour ne jamais toucher la production par accident.

Ouvre les fichiers : chacun est plein de `TODO` à compléter. C'est le squelette que tu vas remplir, un fichier par leçon.

### 2. Deux environnements

Dans `.bruin.yml`, un environnement est une clé sous `environments:`. Exemple, pour une autre base :

~~~yaml
environments:
  default:
    connections:
      postgres:
        - name: pg-boutique
          host: localhost
  recette:
    connections:
      postgres:
        - name: pg-boutique
          host: recette.example.com
~~~

Même nom de connexion, deux cibles. Fais pareil avec `duckdb-default` et tes deux fichiers. Tu peux laisser la connexion `chess-default` de la leçon 2 dans `default`.

### 3. Vérifie

~~~bash
bruin environments list
bruin connections list
bruin validate mon-pipeline
~~~

Compte les problèmes listés par `validate` : ils viennent tous des `TODO` du modèle.

@@ hints
- L'indentation compte : `prod:` est au même niveau que `default:`, sous `environments:`.
- Le chemin `path:` reste relatif à la racine du fork, comme à la leçon 2.
- Si `bruin connections list` n'affiche qu'un environnement, vérifie que `prod:` n'est pas indenté sous `default:`.

@@ solution
`.bruin.yml`, à la racine du fork :

~~~yaml
default_environment: default   # sans --environment, on travaille en dev

environments:
  default:
    connections:
      duckdb:
        - name: duckdb-default
          path: mon-travail/module-05/nyc_taxi.duckdb
      # la connexion chess-default de la leçon 2 peut rester ici
  prod:
    connections:
      duckdb:
        - name: duckdb-default            # le même nom : le code ne change pas
          path: mon-travail/module-05/nyc_taxi_prod.duckdb
~~~

`bruin environments list` :

~~~text
Selected environment: default
Available environments:
- default
- prod
~~~

Le pipeline `premier-pipeline` utilisera désormais `nyc_taxi.duckdb`, lui aussi : c'est voulu, une connexion sert à tous les pipelines du projet.

@@ git
Prouve, avec Git, que ton `.bruin.yml` et tes bases ne partiront jamais dans un commit : pour chacun, quelle **ligne** de quel fichier l'ignore ?

@@ git-hints
- `git check-ignore -v <fichier>` affiche le fichier `.gitignore`, le numéro de ligne et la règle qui ignorent ce fichier.
- Si la commande n'affiche rien pour un fichier, il **n'est pas** ignoré.
- Essaie-la sur `.bruin.yml` et sur un chemin de base, même s'il n'existe pas encore : `mon-travail/module-05/nyc_taxi.duckdb`.

@@ breakfix
Depuis la racine du fork, ajoute une règle au `.gitignore` comme on le fait souvent : `echo "mon-travail/module-05/*.csv" >> .gitignore`. Puis crée un fichier `touch mon-travail/module-05/test.csv` et regarde `git status`. Le fichier devrait être ignoré : l'est-il ? Répare, puis supprime `test.csv`.

@@ breakfix-hints
- Regarde la fin du fichier avec `tail -3 .gitignore`, ou avec `cat -A .gitignore | tail -3` : `$` marque chaque fin de ligne.
- Quand Bruin ajoute ses lignes au `.gitignore`, il ne met pas de retour à la ligne après la dernière.
- `echo >>` écrit à la suite, sur la **même** ligne si la précédente n'est pas terminée.

@@ breakfix-answer
La fin du `.gitignore` après ton `echo`, par exemple (la dernière ligne écrite par Bruin dépend de ce qu'il a déjà lancé) :

~~~text
__pycache__/
*.py[cod]mon-travail/module-05/*.csv
~~~

Bruin a écrit `*.py[cod]` sans retour à la ligne final, et ta règle s'est collée derrière : Git lit une seule règle, qui ne correspond à rien. `test.csv` apparaît donc dans `git status`, et pire, les fichiers `.pyc` ne sont plus ignorés. Ouvre le fichier, coupe la ligne en deux, et termine-le par un retour à la ligne. La parade : `git check-ignore -v` sur le fichier, à chaque nouvelle règle.
