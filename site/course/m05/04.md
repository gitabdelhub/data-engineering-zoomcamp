@@ brief
- Un **pipeline** est un dossier avec un `pipeline.yml` et ses `assets/`. Un projet peut en avoir plusieurs ; on les sépare surtout par leur **rythme** (`schedule`), un seul par pipeline.
- `pipeline.yml` donne le nom, le rythme (`daily`, `monthly`, ou une expression cron), la date de départ (`start_date`), les connexions par défaut et les **variables**.
- Bruin fournit à chaque run une **fenêtre** de dates : `start_date` et `end_date`. En SQL, tu les lis avec Jinja (`{{ start_date }}`) ; en Python, avec les variables d'environnement `BRUIN_START_DATE` et `BRUIN_END_DATE`.
- Les variables à toi se déclarent en **JSON Schema** (un type, une valeur par défaut). En Python, elles arrivent toutes ensemble, en JSON, dans `BRUIN_VARS` ; en SQL, avec `{{ var.nom }}`. On les change au lancement avec `--var`.

@@ codespaces
- La page officielle sur les variables donne `BRUIN_VAR_TAXI_TYPES` pour lire une variable en Python : cette variable n'existe pas dans Bruin 0.11. Utilise `BRUIN_VARS`, comme le disent les commentaires du modèle.
- Je te propose les taxis **verts** par défaut : leurs fichiers sont dix fois plus petits que ceux des jaunes, et chaque run prend quelques secondes. Les jaunes restent à une option près.

@@ verified
- Testé avec Bruin 0.11.801 : `BRUIN_VARS` contient `{"taxi_types": ["green"]}` ; `BRUIN_VAR_TAXI_TYPES` est vide ; `--var 'taxi_types=["yellow"]'` remplace la valeur ; `{{ var.taxi_types }}` marche en SQL.
- `--var taxi_types=yellow` est refusé : `invalid character 'y' looking for beginning of value`. La valeur doit être du JSON.

@@ guide
### 1. Pourquoi mensuel

Les fichiers des taxis sont publiés **un par mois**. Un pipeline mensuel reçoit une fenêtre d'un mois à chaque run : exactement un fichier à charger.

### 2. Le JSON Schema d'une variable

Exemple d'une variable chaîne, pour un autre pipeline :

~~~yaml
variables:
  pays:
    type: string
    default: "FR"
~~~

Pour un tableau, il faut aussi dire le type de ses éléments, avec `items:`.

### 3. Valide

~~~bash
cd /workspaces/data-engineering-zoomcamp/mon-travail/module-05
bruin validate mon-pipeline
~~~

Les messages qui restent parlent des assets (`TODO_SET_ASSET_NAME`…), plus de `pipeline.yml`.

### 4. Lis une variable sans rien lancer

`bruin render` affiche le SQL d'un asset après Jinja. Tu l'utiliseras à la leçon 6, quand ton staging aura sa fenêtre de dates.

@@ hints
- `start_date` est une chaîne au format `YYYY-MM-DD`, entre guillemets.
- Le tableau en YAML : `default: ["green"]`, avec les crochets.
- `items:` est au même niveau que `type: array`, et contient `type: string`.

@@ solution
`mon-pipeline/pipeline/pipeline.yml` :

~~~yaml
name: nyc_taxi
schedule: monthly          # un fichier de taxis par mois, un run par mois
start_date: "2019-01-01"   # le point de départ d'un --full-refresh

default_connections:
  duckdb: duckdb-default   # le nom défini dans .bruin.yml

variables:
  taxi_types:
    type: array
    items:
      type: string
    default: ["green"]     # les verts : dix fois plus petits que les jaunes
~~~

Le modèle officiel garde `["yellow"]` par défaut ; les deux marchent. Pour un run avec les deux types : `--var 'taxi_types=["yellow", "green"]'`, avec les apostrophes autour pour que le terminal ne touche pas aux crochets.

@@ breakfix
Dans `pipeline.yml`, écris `default: green` sans crochets, puis lance `bruin validate mon-pipeline`. Ensuite, dans le terminal, lance `bruin validate mon-pipeline --var taxi_types=yellow`. Compare les deux réactions, puis remets les crochets.

@@ breakfix-hints
- Le premier changement est accepté : la valeur par défaut n'est pas vérifiée contre son type.
- Le second est refusé tout de suite : `--var` attend du JSON après le `=`.
- En JSON, une chaîne s'écrit entre guillemets, et un tableau entre crochets.

@@ breakfix-answer
`default: green` passe `validate` sans un mot, et ne casse qu'au run, quand Python parcourt les lettres de `"green"`. `--var taxi_types=yellow` est refusé avant tout :

~~~text
An error occurred: error creating pipeline from path '.../mon-pipeline/pipeline': invalid variable override "taxi_types=yellow": invalid character 'y' looking for beginning of value
~~~

`yellow` n'est pas du JSON. Les deux formes justes : `--var 'taxi_types=["yellow"]'` pour un tableau, et `--var 'pays="FR"'` pour une chaîne. Remets `default: ["green"]` : une erreur visible tout de suite vaut mieux qu'une erreur au milieu d'un run.
