@@ brief
- La **CLI** de Bruin est un seul programme, installé par un script. `bruin version` vérifie qu'il est là.
- `bruin init <modèle> <dossier>` crée un pipeline à partir d'un **modèle** (*template*) : `default` pour découvrir, `zoomcamp` pour le pipeline des taxis.
- Le fichier `.bruin.yml` contient les **connexions** et les secrets. Il n'est **jamais** commité : `bruin init` l'ajoute lui-même au `.gitignore`.
- Trois commandes reviennent tout le temps : `bruin validate` (vérifier sans rien lancer), `bruin run` (exécuter) et `bruin query` (interroger une base).

@@ codespaces
- `bruin init` cherche la racine du dépôt Git : dans ton fork, `.bruin.yml` est créé à la **racine** du fork, pas dans le dossier du pipeline. C'est le même fichier pour tous tes pipelines Bruin.
- Le premier `bruin run` télécharge une seule fois ce dont Bruin a besoin : le pilote DuckDB, uv pour les assets Python, et ingestr pour les ingestions. Les lignes « This is a one-time operation » sont normales.
- Le modèle `default` télécharge des profils de joueurs d'échecs depuis l'API publique de chess.com : il faut Internet, ce que ton Codespace a.

@@ verified
- Testé avec Bruin 0.11.801 : l'installation, `bruin init default` depuis un sous-dossier du dépôt, l'emplacement de `.bruin.yml` et de la base, `validate`, et l'erreur de la panne ci-dessous.
- Mon environnement de test ne pouvait pas joindre chess.com : l'asset des joueurs y passait sans rien charger. Chez toi, il charge les profils pour de vrai ; ses chiffres exacts ne sont pas vérifiés.

@@ predict
Dans le modèle `default`, l'asset SQL `player_stats` lit la table créée par l'asset d'ingestion `players`. Tu lances `bruin run` sur le fichier `player_stats.sql` **seul**, sur une base neuve. Que se passe-t-il ?

@@ predict-answer
Il échoue : `Catalog Error: Table with name players does not exist!`. Lancer un fichier seul ne lance **que** lui, pas ses dépendances. Sur une base neuve, la table de `players` n'existe pas encore. Il faut d'abord lancer le pipeline entier (ou l'ingestion), puis l'asset SQL. La leçon 7 montre comment lancer un asset **avec** ce qui l'entoure.

@@ practice
Installe Bruin, crée le pipeline `default` dans `mon-travail/module-05/premier-pipeline`, range sa base au bon endroit, puis lance-le et interroge le résultat.

@@ constraints
- `bruin version` affiche un numéro de version
- `mon-travail/module-05/premier-pipeline` existe, créé par `bruin init default`
- Dans `.bruin.yml`, la connexion `duckdb-default` écrit dans `mon-travail/module-05/premier.duckdb`, et pas à la racine du fork
- `bruin validate` puis `bruin run` réussissent sur ce pipeline
- `bruin query` affiche le contenu de la table `dataset.player_stats`
- `git status` ne montre ni `.bruin.yml` ni le fichier `.duckdb`

@@ guide
### 1. L'installation

~~~bash
curl -LsSf https://getbruin.com/install/cli | sh
bruin version
~~~

Si `bruin` est introuvable, ouvre un nouveau terminal : le script a ajouté son dossier au `PATH`. L'extension **Bruin** pour VS Code est facultative : elle ajoute un panneau pour lancer les assets à la souris et voir le lignage. Tout ce module se fait au terminal.

### 2. Le premier pipeline

~~~bash
mkdir -p /workspaces/data-engineering-zoomcamp/mon-travail/module-05
cd /workspaces/data-engineering-zoomcamp/mon-travail/module-05
bruin init default premier-pipeline
~~~

Regarde ce qui a été créé, et **où** : `ls premier-pipeline premier-pipeline/assets`, puis `ls -a /workspaces/data-engineering-zoomcamp`. Ouvre `.bruin.yml` à la racine du fork.

### 3. Une base au bon endroit

Le chemin d'une base DuckDB, dans `.bruin.yml`, part du dossier de `.bruin.yml` : la racine du fork. Change la ligne `path:` de `duckdb-default` pour qu'elle écrive dans ton dossier du module 5. Le `.gitignore` de ton fork ignore déjà les fichiers `*.duckdb`.

### 4. Valide, lance, interroge

~~~bash
bruin validate premier-pipeline
bruin run premier-pipeline
bruin query --connection duckdb-default --query "select * from dataset.player_stats"
~~~

Lis la sortie de `bruin run` : l'ordre des assets, puis les contrôles qualité, notés à part.

@@ hints
- Dans `.bruin.yml`, le chemin est relatif à la racine du fork : `mon-travail/module-05/premier.duckdb`, sans `/` au début.
- Si `git status` montre un fichier `duckdb.db` à la racine du fork, c'est la base du premier lancement, avant ton changement de chemin : supprime-la.
- `bruin validate` vérifie les noms, les dépendances et les connexions, sans rien exécuter : lance-le à chaque modification.

@@ solution
La partie DuckDB de `.bruin.yml`, à la racine du fork (la connexion `chess-default`, ajoutée par le modèle, reste en dessous) :

~~~yaml
default_environment: default

environments:
  default:
    connections:
      duckdb:
        - name: duckdb-default
          path: mon-travail/module-05/premier.duckdb   # relatif à la racine du fork
~~~

Ce que `bruin init` a créé :

~~~text
mon-travail/module-05/premier-pipeline/
├── README.md
├── pipeline.yml
└── assets/
    ├── players.asset.yml     # ingestion : les profils de joueurs, avec ingestr
    ├── player_stats.sql      # SQL : compte les joueurs par nom, avec ses contrôles
    └── my_python_asset.py    # Python : affiche hello world
~~~

Et, à la racine du fork : `.bruin.yml`, et une ligne `.bruin.yml` ajoutée à la fin du `.gitignore`. La fin de `bruin validate` :

~~~text
✓ Successfully validated 3 assets across 1 pipeline, all good.
~~~

@@ selfcheck
- Je sais où Bruin a créé `.bruin.yml`, et pourquoi il n'est pas commité
- Ma base est dans `mon-travail/module-05/`, ignorée par Git
- Je sais ce que `bruin validate` vérifie sans rien lancer

@@ breakfix
Supprime ta base (`rm mon-travail/module-05/premier.duckdb`), puis lance seulement l'asset SQL : `bruin run premier-pipeline/assets/player_stats.sql`. Lis l'erreur, et répare sans toucher au fichier.

@@ breakfix-hints
- Le message parle d'une table qui n'existe pas. Quel asset la crée ?
- Donner un fichier à `bruin run` lance ce seul fichier.
- Lancer le pipeline entier crée les tables dans l'ordre.

@@ breakfix-answer
~~~text
FAIL dataset.player_stats UUUUU
└── dataset.player_stats
    └── Internal: Catalog Error: Table with name players does not exist!
~~~

Sur une base neuve, `dataset.players` n'existe pas : l'asset d'ingestion n'a jamais tourné. Les `U` sont les contrôles qualité **sautés** (*upstream failed*) : sans table, rien à contrôler. `bruin run premier-pipeline` lance tout, dans l'ordre du lignage, et l'asset SQL passe. C'est la même règle que le `--select` de dbt sans `+`, au module 4.
