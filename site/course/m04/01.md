@@ brief
- L'**analytics engineer** fait le pont entre le data engineer (qui amène les données) et l'analyste (qui les exploite) : il **transforme** les données brutes en tables propres, testées et documentées.
- **ETL** : on transforme avant de charger. **ELT** : on charge d'abord les données brutes dans l'entrepôt, puis on les transforme **dedans**, en SQL. C'est l'approche de ce module.
- La **modélisation dimensionnelle** (Kimball) range les données en **tables de faits** (les événements : un trajet, une vente, beaucoup de lignes) et **tables de dimensions** (le contexte : une zone, un vendeur, peu de lignes). Ensemble, elles forment un **schéma en étoile**.
- Le module construit trois couches : **staging** (le brut nettoyé), **intermediate** (les jointures et calculs), **marts** (les tables prêtes pour l'analyse).

La table de faits, de très loin. Une ligne de `fct_trips` est **un trajet** : des millions de lignes, une par course. @@ constraints
- Un domaine de ton choix : une salle de sport, un club de foot, une bibliothèque, une boutique en ligne…
- Une table de faits : ce que représente **une ligne**, et au moins 4 colonnes, dont des mesures (des nombres qu'on additionne)
- Au moins 3 tables de dimensions, avec leurs colonnes, et la colonne qui les relie à la table de faits

- Une phrase : pourquoi ce domaine se prête à l'ELT plutôt qu'à l'ETL

@@ guide
### 1. Choisis la question de l'entreprise

Une table de faits répond à une question qui revient tous les jours. Exemple, pour une boulangerie : « combien a-t-on vendu, de quoi, quand, et dans quelle boutique ? ».

### 2. Trouve l'événement

Ce qui se produit des milliers de fois, c'est ta **table de faits**. Pour la boulangerie : une ligne de ticket de caisse. Ses mesures : la quantité, le prix payé.

### 3. Trouve le contexte

Chaque « quoi, où, qui, quand » de ta question devient une **dimension** : `dim_produits`, `dim_boutiques`, `dim_dates`. La table de faits garde seulement leur identifiant, par exemple `produit_id`.

### 4. Range-les dans les couches

Les données brutes de la caisse arrivent dans **staging**, renommées et typées. Les calculs entre plusieurs sources vont dans **intermediate**. Ce que l'analyste interroge (`fct_ventes`, les dimensions) va dans **marts**.

### 5. Écris-le

Un petit tableau par table dans `modele.md`, ou un schéma en texte : la table de faits au milieu, les dimensions autour.

@@ hints
- Si ta « table de faits » a peu de lignes et change rarement, c'est sans doute une dimension.
- Une mesure s'additionne : un montant, une quantité, une durée. Un identifiant ou un nom n'est pas une mesure.
- Le temps est presque toujours une dimension : on veut tout regrouper par jour, par mois, par année.

@@ solution
Un exemple pour une salle de sport :

~~~markdown
# L'entrepôt de ma salle de sport

Question : qui vient, quand, à quels cours, et combien ça rapporte ?

## fct_passages (marts) : une ligne = une entrée d'un membre dans une salle
| Colonne | Rôle |
| --- | --- |
| passage_id | identifiant |
| membre_id | → dim_membres |
| salle_id | → dim_salles |
| cours_id | → dim_cours (vide si pas de cours) |
| date_heure | → dim_dates par sa date |
| duree_minutes | mesure |
| montant_paye | mesure (0 pour un abonné) |

## dim_membres (marts) : membre_id, age, abonnement, date_inscription
## dim_salles (marts) : salle_id, ville, surface
## dim_cours (marts) : cours_id, nom, coach, niveau

Staging : stg_badges (les passages bruts des tourniquets), stg_abonnements (le logiciel de facturation).
Intermediate : int_passages_avec_abonnement (la jointure des deux).

ELT : les tourniquets et la facturation sont deux systèmes différents. On charge les deux tels quels,
puis on les croise en SQL dans l'entrepôt, et on peut refaire les calculs sans tout recharger.
~~~
