@@ brief
- Un **seed** est un petit CSV versionné dans le projet (`seeds/`) que `dbt seed` charge comme une table. Idéal pour les tables de correspondance qui changent rarement : les zones, les codes de paiement.
- Un seed se lit comme un modèle : `{{ ref('taxi_zone_lookup') }}`.
- Une **macro** est une fonction Jinja (`macros/*.sql`) qui **écrit du SQL** à ta place. Tu l'écris une fois, tu l'appelles partout : `{{ ma_macro('colonne') }}`.
- Un **package** est un projet dbt partagé, plein de macros et de tests. On le déclare dans `packages.yml`, et `dbt deps` le télécharge. Le plus connu : **dbt_utils**.

@@ codespaces
- Les deux CSV de correspondance sont déjà dans ton fork : `04-analytics-engineering/taxi_rides_ny/seeds/`. Ce sont des données de référence, pas du code à écrire : tu les copies.
- `dbt deps` télécharge les packages depuis hub.getdbt.com, et les range dans `dbt_packages/`, que le `.gitignore` de `dbt init` ignore déjà.

@@ predict
Dans `int_trips_unioned`, chaque trajet a déjà un fournisseur, une heure et une zone de départ. Pourquoi aurait-on besoin d'un identifiant unique `trip_id` en plus ? Et que se passe-t-il si deux lignes ont exactement la même combinaison ?

@@ predict-answer
Une table de faits a besoin d'**une clé** qui désigne un trajet sans ambiguïté, pour les jointures, les tests `unique`, et le chargement incrémental de la leçon 6. On la fabrique en hachant les colonnes qui identifient un trajet : c'est une **clé de substitution** (*surrogate key*). Si deux lignes ont la même combinaison, ce sont des **doublons** : les données brutes en contiennent. Le projet garde la première avec `qualify row_number() ... = 1` : on passe de 8 298 395 à 8 095 489 trajets en `dev`.

@@ practice
Charge les deux tables de correspondance en seeds, écris une macro pour la durée d'un trajet, et construis `dim_zones` et `int_trips`, avec un identifiant unique par trajet.

@@ constraints
- `seeds/taxi_zone_lookup.csv` et `seeds/payment_type_lookup.csv`, chargés par `uv run dbt seed`
- `models/marts/dim_zones.sql` lit le seed des zones et renomme `locationid` en `location_id`
- `macros/get_trip_duration_minutes.sql` : une macro qui prend deux colonnes de dates et renvoie la durée en minutes, avec la macro `dbt.datediff` (elle marche sur toutes les bases)
- `packages.yml` déclare `dbt-labs/dbt_utils`, installé par `uv run dbt deps`
- `models/intermediate/int_trips.sql` : un `trip_id` créé avec `dbt_utils.generate_surrogate_key` sur le fournisseur, l'heure de départ, la zone de départ et le type de service ; la description du paiement jointe depuis le seed ; un seul trajet par `trip_id`

@@ guide
### 1. Les seeds

~~~bash
cp ../../../04-analytics-engineering/taxi_rides_ny/seeds/*.csv seeds/
uv run dbt seed
~~~

(Lance-le depuis `mon_taxi/`.) Deux tables apparaissent dans `mon_dev`. Ouvre les CSV : quelles colonnes, combien de lignes ?

### 2. dim_zones

Un modèle de quatre lignes : un `select` sur `{{ ref('taxi_zone_lookup') }}`, avec la colonne de l'identifiant renommée.

### 3. Une macro

Une macro a cette forme, ici pour convertir des centimes en euros :

~~~sql
{% macro centimes_en_euros(colonne) %}
    round({{ colonne }} / 100.0, 2)
{% endmacro %}
~~~

Et s'appelle dans un modèle : `{{ centimes_en_euros('prix') }} as prix_euros`. Écris la tienne : deux arguments, et dans son corps, `{{ dbt.datediff(debut, fin, 'minute') }}`. Elle servira à la leçon 6.

### 4. Le package

`code packages.yml` à la racine de `mon_taxi/` :

~~~yaml
packages:
  - package: dbt-labs/dbt_utils
    version: [">=1.3.0", "<2.0.0"]
~~~

Puis `uv run dbt deps`. Un fichier `package-lock.yml` apparaît : il fixe la version exacte, comme `uv.lock`. Commite-le.

### 5. int_trips

Trois étapes dans des `with` : les trajets réunis (`ref('int_trips_unioned')`), les types de paiement (le seed), puis la jointure. Pour la clé :

~~~sql
{{ dbt_utils.generate_surrogate_key(['colonne_1', 'colonne_2']) }} as ma_cle
~~~

Pour garder une seule ligne par combinaison, DuckDB et BigQuery ont `qualify`, qui filtre sur une fonction de fenêtre :

~~~sql
qualify row_number() over (partition by colonne_1, colonne_2 order by autre_colonne) = 1
~~~

### 6. Construis et compte

~~~bash
uv run dbt run --select int_trips dim_zones
uv run dbt show --inline "select count(*), count(distinct trip_id) from {{ ref('int_trips') }}"
~~~

@@ hints
- Un `payment_type` peut être vide dans les données brutes : `coalesce(payment_type, 0)` le remplace par 0, qui vaut « Unknown » dans le seed.
- `left join` sur le seed, pas `join` : un code inconnu ne doit pas faire disparaître le trajet.
- Si dbt dit `dbt expects 1 package(s) ... but found only 0 package(s) installed in dbt_packages`, tu as oublié `uv run dbt deps`.
- Le `qualify` se place **après** le `from ... join ...`, à la toute fin de la requête.

@@ solution
`macros/get_trip_duration_minutes.sql` :

~~~sql
{# La durée en minutes entre deux dates. dbt.datediff écrit le bon SQL pour chaque base (DuckDB, BigQuery...) #}
{% macro get_trip_duration_minutes(pickup_datetime, dropoff_datetime) %}
    {{ dbt.datediff(pickup_datetime, dropoff_datetime, 'minute') }}
{% endmacro %}
~~~

`models/marts/dim_zones.sql` :

~~~sql
select
    locationid as location_id,
    borough,
    zone,
    service_zone
from {{ ref('taxi_zone_lookup') }}
~~~

`models/intermediate/int_trips.sql` :

~~~sql
with unioned as (
    select * from {{ ref('int_trips_unioned') }}
),

payment_types as (
    select * from {{ ref('payment_type_lookup') }}
),

cleaned_and_enriched as (
    select
        -- une clé unique fabriquée en hachant les colonnes qui identifient un trajet
        {{ dbt_utils.generate_surrogate_key(['u.vendor_id', 'u.pickup_datetime', 'u.pickup_location_id', 'u.service_type']) }} as trip_id,
        u.vendor_id, u.service_type, u.rate_code_id,
        u.pickup_location_id, u.dropoff_location_id,
        u.pickup_datetime, u.dropoff_datetime,
        u.store_and_fwd_flag, u.passenger_count, u.trip_distance, u.trip_type,
        u.fare_amount, u.extra, u.mta_tax, u.tip_amount, u.tolls_amount,
        u.ehail_fee, u.improvement_surcharge, u.total_amount,
        coalesce(u.payment_type, 0) as payment_type,
        coalesce(pt.description, 'Unknown') as payment_type_description
    from unioned u
    left join payment_types pt                     -- left : un code inconnu garde son trajet
        on coalesce(u.payment_type, 0) = pt.payment_type
)

select * from cleaned_and_enriched

-- Les doublons des données brutes : on garde le premier trajet de chaque combinaison
qualify row_number() over (
    partition by vendor_id, pickup_datetime, pickup_location_id, service_type
    order by dropoff_datetime
) = 1
~~~

@@ breakfix-answer
Sans `dbt_packages/` :

~~~text
Compilation Error
  dbt expects 1 package(s) based on packages specified in packages.yml, but found only 0 package(s) installed in dbt_packages. Run "dbt deps" to install package dependencies.
~~~

Les packages ne sont pas dans Git : chaque machine les installe avec `uv run dbt deps`, à la version fixée par `package-lock.yml`. Pour le `join` : sur janvier 2019, tous les codes de paiement existent dans le seed, donc le nombre ne change pas, et c'est le piège. Le jour où un nouveau code arrive (un `7`, par exemple), un `join` fait **disparaître** ces trajets sans aucune erreur, alors que `left join` les garde avec la description `Unknown`. Remets `left join` : avec une table de correspondance, on ne perd jamais une ligne de faits.
