@@ brief
- Une **source** déclare une table brute que dbt n'a pas créée : `sources.yml` lui donne un nom court, sa base et son schéma.
- Dans un modèle, `{{ source('raw', 'green_tripdata') }}` remplace le nom complet de la table. dbt sait alors d'où viennent tes données, et le dessine dans le lignage.
- Un modèle de **staging** fait peu de choses, mais toujours les mêmes : **renommer** les colonnes en snake_case clair, **convertir** les types avec `cast`, **filtrer** les lignes inutilisables. Une source = un modèle `stg_`.
- `dbt run --select <modèle>` construit un seul modèle. `dbt show --select <modèle>` affiche quelques lignes sans rien créer.

@@ predict-answer
Par défaut, dbt crée une **vue** (*view*) : une requête enregistrée, sans copie des données. La commande prend moins d'une seconde, parce que rien n'est calculé : la requête tournera chaque fois que quelqu'un lira la vue. C'est le bon choix pour le staging, que seuls les modèles suivants lisent. Le dossier `staging` du projet officiel le dit explicitement dans `dbt_project.yml` : `+materialized: view`.

@@ guide
### 1. Les dossiers

Dans `mon_taxi/models/`, crée trois dossiers : `staging`, `intermediate` et `marts`. Puis, dans `dbt_project.yml`, sous `models: mon_taxi:`, donne à chaque dossier sa matérialisation : des vues pour `staging`, des tables pour les deux autres. Exemple avec d'autres noms :

~~~yaml
models:
  ma_boutique:
    brut_nettoye:
      +materialized: view
~~~

### 2. Les sources

`code models/staging/sources.yml`. Une source a cette forme :

~~~yaml
sources:
  - name: caisse
    database: boutique
    schema: brut
    tables:
      - name: tickets
~~~

Pour DuckDB, `database` est le nom du fichier sans `.duckdb`.

### 3. Regarde les colonnes brutes

~~~bash
uv run dbt show --inline "select * from {{ source('raw', 'green_tripdata') }}" --limit 3
~~~

`--inline` lance une requête sans créer de fichier. L'affichage coupe les colonnes qui ne tiennent pas (`...`). Pour la liste complète, avec les types :

~~~bash
uv run python -c "import duckdb; print(duckdb.connect('../taxi_rides_ny.duckdb', read_only=True).sql('describe prod.green_tripdata'))"
~~~

Note les 20 colonnes et leurs noms.

### 4. Le modèle

`code models/staging/stg_green_tripdata.sql`. La structure conseillée par dbt, des `with` qui se lisent de haut en bas :

~~~sql
with source as (
    select * from {{ source('caisse', 'tickets') }}
),

renamed as (
    select
        cast(id_ticket as integer) as ticket_id,
        cast(date_heure as timestamp) as sold_at,
        cast(montant as numeric) as amount
    from source
    where id_ticket is not null
)

select * from renamed
~~~

Écris le tien, avec les 19 colonnes utiles des taxis verts. `congestion_surcharge` n'existe pas dans tous les fichiers : laisse-la de côté, comme le projet officiel.

### 5. Construis et regarde

~~~bash
uv run dbt run --select stg_green_tripdata
uv run dbt show --select stg_green_tripdata
~~~

@@ hints
- Le chemin `{{ source('raw', 'green_tripdata') }}` : le premier argument est le `name` de la source, le second le `name` de la table.
- Les identifiants et les codes (`vendorid`, `ratecodeid`, `pulocationid`, `payment_type`, `trip_type`) en `integer`, les dates en `timestamp`, les montants et la distance en `numeric`.
- `lpep` veut dire *Licensed Passenger Enhancement Program* : c'est le préfixe des taxis verts. Après renommage, `lpep_pickup_datetime` devient `pickup_datetime`.
- Si tu vois `depends on a source named 'raw.green_trip_data' which was not found`, le nom dans `source()` ne correspond à aucune table de `sources.yml`.

@@ solution
`models/staging/sources.yml` :

~~~yaml
sources:
  - name: raw
    description: Les trajets bruts des taxis, chargés par charger.py
    database: taxi_rides_ny      # le fichier taxi_rides_ny.duckdb
    schema: prod
    tables:
      - name: green_tripdata
      - name: yellow_tripdata
~~~

`models/staging/stg_green_tripdata.sql` :

~~~sql
with source as (
    select * from {{ source('raw', 'green_tripdata') }}
),

renamed as (
    select
        -- identifiants
        cast(vendorid as integer) as vendor_id,
        cast(ratecodeid as integer) as rate_code_id,
        cast(pulocationid as integer) as pickup_location_id,
        cast(dolocationid as integer) as dropoff_location_id,

        -- dates : lpep est le préfixe des taxis verts
        cast(lpep_pickup_datetime as timestamp) as pickup_datetime,
        cast(lpep_dropoff_datetime as timestamp) as dropoff_datetime,

        -- le trajet
        cast(store_and_fwd_flag as varchar) as store_and_fwd_flag,
        cast(passenger_count as integer) as passenger_count,
        cast(trip_distance as numeric) as trip_distance,
        cast(trip_type as integer) as trip_type,

        -- le paiement
        cast(fare_amount as numeric) as fare_amount,
        cast(extra as numeric) as extra,
        cast(mta_tax as numeric) as mta_tax,
        cast(tip_amount as numeric) as tip_amount,
        cast(tolls_amount as numeric) as tolls_amount,
        cast(ehail_fee as numeric) as ehail_fee,
        cast(improvement_surcharge as numeric) as improvement_surcharge,
        cast(total_amount as numeric) as total_amount,
        cast(payment_type as integer) as payment_type
    from source
    where vendorid is not null   -- un trajet sans fournisseur est inutilisable
)

select * from renamed
~~~

`uv run dbt run --select stg_green_tripdata` se termine par :

~~~text
1 of 1 OK created sql view model mon_dev.stg_green_tripdata ............ [OK in 0.08s]
Done. PASS=1 WARN=0 ERROR=0 SKIP=0 NO-OP=0 REUSED=0 TOTAL=1
~~~

Sans filtre de date, la vue lit les deux années : 6 835 902 trajets verts avec un `vendorid`. La leçon suivante ajoute le filtre de la target `dev`.

@@ breakfix-hints
- La première erreur arrive à la **compilation**, avant toute requête vers DuckDB : dbt vérifie ses sources lui-même.
- Avec le nom en dur, le modèle tourne. Lance `uv run dbt ls --select source:raw+` : ton modèle est-il dans la liste ?
- Et si demain le schéma des données brutes s'appelle `raw` au lieu de `prod` ?

@@ breakfix-answer
Avec la faute de frappe :

~~~text
Compilation Error
  Model 'model.mon_taxi.stg_green_tripdata' (models/staging/stg_green_tripdata.sql) depends on a source named 'raw.green_trip_data' which was not found
~~~

dbt refuse de lancer quoi que ce soit : il vérifie toutes les références **avant** d'écrire une ligne de SQL. Avec `prod.green_tripdata` écrit en dur, le modèle marche, mais dbt ne sait plus qu'il dépend de cette source : il disparaît de `dbt ls --select source:raw+`, du lignage de la documentation, et le jour où le schéma change, il faut retrouver chaque nom en dur à la main. Avec `source()`, on change une ligne de `sources.yml`. Remets `source()`.
