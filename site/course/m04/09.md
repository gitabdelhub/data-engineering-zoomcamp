@@ brief
- Les quatre commandes de tous les jours : `dbt run` (construire), `dbt test` (tester), `dbt build` (construire **et** tester, dans l'ordre, avec les seeds), `dbt compile` (écrire le SQL final sans rien lancer).
- `--select` choisit les modèles : `fct_trips` seul, `+fct_trips` (lui et ses parents), `fct_trips+` (lui et ses enfants), `staging` (un dossier), `tag:...`, `source:raw+`.
- `--target prod` construit dans le schéma de la target `prod`, sur toutes les données.
- `dbt retry` relance seulement ce qui a échoué ou a été sauté au dernier lancement. `dbt clean` supprime `target/` et `dbt_packages/`.

@@ codespaces
- Un `dbt build --target prod` traite environ 117 millions de trajets. Sur un Codespace de 2 cœurs (8 Go de mémoire), il peut manquer de mémoire : passe ton Codespace en **4 cœurs** (16 Go) pour cette étape, depuis la page github.com/codespaces, menu **⋯**, **Change machine type**. Il consomme alors ton quota gratuit deux fois plus vite : reviens à 2 cœurs après.
- Il faut aussi de la place : les tables `prod` prennent environ 15 Go dans le fichier DuckDB. Vérifie avec `df -h /workspaces`, et supprime `mon-travail/module-04/data/` si ce n'est pas déjà fait.
- Si un modèle échoue par manque de mémoire, `uv run dbt retry --target prod` reprend là où ça s'est arrêté.

@@ verified
- Les commandes et les sélections de cette leçon ont été testées avec dbt 1.12.6 en `dev`.
- La construction `prod` complète n'a pas pu aller au bout dans mon environnement de test, faute de place disque. Les chiffres de mémoire et de place sont des estimations, à partir de la taille mesurée des tables en `dev` (environ 25 à 50 octets par trajet et par table).

@@ predict-answer
`dbt build` avance **modèle par modèle** dans l'ordre du lignage, et lance les tests de chaque modèle **juste après** sa construction : seeds et leurs tests, staging et ses tests, `int_trips_unioned`, `int_trips` et ses tests, etc. Si un test de `int_trips` échoue, tout ce qui en dépend (`fct_trips`, le rapport) est **sauté** (`SKIP`) : dbt ne construit pas des tables sur des données qu'il sait fausses. `dbt run` puis `dbt test`, eux, construiraient tout avant de tester.

@@ guide
### 1. Liste avant de construire

`dbt ls` affiche ce qu'une sélection choisit, sans rien lancer. C'est le meilleur moyen d'apprendre la syntaxe :

~~~bash
uv run dbt ls --select stg_green_tripdata+
uv run dbt ls --select +dim_zones
uv run dbt ls --select staging
uv run dbt ls --resource-type test --select fct_trips
~~~

Note ce que chaque ligne renvoie.

### 2. Les commandes une par une

Essaie chaque commande de la consigne sur une petite sélection, et note sa sortie. Pour `retry`, provoque un échec : un test qui échoue (un `accepted_values` faux, par exemple), un `dbt build`, puis répare et `dbt retry`.

### 3. La prod

Vérifie la machine et la place (voir **Dans ton Codespace**), puis :

~~~bash
time uv run dbt build --target prod
~~~

`time` affiche la durée à la fin. Pendant ce temps, ouvre un deuxième terminal et lance `top` pour voir la mémoire utilisée.

### 4. Compare les deux targets

Le nombre de lignes de `fct_trips` dans `mon_dev` et dans `mon_prod`, avec `dbt show --inline` et `--target`.

@@ hints
- Le `+` se lit comme une flèche du lignage : devant, on remonte vers les parents ; derrière, on descend vers les enfants. Les deux : `+fct_trips+`.
- `dbt show --target prod --inline "select count(*) from {{ ref('fct_trips') }}"` lit la table de la target `prod`.
- Si tu vois `The profile 'mon_taxi' does not have a target named 'prd'`, la target n'existe pas dans `profiles.yml` : relis son nom.

@@ breakfix
Lance `uv run dbt run --select dim_zones --target prd` (une lettre manque). Lis l'erreur. Puis lance `uv run dbt build --select fct_trips` dans un terminal, et interromps-le avec `Ctrl+C` pendant qu'il construit. Comment reprendre sans tout relancer ?

@@ breakfix-hints
- La première erreur liste les targets valides de ton profil.
- Après une interruption, le dernier lancement n'est pas complet. Une commande relance seulement ce qui manque.
- `dbt retry` relit `target/run_results.json` pour savoir ce qui a échoué ou a été sauté.

@@ breakfix-answer
~~~text
Runtime Error
  The profile 'mon_taxi' does not have a target named 'prd'. The valid target names for this profile are:
   - dev
   - prod
~~~

dbt lit la liste des outputs de `profiles.yml` et te donne les noms valides. Après une interruption, `uv run dbt retry` reprend avec les mêmes options que la commande interrompue, et seulement les nœuds qui ne sont pas allés au bout. Sur un gros `build --target prod` qui a échoué par manque de mémoire, c'est un gain de plusieurs minutes.
