@@ brief
- 🔑 La documentation d'un projet dbt vit **dans le code** : des `description:` dans les fichiers YAML, sur les sources, les modèles, les colonnes, les seeds et les macros.
- `dbt docs generate` assemble tout dans `target/` : le projet (`manifest.json`) et le catalogue de la base (`catalog.json`, avec les types réels des colonnes).
- 🔑 `dbt docs serve` ouvre un site web local : chaque modèle, son SQL, ses colonnes, ses tests, et le **graphe du lignage**.
- Une description longue s'écrit sur plusieurs lignes avec `>` en YAML. Un bloc `{% docs %}` dans un fichier `.md` se réutilise à plusieurs endroits.

@@ codespaces
- `uv run dbt docs serve --port 8080` : VS Code propose d'ouvrir le port 8080 dans le navigateur. Sinon, onglet **Ports**, puis le globe. Si Airflow tourne encore du module 2, il occupe déjà le 8080 : prends `--port 8081`.
- Le site s'arrête avec `Ctrl+C` dans le terminal.

@@ verified
- `dbt docs generate` et `dbt docs serve` testés avec dbt 1.12.6 : le site répond, et `target/` contient `manifest.json`, `catalog.json` et `index.html`.
- `dbt docs generate` réécrit aussi `target/run_results.json`. Pour le défi, relance `dbt build` après la documentation, avant le script de vérification.

@@ predict
Tu ajoutes une `description:` à une colonne dans `schema.yml`, puis tu lances directement `dbt docs serve`, sans `generate`. La nouvelle description apparaît-elle sur le site ?

@@ predict-answer
**Non**. `serve` ne fait que servir les fichiers déjà dans `target/` : il affiche la documentation du dernier `generate`. Sur un projet tout neuf, ou après `dbt clean`, il échoue même, faute de dossier `target/`. Règle : `dbt docs generate`, puis `dbt docs serve`, à chaque changement.

@@ practice
Documente ton projet : chaque modèle des marts, ses colonnes et la source brute, puis ouvre le site de documentation et suis le lignage de `fct_monthly_zone_revenue`.

@@ constraints
- Dans `sources.yml`, une description pour la source `raw` et pour chacune de ses deux tables
- Dans `models/marts/schema.yml`, une description pour `dim_zones`, `fct_trips` et `fct_monthly_zone_revenue`, et pour au moins 6 colonnes de `fct_trips`
- Au moins une description longue, sur plusieurs lignes, avec `>`

@@ guide
### 1. Les descriptions

Dans un `schema.yml`, à côté des tests :

~~~yaml
models:
  - name: dim_clients
    description: >
      Un client par ligne. Les clients supprimés sont gardés
      avec la colonne est_supprime à true.
    columns:
      - name: client_id
        description: L'identifiant du client dans le logiciel de caisse
~~~

Pour les sources, la même `description:` sous la source et sous chaque table, dans `sources.yml`.

### 2. Un bloc de documentation réutilisable

`code models/docs.md` :

~~~markdown
{% docs pays_client %}
Le pays de facturation, en toutes lettres. Vide pour les clients d'avant 2020.
{% enddocs %}
~~~

Puis, dans le YAML : `description: "{{ doc('pays_client') }}"`. Écris le tien pour les 7 codes de paiement.

### 3. Génère et ouvre

~~~bash
uv run dbt docs generate
uv run dbt docs serve --port 8080
~~~

### 4. Explore

Ouvre `fct_trips` : ses colonnes, avec tes descriptions et les types venus de DuckDB. Puis le bouton bleu en bas à droite : le graphe du lignage. Dans le champ `--select` du graphe, tape `+fct_monthly_zone_revenue`.

@@ hints
- Les guillemets autour de `"{{ doc('payment_type') }}"` sont obligatoires en YAML, à cause des accolades.
- Après `>`, les lignes suivantes doivent être plus indentées que `description:`.
- Si `serve` dit `No such file or directory: '.../target'`, lance d'abord `generate`.

@@ solution
`models/docs.md` :

~~~markdown
{% docs payment_type %}
Le moyen de paiement, codé par la TLC de New York :

| Code | Signification |
| --- | --- |
| 0 | Inconnu (vide dans les données brutes) |
| 1 | Carte bancaire |
| 2 | Espèces |
| 3 | Sans frais |
| 4 | Contestation |
| 5 | Inconnu |
| 6 | Trajet annulé |

Les pourboires ne sont enregistrés que pour les paiements par carte.
{% enddocs %}
~~~

Un extrait de `models/marts/schema.yml` :

~~~yaml
models:
  - name: fct_trips
    description: >
      La table de faits des trajets de taxis verts et jaunes : un trajet par ligne,
      dédoublonné, avec les noms des zones de départ et d'arrivée.
    columns:
      - name: trip_id
        description: Clé de substitution (fournisseur, heure et zone de départ, type de service)
        data_tests: [unique, not_null]
      - name: payment_type
        description: "{{ doc('payment_type') }}"
      - name: trip_duration_minutes
        description: La durée du trajet en minutes, calculée par la macro get_trip_duration_minutes
~~~

Le projet officiel documente tout, avec plus de détails : ses fichiers `schema.yml` et `sources.yml` sont un bon modèle.

@@ breakfix

@@ breakfix-hints
- `dbt clean` supprime les dossiers listés dans `clean-targets` de `dbt_project.yml`. Lesquels ?
- La seconde erreur arrive à la compilation : dbt cherche un bloc de documentation par son nom.
- Un bloc `docs` et son `doc('...')` doivent porter **exactement** le même nom.

@@ breakfix-answer
Après `dbt clean`, le dossier `target/` n'existe plus :

~~~text
[Errno 2] No such file or directory: '.../mon_taxi/target'
~~~

`serve` ne fabrique rien, il sert ce que `generate` a écrit. Relance `uv run dbt docs generate`. Avec le bloc renommé, `generate` échoue à la compilation :

~~~text
Compilation Error
  Documentation for 'model.mon_taxi.fct_trips' depends on doc 'payment_type'  which was not found
~~~

`doc('payment_type')` ne trouve plus de bloc de ce nom : dbt vérifie les références de la documentation comme celles des modèles. Remets le même nom des deux côtés. `dbt clean` reste utile : il supprime aussi `dbt_packages/`, pour repartir d'une installation propre avec `dbt deps`.

@@ pas
>>> Raw NYC taxi trip data loaded from BigQuery
**Où mettre ce bloc :** pas dans un nouveau fichier. Tu **ajoutes les lignes `description:`** à ton `models/staging/sources.yml` existant. Garde ton nom de source (`raw`), ta `database` (`taxi_rides_ny`) et ton `schema` (`prod`) : ceux du bloc sont ceux du formateur sur BigQuery.

**Comment lire `description: >`** : le `>` permet d'écrire la description sur plusieurs lignes, en retrait. YAML les recolle en une seule phrase. Le retrait doit être plus grand que celui de `description:`.

>>> Zone lookup table containing LocationID
**Où mettre ce bloc :** un `schema.yml` dans le dossier de `dim_zones`, donc `models/marts/schema.yml` (`code models/marts/schema.yml`). S'il existe déjà avec `models:`, ajoute seulement le `- name: dim_zones` et ce qui suit : un seul `models:` par fichier.

**Attention au nom de colonne :** ton `dim_zones` (leçon des seeds) renomme `locationid` en `location_id`. Ici, `- name: locationid` ne correspond donc à aucune colonne : écris `- name: location_id`. Sinon la doc affiche une colonne fantôme, et le test `unique` échoue avec `column "locationid" not found`.

>>> Each row represents a single trip with:
**Où mettre ce bloc :** dans le même `models/marts/schema.yml`, sous `models:`, pour `fct_trips`. Si `fct_trips` y est déjà (tests de la leçon d'avant), ajoute seulement sa ligne `description: |` et le texte : un seul `- name: fct_trips` par fichier.

**`|` au lieu de `>` :** avec `|`, YAML **garde les retours à la ligne**. C'est ce qu'il faut pour une liste à puces comme ici.

**Générer et voir la doc (les deux commandes plus bas dans le texte), depuis `mon_taxi` :**

~~~bash
uv run dbt docs generate
uv run dbt docs serve --port 8080
~~~

La première écrit `target/catalog.json` (`Catalog written to ...`). La deuxième lance un petit site et occupe le terminal. VS Code propose d'ouvrir le port 8080 : clique **Ouvrir dans le navigateur**. Sinon, onglet **Ports**, ligne 8080, globe. Si le port 8080 est déjà pris (Airflow du module 2), prends `--port 8081`.

**Ce que tu dois voir :** à gauche, ton projet et ses modèles. Clique sur `fct_trips` : ta description, avec la liste à puces. En bas à droite, le bouton bleu ouvre le **graphe de lignage** : les sources en vert, puis staging, intermediate et marts. **Ctrl + C** dans le terminal arrête le site.
