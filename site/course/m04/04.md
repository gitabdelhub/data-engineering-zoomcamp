@@ brief
- `{{ ref('stg_green_tripdata') }}` désigne **un autre modèle** dbt. C'est grâce à `ref()` que dbt connaît l'ordre de construction : le **lignage** (*lineage*), un graphe des dépendances.
- `source()` pour les tables brutes, `ref()` pour tout le reste : jamais un nom de table écrit en dur.
- Un modèle **intermediate** prépare les données pour les marts : ici, réunir les taxis verts et jaunes dans une seule table, avec les mêmes colonnes dans le même ordre.
- **Jinja** (`{% if %}`, `{{ }}`) rend le SQL dynamique. `target.name` vaut `dev` ou `prod` : en `dev`, on ne garde qu'un mois pour aller vite.

@@ codespaces
- Les taxis jaunes sont gros : 109 millions de lignes sur deux ans. En `dev`, un mois suffit, et un `dbt run` prend quelques secondes au lieu de plusieurs minutes.
- `uv run dbt ls --select +int_trips_unioned` liste un modèle et tout ce dont il dépend, sans rien construire.

@@ verified
- Testé avec dbt 1.12.6 sur la target `dev` (janvier 2019) : **630 830** trajets verts, **7 667 565** jaunes, **8 298 395** dans `int_trips_unioned`.

@@ predict
Dans `int_trips_unioned`, tu réunis les verts et les jaunes. Si tu écris `union` au lieu de `union all`, le résultat change-t-il ? Et la durée ?

@@ predict-answer
`union` **supprime les lignes en double** entre les deux parties, `union all` garde tout. Ici, une ligne verte et une ligne jaune ne peuvent jamais être identiques, puisque la colonne `service_type` vaut `'Green'` ou `'Yellow'` : le nombre de lignes serait le même, mais `union` le calculerait beaucoup plus lentement, car il doit comparer 8 millions de lignes entre elles. Règle simple : `union all`, sauf si tu veux vraiment dédoublonner.

@@ guide
### 1. Le staging des jaunes

Copie ton modèle vert en `stg_yellow_tripdata.sql`, puis adapte : la source, le préfixe des dates (`tpep_` pour les jaunes, *Taxicab Passenger Enhancement Program*), et retire les deux colonnes qui n'existent pas. Vérifie avec `dbt show --inline` sur la source jaune, comme à la leçon 3.

### 2. Le filtre de la target dev

À la fin d'un modèle, un bloc Jinja ajoute du SQL seulement dans certains cas. Exemple :

~~~sql
select * from renamed
{% if target.name == 'dev' %}
where sold_at >= '2026-01-01'
{% endif %}
~~~

Ajoute le tien aux **deux** modèles de staging. `uv run dbt compile --select stg_green_tripdata` écrit le SQL final dans `target/compiled/` : ouvre-le pour voir ce que Jinja a produit.

### 3. Le modèle intermediate

`code models/intermediate/int_trips_unioned.sql`. Deux `with` qui lisent chacun un staging avec `ref()`, en listant les colonnes **dans le même ordre**, puis :

~~~sql
select * from green_trips
union all
select * from yellow_trips
~~~

Pour les colonnes qui manquent aux jaunes, une valeur fixe avec un type : `cast(1 as integer) as trip_type`.

### 4. Construis la chaîne

~~~bash
uv run dbt run --select +int_trips_unioned
~~~

Le `+` **devant** le nom veut dire « et tout ce dont il dépend ». Regarde l'ordre dans la sortie.

### 5. Compte

~~~bash
uv run dbt show --inline "select service_type, count(*) as n from {{ ref('int_trips_unioned') }} group by 1"
~~~

@@ hints
- `union all` associe les colonnes **par position**, pas par nom. Si `trip_type` est en 10e position chez les verts, elle doit l'être chez les jaunes.
- `target.name` vient de ton `profiles.yml` : c'est le nom de l'output utilisé, `dev` par défaut.
- Si dbt dit `depends on a node named 'stg_green_trips' which was not found`, le nom dans `ref()` ne correspond à aucun fichier `.sql` : c'est le **nom du fichier**, sans `.sql`.
- Le filtre porte sur `pickup_datetime`, la colonne renommée : il est après le `select * from renamed`.

@@ solution
La fin de `stg_green_tripdata.sql` et de `stg_yellow_tripdata.sql` :

~~~sql
select * from renamed

-- En dev, un seul mois : les modèles se construisent en quelques secondes
{% if target.name == 'dev' %}
where pickup_datetime >= '2019-01-01' and pickup_datetime < '2019-02-01'
{% endif %}
~~~

`models/intermediate/int_trips_unioned.sql` :

~~~sql
with green_trips as (
    select
        vendor_id, rate_code_id, pickup_location_id, dropoff_location_id,
        pickup_datetime, dropoff_datetime, store_and_fwd_flag, passenger_count,
        trip_distance, trip_type, fare_amount, extra, mta_tax, tip_amount,
        tolls_amount, ehail_fee, improvement_surcharge, total_amount, payment_type,
        'Green' as service_type
    from {{ ref('stg_green_tripdata') }}
),

yellow_trips as (
    select
        vendor_id, rate_code_id, pickup_location_id, dropoff_location_id,
        pickup_datetime, dropoff_datetime, store_and_fwd_flag, passenger_count,
        trip_distance,
        cast(1 as integer) as trip_type,     -- les jaunes ne prennent que des clients hélés dans la rue
        fare_amount, extra, mta_tax, tip_amount, tolls_amount,
        cast(0 as numeric) as ehail_fee,     -- pas de réservation par application chez les jaunes
        improvement_surcharge, total_amount, payment_type,
        'Yellow' as service_type
    from {{ ref('stg_yellow_tripdata') }}
)

-- union all : les deux parties ne peuvent pas avoir de ligne commune (service_type diffère)
select * from green_trips
union all
select * from yellow_trips
~~~

| ------------ | ------- |
| Green        |  630830 |
| Yellow       | 7667565 |
~~~
