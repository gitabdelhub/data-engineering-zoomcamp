@@ brief
- Jusqu'ici, `master("local[*]")` faisait tout tourner dans un seul processus. Un **cluster standalone** sépare les rôles : un **master** (port 7077, interface sur 8080) et un ou plusieurs **workers** qui s'enregistrent auprès de lui.
- 🔑 En production, on ne code pas l'adresse du master dans le script : on la donne à **`spark-submit`**, avec `--master spark://hôte:7077`. Le même script tourne alors en local, sur un cluster, ou dans le cloud.
- Les chemins d'entrée et de sortie deviennent des **arguments** (`argparse`), pour lancer le même script sur d'autres mois.
- La vidéo démarre le cluster avec `start-master.sh` et `start-worker.sh`, qui viennent de l'archive de Spark. Le paquet `pyspark` ne les a pas : tu passes par `spark-class`, qui lance les mêmes programmes Java.

@@ codespaces
- Le master et le worker tournent dans deux terminaux de ton Codespace, et `spark-submit` dans un troisième. L'interface du master apparaît sur le port **8080** de l'onglet Ports, celle de chaque job sur le port 4040.
- `spark-class` et `spark-submit` sont dans l'environnement uv : lance-les avec `uv run`.

@@ verified
- Testé avec PySpark 4.2.1 : `spark-class org.apache.spark.deploy.master.Master` et `...deploy.worker.Worker spark://localhost:7077` démarrent le cluster ; `spark-submit` du script officiel `06_spark_sql.py` sur les données de 2021 finit en 22 secondes et écrit 1 fichier.
- `ls .venv/lib/python3.*/site-packages/pyspark/sbin/` ne contient que des scripts du *history server* : pas de `start-master.sh`.
- Sans worker, le job ne démarre jamais et répète : `WARN TaskSchedulerImpl: Initial job has not accepted any resources; check your cluster UI to ensure that workers are registered and have sufficient resources`.

@@ predict
Tu démarres le master, mais tu oublies le worker. Tu lances `spark-submit --master spark://localhost:7077 ...`. Que se passe-t-il : une erreur immédiate, un calcul en local à la place, ou autre chose ?

@@ predict-answer
Autre chose, de plus sournois : **le job attend**. Le driver se connecte au master, qui l'accepte, mais aucun worker ne peut prendre de tâche. Spark répète toutes les 15 secondes `Initial job has not accepted any resources`, sans jamais échouer. Un job bloqué sans erreur se diagnostique dans l'interface du master (port 8080) : zéro worker, zéro cœur.

@@ guide
### 1. Le master

~~~bash

uv run spark-class org.apache.spark.deploy.master.Master --host localhost --port 7077 --webui-port 8080
~~~

### 2. Le worker

Dans un deuxième terminal, la même commande `spark-class`, avec la classe `org.apache.spark.deploy.worker.Worker` et l'adresse du master en argument. Rafraîchis la page du port 8080.

### 3. Le script à arguments

Un exemple :

~~~python
import argparse

parser = argparse.ArgumentParser()
parser.add_argument("--input", required=True)
parser.add_argument("--output", required=True)
args = parser.parse_args()

spark = SparkSession.builder.appName("ventes").getOrCreate()   # pas de .master() ici
spark.read.parquet(args.input)  # ...
~~~

Repars de ton `rapport.py` de la leçon 6, et remplace les chemins par les arguments.

### 4. spark-submit

~~~bash
uv run spark-submit --master spark://localhost:7077 ton_script.py --input=... --output=...
~~~

Les options de Spark vont **avant** le script, ses arguments **après**.

@@ breakfix-hints
- Le message contient « accepted any resources ».
- Regarde la ligne « Workers » de l'interface du port 8080.
- Spark n'abandonne pas un job qui attend des ressources.

@@ breakfix-answer
~~~text
WARN TaskSchedulerImpl: Initial job has not accepted any resources; check your cluster UI to ensure that workers are registered and have sufficient resources
~~~

Le message revient sans fin : il n'y a pas d'erreur à attendre, le job attend un worker pour toujours. Dès que le worker redémarre et s'enregistre, le master lui donne le job, et il finit normalement. Ce message apparaît aussi quand un worker existe mais n'a pas assez de cœurs ou de mémoire pour ce que le job demande : l'interface du master le montre.
