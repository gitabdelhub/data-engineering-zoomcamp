@@ brief
- Dans le cloud, les fichiers ne sont plus sur ton disque mais dans un **bucket** Google Cloud Storage, avec des chemins `gs://bucket/...`. Spark les lit comme des fichiers locaux, une fois qu'il a le **connecteur GCS**.
- **Dataproc** est le service Spark géré de Google : il crée un cluster en deux minutes, avec Spark, le connecteur GCS et le connecteur BigQuery déjà installés. Tu paies tant qu'il tourne.
- `gcloud dataproc jobs submit pyspark` est le `spark-submit` de Dataproc : les options **avant** `--`, les arguments du script **après**.
- Pour écrire dans **BigQuery**, on remplace l'écriture parquet par `df.write.format("bigquery").option("table", "dataset.table").save()`, avec un bucket temporaire.

@@ codespaces
- Tout se pilote depuis ton Codespace avec `gcloud`, déjà installé par ton devcontainer (module 0), et ta clé du module 1, dans `~/.gcp/key.json`, recréée depuis le secret `GCP_SA_KEY`. **La clé ne va jamais dans Git.**
- **Coût** : un cluster Dataproc facture à la minute, même s'il ne fait rien. Crée-le avec `--max-idle=30m`, pour qu'il se supprime seul après 30 minutes sans job, et supprime-le toi-même à la fin. Sur les crédits gratuits, une heure coûte quelques dizaines de centimes.

@@ verified
- **Non testé** dans mon environnement : il n'a pas accès à Google Cloud. Les commandes viennent du cours officiel et de la documentation de Dataproc. Si une commande échoue, le message d'erreur de `gcloud` dit presque toujours quoi faire (une API à activer, un rôle à ajouter).
- Ton script n'a rien de propre à Spark 4 : il tourne aussi sur la version de Spark de l'image Dataproc (Spark 3.5 sur les images 2.2).
- Le cours officiel connecte aussi Spark **local** à GCS avec un fichier `.jar` (leçon officielle 13). Dataproc l'a déjà : cette leçon passe directement au cluster.

@@ constraints
- Le parquet de 2020 et 2021 est dans `gs://<ton-bucket>/pq/`, et ton script dans `gs://<ton-bucket>/code/`
- Le cluster est créé en `--single-node`, avec `--max-idle=30m`, dans la région de ton bucket
- Un `gcloud dataproc jobs submit pyspark` écrit le rapport de 2020 dans `gs://<ton-bucket>/report-2020/`
- Une variante du script écrit le rapport de 2021 dans une table BigQuery de ton dataset du module 3
- Le cluster est supprimé, et `gcloud dataproc clusters list --region=<ta-région>` n'affiche plus rien
- `git status` ne montre aucune clé

@@ guide
### 1. Se connecter

~~~bash
echo "$GCP_SA_KEY" > ~/.gcp/key.json      # si ton Codespace a été recréé
gcloud auth activate-service-account --key-file ~/.gcp/key.json
gcloud config set project <ton-projet>
gcloud services enable dataproc.googleapis.com
~~~

### 2. Envoyer les fichiers

`gcloud storage cp -r data/pq gs://<ton-bucket>/pq` envoie le dossier (1,2 Go : quelques minutes). Puis ton script dans `gs://<ton-bucket>/code/`.

### 3. Le cluster

~~~bash
gcloud dataproc clusters create zoomcamp-spark \
    --region=<ta-région> --single-node \
    --master-machine-type=e2-standard-4 --master-boot-disk-size=50 \
    --max-idle=30m
~~~

### 4. Le job

La commande est dans le texte de la leçon officielle, plus bas, section *Submitting a job with gcloud*. Adapte le nom du cluster, la région et les chemins. Suis le job dans la console Google Cloud, page **Dataproc > Tâches**.

### 5. BigQuery

Copie ton script en `rapport_bq.py`, et remplace l'écriture parquet par l'écriture `bigquery` de la leçon officielle 16. Le bucket temporaire : le cluster en crée un, nommé `dataproc-temp-...`, visible avec `gcloud storage ls`. Puis un second job, avec `--output=<ton-dataset>.reports_2021`.

### 6. Supprimer

`gcloud dataproc clusters delete zoomcamp-spark --region=<ta-région>`.

@@ hints
- Le nom de ton bucket et ta région sont dans tes fichiers Terraform du module 1.
- `Permission denied` au premier job : ton compte de service n'a pas le rôle **Dataproc Administrator** (ou **Dataproc Editor**). La leçon officielle explique où l'ajouter.
- `Failed to find data source: bigquery` : le connecteur manque. Les images Dataproc 2.1 et plus récentes l'ont ; sinon, `--jars=gs://spark-lib/bigquery/spark-bigquery-latest_2.12.jar`.
- Les motifs `*` des chemins `gs://` vont entre guillemets, comme à la leçon 10.
- Un cluster oublié coûte de l'argent : vérifie la liste des clusters à la fin de chaque séance.

@@ solution
Les commandes, une fois connecté :

~~~bash
cd /workspaces/data-engineering-zoomcamp/mon-travail/module-06
BUCKET=<ton-bucket>
REGION=<ta-région>

gcloud storage cp -r data/pq "gs://${BUCKET}/pq"
gcloud storage cp rapport_submit.py rapport_bq.py "gs://${BUCKET}/code/"

gcloud dataproc clusters create zoomcamp-spark \
    --region="${REGION}" --single-node \
    --master-machine-type=e2-standard-4 --master-boot-disk-size=50 \
    --max-idle=30m

gcloud dataproc jobs submit pyspark \
    --cluster=zoomcamp-spark --region="${REGION}" \
    "gs://${BUCKET}/code/rapport_submit.py" \
    -- \
        --input_green="gs://${BUCKET}/pq/green/2020/*/" \
        --input_yellow="gs://${BUCKET}/pq/yellow/2020/*/" \
        --output="gs://${BUCKET}/report-2020"

gcloud dataproc jobs submit pyspark \
    --cluster=zoomcamp-spark --region="${REGION}" \
    "gs://${BUCKET}/code/rapport_bq.py" \
    -- \
        --input_green="gs://${BUCKET}/pq/green/2021/*/" \
        --input_yellow="gs://${BUCKET}/pq/yellow/2021/*/" \
        --output=<ton-dataset>.reports_2021

gcloud dataproc clusters delete zoomcamp-spark --region="${REGION}"
~~~

Dans `rapport_bq.py`, la fin devient :

~~~python
spark.conf.set("temporaryGcsBucket", "<le-bucket-dataproc-temp>")
df_result.write.format("bigquery").option("table", args.output).save()
~~~

Pas de `coalesce(1)` : BigQuery range lui-même les données.

@@ breakfix
Avant de créer un cluster, imagine l'oubli : tu fermes ton Codespace un vendredi soir, le cluster créé **sans** `--max-idle` tourne tout le week-end. Calcule le coût avec la page des prix de Dataproc et de Compute Engine pour un `e2-standard-4`. Puis trouve deux protections qui t'auraient évité la facture, en plus de `--max-idle`.

@@ breakfix-hints
- Dataproc facture un supplément par processeur virtuel et par heure, **en plus** de la machine.
- Un week-end, c'est environ 60 heures.
- Google Cloud permet de recevoir une alerte quand un budget est dépassé.

@@ breakfix-answer
Pour 60 heures, compte la machine (`e2-standard-4`, 4 processeurs virtuels) plus le supplément Dataproc (4 × le prix horaire par processeur), plus le disque : selon la région, de l'ordre de 10 à 15 dollars. Pas une ruine sur les crédits gratuits, mais avec un cluster de production à plusieurs nœuds, la même erreur coûte des centaines de dollars. Protections : `--max-idle` (suppression après inactivité), `--max-age` (suppression après une durée fixe, même s'il travaille), et une **alerte de budget** dans **Facturation > Budgets et alertes**, qui t'envoie un e-mail à 50 %, 90 % et 100 % d'un montant que tu choisis. La règle du cloud : tout ce qui tourne coûte, et ce qui coûte doit avoir une date de fin.
