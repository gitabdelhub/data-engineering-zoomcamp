# Un cluster kind dans ton Codespace

Un vrai cluster coûte de l'argent dans le cloud. Pour apprendre, **kind** (*Kubernetes IN Docker*) fait tourner un cluster complet **dans un conteneur Docker** : chaque nœud est un conteneur. C'est gratuit, ça tourne dans ton Codespace, et c'est ce qu'utilise le workshop de DataTalksClub.

Tu as besoin de deux programmes :

- **`kubectl`**, la télécommande de n'importe quel cluster Kubernetes (kind, GKE chez Google, EKS chez Amazon...) ;
- **`kind`**, qui crée et supprime des clusters locaux.

## Installer les deux dans `~/bin`

Le workshop installe tout dans un dossier `bin` de ton dossier personnel. J'épingle des versions précises, testées ensemble : le cours marchera pareil dans six mois.

```bash
mkdir -p ~/bin && cd ~/bin
curl -Lo kubectl https://dl.k8s.io/release/v1.34.1/bin/linux/amd64/kubectl
curl -Lo kind https://kind.sigs.k8s.io/dl/v0.30.0/kind-linux-amd64
chmod +x kubectl kind
echo 'export PATH="$HOME/bin:$PATH"' >> ~/.bashrc
source ~/.bashrc
kubectl version --client
kind version
```

`chmod +x` rend un fichier **exécutable** : sans ça, Linux refuse de le lancer (`Permission denied`). La ligne `echo ... >> ~/.bashrc` ajoute `~/bin` au `PATH` de chaque nouveau terminal.

## 🔑 Créer le cluster

```bash
kind create cluster --name zoomcamp --image kindest/node:v1.34.0
```

La première fois, kind télécharge l'image du nœud (environ 450 Mo) : compte une à deux minutes. Ensuite :

```bash
kubectl cluster-info --context kind-zoomcamp
kubectl get nodes
docker ps
```

Tu vois **un nœud**, `zoomcamp-control-plane`, et dans `docker ps` le **conteneur** du même nom : ton cluster entier est dans ce conteneur.

## Le contexte : à quel cluster tu parles

`kind` a écrit l'adresse du cluster et une clé dans `~/.kube/config`, sous le nom de **contexte** `kind-zoomcamp`. `kubectl` envoie ses commandes au contexte actif :

```bash
kubectl config get-contexts
kubectl config current-context
```

En entreprise, tu auras plusieurs contextes (dev, prod...). Avant une commande qui supprime quelque chose, regarde toujours sur **quel** contexte tu es.

## Ton premier pod

```bash
kubectl run bonjour --image=busybox:1.37 --restart=Never -- sh -c 'echo "Bonjour depuis $(hostname)"'
kubectl get pods
kubectl logs bonjour
kubectl delete pod bonjour
```

`--restart=Never` crée un pod seul, qui s'arrête quand sa commande finit. Son statut passe de `ContainerCreating` à `Completed`. `kubectl logs` affiche ce que le conteneur a écrit, comme `docker logs`.

## Les commandes de base

| Commande | Ce qu'elle fait |
| --- | --- |
| `kubectl get pods` (ou `po`) | La liste des pods, avec leur état |
| `kubectl get all` | Pods, Deployments, Services... d'un coup |
| `kubectl describe pod <nom>` | Tous les détails, et **les événements en bas** : c'est là qu'on lit pourquoi un pod ne démarre pas |
| `kubectl logs <nom>` | Ce qu'a écrit le conteneur |
| `kubectl apply -f <fichier>` | Créer ou mettre à jour depuis un manifeste |
| `kubectl delete -f <fichier>` | Supprimer ce que décrit le manifeste |
| `kubectl explain pod.spec` | La documentation d'un champ, dans le terminal |

## Quand tu as fini ta séance

Un cluster kind consomme de la mémoire même quand tu ne t'en sers pas. Deux options :

- **Le garder** : il survit à l'arrêt de ton Codespace, mais il faut parfois le rallumer au retour (tu le verras dans « casser et réparer »).
- **Le supprimer** : `kind delete cluster --name zoomcamp`. Tes manifestes sont dans Git, tu recrées tout en deux minutes.

**Tu pars de** : ton Codespace, avec Docker. Rien d'autre.

@@ constraints
- `kubectl get nodes` affiche `zoomcamp-control-plane` avec le statut `Ready`
- `kubectl config current-context` affiche `kind-zoomcamp`
- Un pod `horloge`, image `busybox:1.37`, a affiché la date du jour, et `kubectl logs horloge` la montre

@@ guide
### 1. Les deux programmes

Copie le bloc d'installation de la leçon, puis vérifie avec `kubectl version --client` et `kind version`. Si le terminal répond `command not found`, c'est le `PATH` : lance `source ~/.bashrc`, ou ouvre un nouveau terminal.

### 2. Le cluster

`kind create cluster --name zoomcamp --image kindest/node:v1.34.0`. Attends la ligne `Have a nice day!`, puis `kubectl get nodes`. Si le nœud est `NotReady`, attends 20 secondes : il démarre encore.

### 3. Le pod

Sur le modèle de `bonjour`, mais la commande est `date`. Un pod `--restart=Never` qui affiche une seule chose finit tout de suite : son statut passe à `Completed`.

### 4. Où a-t-il tourné ?

`-o wide` ajoute des colonnes à `kubectl get`, dont `NODE`. Ici il n'y a qu'un nœud : dans un vrai cluster, ce serait l'une des machines.

@@ hints
- `kubectl run horloge --image=busybox:1.37 --restart=Never -- date` : tout ce qui suit `--` est la commande du conteneur.
- Si le pod reste en `ContainerCreating`, l'image se télécharge : `kubectl describe pod horloge` le confirme dans les événements (`Pulling image`).

@@ solution
~~~bash
# Les programmes, dans ~/bin
mkdir -p ~/bin && cd ~/bin
curl -Lo kubectl https://dl.k8s.io/release/v1.34.1/bin/linux/amd64/kubectl
curl -Lo kind https://kind.sigs.k8s.io/dl/v0.30.0/kind-linux-amd64
chmod +x kubectl kind
echo 'export PATH="$HOME/bin:$PATH"' >> ~/.bashrc
source ~/.bashrc

# Le cluster : un conteneur Docker qui contient tout Kubernetes
kind create cluster --name zoomcamp --image kindest/node:v1.34.0
kubectl get nodes                      # zoomcamp-control-plane   Ready
kubectl config current-context         # kind-zoomcamp

# Un pod qui affiche la date puis s'arrête
kubectl run horloge --image=busybox:1.37 --restart=Never -- date
kubectl get pod horloge -o wide        # STATUS Completed, NODE zoomcamp-control-plane
kubectl logs horloge                   # la date, à l'heure UTC du cluster
kubectl delete pod horloge
~~~

@@ breakfix
Simule un Codespace qui redémarre : `docker stop zoomcamp-control-plane`. Lance `kubectl get nodes` et lis le message. Que s'est-il passé, et comment rallumer ton cluster **sans le recréer** ?

@@ breakfix-hints
- Le message parle d'une connexion refusée vers une adresse `127.0.0.1:<port>` : c'est l'adresse du plan de contrôle, dans le conteneur.
- `docker ps -a` montre aussi les conteneurs arrêtés.

@@ breakfix-answer
`kubectl` répond `The connection to the server 127.0.0.1:<port> was refused` : le conteneur qui **est** ton cluster est arrêté, donc personne ne répond. Le relancer suffit : `docker start zoomcamp-control-plane`. Attends 20 à 30 secondes, puis `kubectl get nodes` : le nœud revient `Ready`, avec tout ce que tu y avais créé, car l'état du cluster est gardé dans le conteneur.

C'est ce qui peut t'arriver au retour d'une pause de ton Codespace. Si le cluster refuse vraiment de repartir, supprime-le et recrée-le : tes manifestes sont dans Git.
