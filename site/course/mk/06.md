# L'autoscaling avec le HPA

Ton service a 3 copies, jour et nuit. La nuit, elles ne font rien ; un jour de forte demande, elles ne suffisent plus. Le **HorizontalPodAutoscaler** (HPA) ajuste le nombre de pods tout seul, selon l'usage du processeur.

## Les mesures : metrics-server

Pour décider, le HPA doit savoir combien de CPU consomme chaque pod. C'est le travail de **metrics-server**, un petit service qui interroge le kubelet de chaque nœud. Il n'est pas installé dans kind :

```bash
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/download/v0.8.1/components.yaml
kubectl patch -n kube-system deployment metrics-server --type=json \
  -p '[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'
kubectl get deployment metrics-server -n kube-system
```

Le `patch` ajoute une option : dans kind, le kubelet se présente avec un certificat que metrics-server ne peut pas vérifier. `--kubelet-insecure-tls` lui dit de l'accepter. C'est acceptable sur ton cluster d'apprentissage, **jamais** en production.

Attends `READY 1/1`, puis, une minute plus tard :

```bash
kubectl top pods
```

## Le HPA

```bash
cd /workspaces/data-engineering-zoomcamp/mon-travail/kubernetes/k8s
curl -o hpa.yaml https://raw.githubusercontent.com/DataTalksClub/machine-learning-zoomcamp/da53bea959d70b21b9dd894ce981f418a35a24e3/10-kubernetes/workshop/k8s/hpa.yaml
```

```yaml
spec:
  scaleTargetRef:                # le Deployment qu'il pilote
    kind: Deployment
    name: clothing-classifier
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 50   # viser 50 % du CPU **demandé** (requests), en moyenne
```

🔑 Le pourcentage se calcule par rapport aux **`requests`** du Deployment (ici `250m`), pas à la machine. Sans `requests` CPU, le HPA ne peut rien calculer et affiche `<unknown>`.

🔑 Une fois le HPA en place, c'est **lui** qui fixe le nombre de copies. Retire la ligne `replicas:` de `deployment.yaml` : sinon, chaque `kubectl apply` remet ton chiffre, et le HPA doit tout recorriger. Attention, au premier `apply` sans cette ligne, Kubernetes repasse le Deployment à **1** copie (la valeur par défaut) ; le HPA le remonte à son minimum, 2, quelques secondes plus tard. Applique donc le HPA **avant** ou en même temps.

## Le test de charge

Le workshop fournit `load_test.py`, qui envoie 1 000 requêtes, 50 à la fois :

```bash
cd /workspaces/data-engineering-zoomcamp/mon-travail/kubernetes
curl -o load_test.py https://raw.githubusercontent.com/DataTalksClub/machine-learning-zoomcamp/da53bea959d70b21b9dd894ce981f418a35a24e3/10-kubernetes/workshop/load_test.py
sed -i 's#http://bit.ly/mlbookcamp-pants#https://raw.githubusercontent.com/alexeygrigorev/clothing-dataset-small/master/test/pants/4aabd82c-82e1-4181-a84d-d0c6e550d26d.jpg#' load_test.py
uv run --with requests python load_test.py
```

`uv run --with requests` lance le script avec `requests` installé pour l'occasion, sans toucher à ton projet. Le tunnel `port-forward` vers le port `30080` doit être ouvert.

Pendant le test, dans un autre terminal : `kubectl get hpa -w`. Le nombre de copies monte en quelques dizaines de secondes. Après le test, il **redescend lentement** : par défaut, le HPA attend 5 minutes de calme avant de retirer des pods, pour ne pas osciller.

@@ brief
- metrics-server mesure le CPU des pods ; le HPA s'en sert pour ajuster le nombre de copies.
- 🔑 La cible en pourcentage se calcule sur les `requests` CPU du conteneur.
- 🔑 Avec un HPA, retire `replicas:` du Deployment.
- La descente est volontairement lente (5 minutes).

@@ verified
- metrics-server 0.8.1, son `patch` et `hpa.yaml` du workshop acceptés par un vrai serveur d'API Kubernetes 1.34.1.
- **Pas testé ici** : la montée en charge elle-même. Le nombre de pods atteint dépend de ta machine : avec 2 cœurs, le test peut n'en ajouter que quelques-uns.

@@ predict
Tu installes le HPA, puis tu lances `kubectl apply -f deployment.yaml` avec `replicas: 3`, alors que le HPA venait de monter à 6 pods pendant un test de charge. Combien de pods juste après, et une minute plus tard ?

@@ predict-answer
Juste après, **3** : ton `apply` a remis le chiffre du fichier, et Kubernetes supprime 3 pods. Une minute plus tard, si la charge continue, le HPA remonte vers **6**. Tu as créé une coupure pour rien. C'est pour ça qu'on retire `replicas:` du manifeste dès qu'un HPA pilote le Deployment.

@@ practice
**Objectif** : voir ton service passer tout seul de 2 pods à plus de 2 sous la charge, puis redescendre.

**Tu pars de** : ton Deployment `clothing-classifier` en `v2` (leçon 5), le tunnel vers le port `30080`, et tes manifestes dans `mon-travail/kubernetes/k8s/`.

@@ constraints
- `kubectl top pods` affiche le CPU et la mémoire de chaque pod
- `kubectl get hpa` affiche une cible du type `cpu: 3%/50%`, pas `<unknown>/50%`
- Pendant `load_test.py`, la colonne `REPLICAS` de `kubectl get hpa -w` dépasse 2
- `deployment.yaml` n'a plus de ligne `replicas:`, et 5 à 10 minutes après le test, le HPA est revenu à 2

@@ hints
- `kubectl top` répond `Metrics API not available` : metrics-server n'est pas encore prêt, ou le `patch` manque. `kubectl logs -n kube-system deploy/metrics-server` le dit.
- La cible reste `<unknown>` : il faut une ou deux minutes de mesures, et des `requests` CPU dans le Deployment.
- Le test finit vite sans faire monter le CPU : beaucoup de requêtes échouent peut-être (`Failed requests`). Vérifie le tunnel, et relance-le si besoin.

@@ solution
~~~bash
# Les mesures
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/download/v0.8.1/components.yaml
kubectl patch -n kube-system deployment metrics-server --type=json \
  -p '[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'
kubectl rollout status -n kube-system deployment/metrics-server
kubectl top pods                       # après une minute

# Le HPA, et le Deployment sans replicas
cd /workspaces/data-engineering-zoomcamp/mon-travail/kubernetes/k8s
curl -o hpa.yaml https://raw.githubusercontent.com/DataTalksClub/machine-learning-zoomcamp/da53bea959d70b21b9dd894ce981f418a35a24e3/10-kubernetes/workshop/k8s/hpa.yaml
sed -i '/replicas:/d' deployment.yaml
kubectl apply -f hpa.yaml -f deployment.yaml
kubectl get hpa                        # TARGETS cpu: 2%/50%, REPLICAS 2 (ou 3, il redescend)

# La charge : terminal 1 le tunnel, terminal 2 la surveillance, terminal 3 le test
kubectl port-forward service/clothing-classifier 30080:8080
kubectl get hpa -w
cd .. && uv run --with requests python load_test.py
~~~
