# Deployment, Service et sondes de santé

Ton image marche dans Docker. Maintenant, tu demandes à Kubernetes d'en garder **deux copies** en vie, et de les rendre joignables sous un seul nom.

## 🔑 Donner l'image au cluster

Ton cluster kind vit dans son propre conteneur : il ne voit **pas** les images de ton Docker. Il faut les lui copier :

```bash
kind load docker-image clothing-classifier:v1 --name zoomcamp
```

En entreprise, on pousse plutôt l'image dans un **registre** (Docker Hub, Artifact Registry chez Google, ECR chez Amazon), et le cluster la télécharge de là. Avec kind, `kind load` remplace le registre.

## Le Deployment

```bash
mkdir -p /workspaces/data-engineering-zoomcamp/mon-travail/kubernetes/k8s
cd /workspaces/data-engineering-zoomcamp/mon-travail/kubernetes/k8s
curl -o deployment.yaml https://raw.githubusercontent.com/DataTalksClub/machine-learning-zoomcamp/da53bea959d70b21b9dd894ce981f418a35a24e3/10-kubernetes/workshop/k8s/deployment.yaml
```

Lis-le. Les parties qui comptent :

```yaml
spec:
  replicas: 2                        # deux pods identiques
  selector:
    matchLabels:
      app: clothing-classifier       # « mes pods sont ceux qui ont cette étiquette »
  template:                          # le modèle de chaque pod
    metadata:
      labels:
        app: clothing-classifier     # l'étiquette posée sur chaque pod
    spec:
      containers:
      - name: clothing-classifier
        image: clothing-classifier:v1
        imagePullPolicy: Never       # ne jamais télécharger : l'image est déjà là (kind load)
```

🔑 Les **étiquettes** (*labels*) sont la colle de Kubernetes. Le Deployment ne connaît pas ses pods par leur nom, mais par leur étiquette `app: clothing-classifier`. Le Service, plus bas, les trouve de la même façon.

### Les ressources

```yaml
        resources:
          requests: {memory: "256Mi", cpu: "250m"}   # ce que le pod réserve pour être placé
          limits:   {memory: "512Mi", cpu: "500m"}   # ce qu'il n'a jamais le droit de dépasser
```

`250m` veut dire 250 millièmes d'un cœur, soit un quart. Un conteneur qui dépasse sa limite de **mémoire** est tué (`OOMKilled`) ; un conteneur qui dépasse sa limite de **CPU** est seulement ralenti.

### 🔑 Les deux sondes

```yaml
        livenessProbe:               # « es-tu vivant ? » Sinon, Kubernetes redémarre le conteneur
          httpGet: {path: /health, port: 8080}
          initialDelaySeconds: 10
          periodSeconds: 10
        readinessProbe:              # « es-tu prêt à recevoir du trafic ? » Sinon, le Service ne t'envoie rien
          httpGet: {path: /health, port: 8080}
          initialDelaySeconds: 5
          periodSeconds: 5
```

Voilà à quoi sert `/health`. Un pod qui démarre n'est pas encore **prêt** : il charge son modèle. La colonne `READY` de `kubectl get pods` passe de `0/1` à `1/1` quand la sonde de disponibilité répond.

```bash
kubectl apply -f deployment.yaml
kubectl get deployments
kubectl get pods
kubectl logs -l app=clothing-classifier --tail=20
```

`-l app=clothing-classifier` choisit les pods par leur étiquette : tu n'as pas besoin de connaître leurs noms.

## Le Service

```bash
curl -o service.yaml https://raw.githubusercontent.com/DataTalksClub/machine-learning-zoomcamp/da53bea959d70b21b9dd894ce981f418a35a24e3/10-kubernetes/workshop/k8s/service.yaml
kubectl apply -f service.yaml
kubectl get services
```

Le Service s'appelle `clothing-classifier`. Tout pod du cluster peut maintenant joindre l'API à l'adresse `http://clothing-classifier:8080`, et le Service répartit les requêtes entre les pods **prêts**.

Le workshop le déclare en `NodePort` (port `30080` ouvert sur le nœud). Comme il le dit lui-même, un cluster kind n'est pas réglé pour ça, donc on passe par un **tunnel** depuis ton terminal :

```bash
kubectl port-forward service/clothing-classifier 30080:8080
```

Ce terminal reste occupé tant que le tunnel est ouvert. Dans un autre :

```bash
curl http://localhost:30080/health
```

Dans le cloud, on utilise plutôt un Service de type `LoadBalancer` : le fournisseur crée une vraie adresse publique.

@@ brief
- 🔑 `kind load docker-image` copie ton image dans le cluster ; en entreprise, c'est un registre.
- 🔑 Les **étiquettes** relient tout : le Deployment et le Service trouvent leurs pods par `app: clothing-classifier`.
- La sonde **liveness** redémarre un conteneur malade ; la sonde **readiness** le retire du trafic tant qu'il n'est pas prêt.
- `kubectl port-forward` ouvre un tunnel de ton terminal vers un Service.

@@ predict
Tu supprimes un des deux pods avec `kubectl delete pod <nom>` pendant que `kubectl get pods -w` tourne dans un autre terminal. Que vois-tu défiler ? Et pendant ce temps, l'API répond-elle encore par le tunnel ?

@@ predict-answer
Tu vois l'ancien pod passer en `Terminating`, et **un nouveau pod** apparaître presque en même temps, avec un autre nom, en `ContainerCreating` puis `Running`, `0/1` puis `1/1`. Pendant ce temps, l'API **répond** : le Service envoie tout au pod qui reste. Seule exception : si ton tunnel `port-forward` était branché sur le pod supprimé, il se coupe et il faut le relancer. C'est une limite du tunnel, pas du Service.

@@ guide
### 1. L'image dans le cluster

`kind load docker-image clothing-classifier:v1 --name zoomcamp`. Le nom du cluster doit être le tien, sinon kind répond qu'il ne le trouve pas.

### 2. Les deux manifestes

Télécharge-les comme dans la leçon, puis change `replicas` dans `deployment.yaml`. Applique les deux fichiers d'un coup : `kubectl apply -f .` applique tous les fichiers YAML du dossier.

### 3. Regarde les pods naître

`kubectl get pods -w` (`-w` pour *watch*) affiche chaque changement d'état. `Ctrl+C` pour arrêter. Un pod reste `0/1` quelques secondes : la sonde de disponibilité attend que le modèle soit chargé.

### 4. Le tunnel et la requête

Un terminal pour `port-forward`, un autre pour `curl`. La requête est celle de la leçon 3, sur le port `30080`.

@@ hints

@@ breakfix
Dans `deployment.yaml`, change le tag de l'image en `clothing-classifier:v9`, puis `kubectl apply -f deployment.yaml`. Regarde `kubectl get pods`, puis `kubectl describe` d'un pod qui ne démarre pas. Combien de pods servent encore l'API ? Répare ensuite.

@@ breakfix-hints
- Le statut d'un nouveau pod commence par `Err` : lis le reste du mot.
- En bas de `kubectl describe pod <nom>`, les **événements** donnent la phrase exacte.
- Compte les pods `1/1` : Kubernetes n'a rien cassé de ce qui marchait.

@@ breakfix-answer
Un nouveau pod reste en **`ErrImageNeverPull`** : l'image `v9` n'existe pas dans le cluster, et `imagePullPolicy: Never` interdit de la chercher ailleurs. Les événements de `describe` le disent : `Container image "clothing-classifier:v9" is not present with pull policy of Never`.

Mais l'API **répond toujours** : la mise à jour se fait pod par pod (*rolling update*). Kubernetes crée un pod `v9` en plus, attend qu'il soit prêt avant de retirer un ancien, et comme il ne l'est jamais, il garde **tous** les pods `v1`. C'est cette prudence qui évite les coupures. Pour réparer, remets `v1` et applique : le pod cassé disparaît. Tu verras à la leçon suivante comment annuler une mise à jour sans toucher au fichier.
