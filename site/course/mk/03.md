# Le service de prédiction dans Docker

Kubernetes lance des **images Docker**. Avant de déployer quoi que ce soit, il te faut donc une image qui marche. Le workshop de DataTalksClub utilise un petit service d'IA : une API **FastAPI** qui reçoit l'adresse d'une photo et dit quel vêtement elle montre (pantalon, robe, chaussures...).

Le modèle est déjà entraîné et converti au format **ONNX**, un format qui se lit sans PyTorch ni TensorFlow, avec la petite bibliothèque `onnxruntime`. Tu n'as pas besoin de savoir comment il a été entraîné : pour ce module, c'est une application comme une autre.

## Le dossier et le modèle

```bash
mkdir -p /workspaces/data-engineering-zoomcamp/mon-travail/kubernetes/service
cd /workspaces/data-engineering-zoomcamp/mon-travail/kubernetes/service
wget https://github.com/DataTalksClub/machine-learning-zoomcamp/releases/download/dl-models/clothing_classifier_mobilenet_v2_latest.onnx -O clothing-model.onnx
```

Le fichier fait environ 10 Mo. Ne le mets **pas** dans Git : on ne versionne pas un fichier binaire qu'on peut retélécharger.

## Le projet Python avec uv

```bash
uv init --vcs none --python 3.13
rm main.py
uv add fastapi uvicorn onnxruntime keras-image-helper numpy
```

🔑 `--vcs none` est important : sans lui, `uv init` crée un **dépôt Git dans ton dépôt Git** (un dossier `.git` caché dans `service/`), et ton fork ne voit plus ces fichiers. Le workshop ne le précise pas, car il ne travaille pas dans un fork.

`uv init` crée `pyproject.toml` et `.python-version` (avec `--vcs none`, il ne crée pas de `.gitignore` : le `.gitignore` à la racine de ton fork ignore déjà `.venv/` et `__pycache__/`) ; `uv add` installe les paquets dans `.venv/` et écrit les versions exactes dans **`uv.lock`**. Ce fichier de verrouillage rend l'image reproductible : le Dockerfile installe exactement les mêmes versions.

## Le Dockerfile

```dockerfile
FROM python:3.13.5-slim-bookworm

# uv, copié depuis son image officielle
COPY --from=ghcr.io/astral-sh/uv:latest /uv /uvx /bin/

WORKDIR /app
ENV PATH="/app/.venv/bin:$PATH"

# Les dépendances d'abord : cette couche reste en cache tant que uv.lock ne change pas
COPY pyproject.toml uv.lock .python-version ./
RUN uv sync --locked

COPY app.py clothing-model.onnx ./

EXPOSE 8080
ENTRYPOINT ["uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8080"]
```

```bash
docker build -t clothing-classifier:v1 .
docker run -it --rm -p 8080:8080 clothing-classifier:v1
```

🔑 Le **tag** `v1` compte. Avec Kubernetes, on donne un nouveau tag à chaque version (`v2`, `v3`...), jamais toujours `latest` : sinon, impossible de savoir quelle version tourne, ni de revenir en arrière.

@@ predict-answer
`top_probability` vaut environ **5,34**, et la somme des dix valeurs n'est pas 1 : certaines sont même **négatives**. Ce ne sont pas des probabilités, mais des **scores bruts** du modèle (des *logits*). Le script `test.py` du workshop les affiche pourtant comme des pourcentages, et écrit « pants (533.69%) ». Le modèle a raison sur la catégorie, mais le nom du champ ment. C'est l'exercice de cette leçon.

@@ guide
### 1. Trouve où naissent les scores

Dans `app.py`, la fonction `predict` : `session.run(...)` renvoie un tableau, et `result[0][0]` contient les dix scores. C'est juste avant `.tolist()` qu'il faut les transformer.

### 2. La fonction softmax

Elle change des scores en probabilités : on prend l'exponentielle de chaque score, puis on divise par la somme. Exemple en NumPy, sur trois scores :

~~~python
s = np.array([2.0, 1.0, -1.0])
e = np.exp(s - s.max())   # retirer le max évite les nombres trop grands, sans changer le résultat
print(e / e.sum())        # [0.705 0.259 0.035], la somme fait 1
~~~

### 3. Teste sans Docker

`uv run uvicorn app:app --host 0.0.0.0 --port 8080 --reload` : avec `--reload`, chaque sauvegarde relance le serveur. Relance la requête `curl` de la leçon.

### 4. Le `.gitignore` et l'image

Crée `service/.gitignore` avec la ligne `*.onnx` : le `.gitignore` de la racine du fork s'occupe déjà de `.venv/`. Puis le Dockerfile de la leçon, `docker build`, et `docker run`.

@@ hints
- La somme ne fait pas 1 ? Tu divises peut-être par la somme des scores, au lieu de la somme des **exponentielles**.
- `np.exp(logits - logits.max())` : `logits` doit être un tableau NumPy, donc travaille **avant** le `.tolist()`.
- `docker build` échoue sur `uv.lock` introuvable : tu as lancé `docker build` depuis un autre dossier que `service/`.

@@ solution
Dans `app.py`, la fonction `predict` devient :

~~~python
def predict(url: str):
    X = preprocessor.from_url(url)
    result = session.run([output_name], {input_name: X})
    logits = result[0][0]
    # Le modèle renvoie des scores bruts (logits) : softmax les change en probabilités qui font 1
    exp = np.exp(logits - logits.max())
    float_predictions = (exp / exp.sum()).tolist()
    predictions_dict = dict(zip(classes, float_predictions))

    top_class = max(predictions_dict, key=predictions_dict.get)
    top_probability = predictions_dict[top_class]

    return predictions_dict, top_class, top_probability
~~~

La catégorie gagnante ne change pas : softmax garde l'ordre des scores. Seules les valeurs deviennent lisibles.
