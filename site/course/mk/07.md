# Postgres dans le cluster : Secret, ConfigMap et disque

Jusqu'ici, ton service ne gardait rien : on peut tuer ses pods sans rien perdre. Une base de données, c'est l'inverse. Dans cette leçon, ajoutée pour les data engineers, tu fais tourner **Postgres** dans le cluster, avec trois objets nouveaux : un **Secret** pour le mot de passe, une **ConfigMap** pour les réglages, et un **disque** qui survit aux pods.

## 🔑 Le Secret : le mot de passe hors de Git

```bash
kubectl create secret generic taxi-db --from-literal=PGPASSWORD=choisis-un-mot-de-passe
kubectl get secret taxi-db -o yaml
```

Tu crées le Secret **par une commande**, pas par un fichier : ainsi le mot de passe n'arrive jamais dans Git. Regarde ce qu'affiche la deuxième commande : `PGPASSWORD: Y2hvaXNpcy11bi1tb3QtZGUtcGFzc2U=`. Ce n'est **pas** chiffré, c'est seulement encodé en base64 :

```bash
kubectl get secret taxi-db -o jsonpath='{.data.PGPASSWORD}' | base64 -d
```

Un Secret protège par les **droits d'accès** du cluster (qui peut lire les Secrets), pas par le chiffrement. En entreprise, il vient souvent d'un coffre-fort comme Google Secret Manager ou HashiCorp Vault.

## La ConfigMap : les réglages non secrets

Le nom de la base, l'utilisateur, l'adresse du serveur : rien de secret, donc dans un fichier versionné.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: taxi-db
data:
  PGDATABASE: taxi
  PGUSER: taxi
  PGHOST: postgres
```

Les noms `PGDATABASE`, `PGUSER`, `PGHOST` et `PGPASSWORD` ne sont pas choisis au hasard : ce sont les variables que lisent `psql` et la plupart des bibliothèques Postgres. Un programme qui les reçoit se connecte sans autre réglage.

## 🔑 Le disque : un PersistentVolumeClaim

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-data
spec:
  accessModes: ["ReadWriteOnce"]   # un seul nœud à la fois peut l'écrire
  resources:
    requests:
      storage: 1Gi
```

Un PVC est une **demande** de disque. Le cluster la satisfait avec sa *StorageClass* par défaut : dans kind, un dossier du nœud ; chez Google, un vrai disque persistant. Ton manifeste ne change pas d'un cluster à l'autre.

## Le Deployment de Postgres

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: postgres
  labels:
    app: postgres
spec:
  replicas: 1
  strategy:
    type: Recreate          # arrêter l'ancien pod AVANT de créer le nouveau : jamais deux Postgres sur le même disque
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      containers:
      - name: postgres
        image: postgres:17
        ports:
        - containerPort: 5432
        env:
        - name: POSTGRES_DB
          valueFrom:
            configMapKeyRef: {name: taxi-db, key: PGDATABASE}
        - name: POSTGRES_USER
          valueFrom:
            configMapKeyRef: {name: taxi-db, key: PGUSER}
        - name: POSTGRES_PASSWORD
          valueFrom:
            secretKeyRef: {name: taxi-db, key: PGPASSWORD}
        - name: PGDATA                              # les données dans un sous-dossier du disque
          value: /var/lib/postgresql/data/pgdata
        volumeMounts:
        - name: data
          mountPath: /var/lib/postgresql/data
        readinessProbe:
          exec:
            command: ["pg_isready", "-U", "taxi"]
          periodSeconds: 5
        resources:
          requests: {memory: "256Mi", cpu: "100m"}
          limits: {memory: "512Mi"}
      volumes:
      - name: data
        persistentVolumeClaim:
          claimName: postgres-data
```

`valueFrom` lit **une clé** d'une ConfigMap ou d'un Secret, et la donne au conteneur sous le nom que tu veux. L'image `postgres` attend `POSTGRES_PASSWORD` : on lui passe la clé `PGPASSWORD` du Secret sous ce nom.

L'image `postgres:17` est épinglée : à partir de la version 18, l'image range ses données dans un autre dossier, et ce manifeste ne marcherait plus tel quel.

Enfin un **Service** `postgres`, comme à la leçon 4, sur le port 5432. Grâce à lui, le nom `postgres` devient une adresse partout dans le cluster.

En entreprise, une base dans Kubernetes utilise plutôt un **StatefulSet**, ou n'est pas dans le cluster du tout (Cloud SQL, RDS). Le Deployment `Recreate` avec un seul pod est la forme la plus simple qui ne perd pas de données.

@@ brief
- 🔑 Un **Secret** se crée par commande, hors de Git ; il est encodé en base64, **pas** chiffré.
- Une **ConfigMap** porte les réglages non secrets ; `PGHOST`, `PGUSER`, `PGDATABASE`, `PGPASSWORD` suffisent à `psql`.
- 🔑 Un **PVC** demande un disque qui survit aux pods.
- `strategy: Recreate` : jamais deux Postgres sur le même disque.

- Tous les objets de cette leçon (ConfigMap, Secret, PVC, Deployment, Service) acceptés par un vrai serveur d'API Kubernetes 1.34.1, et l'image `postgres:17` avec ces variables testée dans Docker.

@@ predict
Tu as créé une table et trois lignes dans ce Postgres. Tu fais `kubectl delete pod` sur son pod. Le Deployment en recrée un. Tes trois lignes sont-elles encore là ? Et si le manifeste n'avait **pas** de volume ?

@@ predict-answer
Avec le PVC, **oui** : le nouveau pod remonte le même disque, et Postgres retrouve ses fichiers. Sans volume, **non** : les données étaient dans le système de fichiers du conteneur, qui disparaît avec lui. C'est la même chose qu'un `docker rm` sans volume. Tu le vérifies dans l'exercice.

@@ practice
**Objectif** : faire tourner Postgres dans le cluster, y écrire une ligne depuis un autre pod, puis prouver qu'elle survit à la mort du pod Postgres.

**Tu pars de** : ton cluster `zoomcamp`. Ton fichier : `mon-travail/kubernetes/k8s/postgres.yaml`, qui contient la ConfigMap, le PVC, le Deployment et le Service de la leçon, séparés par des lignes `---`.

@@ constraints
- `kubectl get pods -l app=postgres` montre un pod `1/1`, et `kubectl get pvc` un PVC `postgres-data` à l'état `Bound`
- Depuis un pod client (pas depuis le pod Postgres), une table `essai` avec une ligne a été créée, en se connectant à l'adresse `postgres`
- Après `kubectl delete pod` du pod Postgres, le nouveau pod affiche toujours cette ligne
- `git status` montre `postgres.yaml`, et aucun fichier du dépôt ne contient ton mot de passe

@@ guide
### 1. Le Secret, puis le fichier

D'abord `kubectl create secret ...` comme dans la leçon. Puis `postgres.yaml` : les quatre objets de la leçon, l'un après l'autre, séparés par une ligne qui contient seulement `---`. Le Service est le seul que tu écris seul : sur le modèle de celui de la leçon 4, avec le sélecteur `app: postgres` et le port 5432.

### 2. Applique et attends

`kubectl apply -f postgres.yaml`, puis `kubectl get pods -w` jusqu'à `1/1`. `kubectl get pvc` doit dire `Bound`.

### 3. Un client dans le cluster

Un pod jetable avec `psql`, qui disparaît quand tu quittes :

~~~bash
kubectl run client --rm -it --image=postgres:17 -- psql -h postgres -U taxi taxi
~~~

`psql` te demande le mot de passe du Secret. `-h postgres` passe par le **Service**. Une fois connecté : `CREATE TABLE`, puis `INSERT`, puis `\q`.

### 4. La preuve

`kubectl delete pod -l app=postgres`, attends le nouveau pod, puis relis ta table, cette fois depuis le pod Postgres lui-même : `kubectl exec -it deploy/postgres -- psql -U taxi taxi`.

@@ hints
- Le pod reste `Pending` : `kubectl describe pod` parle du PVC ? Vérifie que `claimName` est exactement le nom du PVC.
- `psql: could not translate host name "postgres"` : le Service manque, ou son nom n'est pas `postgres`. `kubectl get svc`.
- `password authentication failed` : tu as peut-être recréé le Secret **après** le premier démarrage. Postgres n'utilise `POSTGRES_PASSWORD` qu'à la création de la base, sur un disque vide.

@@ solution
Le Service, à la fin de `postgres.yaml` :

~~~yaml
---
apiVersion: v1
kind: Service
metadata:
  name: postgres
spec:
  selector:
    app: postgres
  ports:
  - port: 5432
    targetPort: 5432
~~~

~~~bash
cd /workspaces/data-engineering-zoomcamp/mon-travail/kubernetes/k8s
kubectl create secret generic taxi-db --from-literal=PGPASSWORD=choisis-un-mot-de-passe
kubectl apply -f postgres.yaml
kubectl get pvc                                   # postgres-data   Bound
kubectl get pods -l app=postgres -w               # 1/1 ; Ctrl+C

# Un client jetable, qui passe par le Service
kubectl run client --rm -it --image=postgres:17 -- psql -h postgres -U taxi taxi
#   CREATE TABLE essai (id int, note text);
#   INSERT INTO essai VALUES (1, 'je survis');
#   \q

# Le pod meurt, le disque reste
kubectl delete pod -l app=postgres
kubectl get pods -l app=postgres -w               # un nouveau pod, 1/1
kubectl exec -it deploy/postgres -- psql -U taxi taxi -c "SELECT * FROM essai"   # 1 | je survis
~~~

`kubectl exec deploy/postgres` choisit un pod du Deployment pour toi : pas besoin de recopier son nom.

@@ breakfix
Dans `postgres.yaml`, dans le `secretKeyRef` de `POSTGRES_PASSWORD`, change `key: PGPASSWORD` en `key: PASSWORD`, puis applique. Quel état prend le nouveau pod ? Les logs t'aident-ils ? Où est la cause exacte ? Répare.

@@ breakfix-hints
- Comme `strategy: Recreate` arrête l'ancien pod d'abord, cette fois ta base est vraiment **arrêtée** : c'est le prix d'un seul pod.
- `kubectl logs` ne peut rien montrer : le conteneur n'a jamais démarré.
- Les événements de `describe` nomment la clé et le Secret.

@@ breakfix-answer
Le pod reste en **`CreateContainerConfigError`**. Les logs sont vides : Kubernetes refuse de **créer** le conteneur, parce qu'il ne peut pas lui donner toutes ses variables. Les événements de `describe` disent la cause : `couldn't find key PASSWORD in Secret default/taxi-db`. Remets `key: PGPASSWORD` et applique.

À retenir : une faute dans une ConfigMap ou un Secret ne fait pas planter ton programme, elle l'**empêche de démarrer**. Et comme ce Deployment n'a qu'un pod en `Recreate`, la base est indisponible le temps de réparer. C'est pour ça que les bases de production vivent souvent hors du cluster.
