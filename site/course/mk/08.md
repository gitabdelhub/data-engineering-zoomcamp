# Jobs et CronJobs : une ingestion planifiée

Un service tourne en permanence. Une **ingestion**, elle, démarre, charge des données, et s'arrête. Pour ça, Kubernetes a deux objets, ajoutés ici pour les data engineers :

- un **Job** lance un ou plusieurs pods jusqu'à ce qu'ils **réussissent**, et réessaie s'ils échouent ;
- un **CronJob** crée un Job **à heure fixe**, comme `cron` sous Linux.

C'est la façon la plus simple de planifier un traitement dans un cluster, sans orchestrateur. Dès qu'il y a des dépendances entre étapes, on passe à un orchestrateur comme Airflow, qui lui-même lance souvent ses tâches comme des pods.

## Le programme d'ingestion

Il charge la table des 265 zones de taxi de New York dans ton Postgres. Il lit sa connexion dans les variables `PG...` de la leçon 7.

`mon-travail/kubernetes/ingest/ingest.py` :

```python
"""Charge la table des zones de taxi dans Postgres. Relançable sans doublons."""
import os
import urllib.request

import psycopg

URL = os.environ.get(
    "ZONES_URL",
    "https://github.com/DataTalksClub/nyc-tlc-data/releases/download/misc/taxi_zone_lookup.csv",
)

# La connexion vient des variables d'environnement (ConfigMap et Secret du cluster)
conninfo = (
    f"host={os.environ['PGHOST']} dbname={os.environ['PGDATABASE']} "
    f"user={os.environ['PGUSER']} password={os.environ['PGPASSWORD']}"
)

print(f"Téléchargement de {URL}")
with urllib.request.urlopen(URL) as r:
    csv = r.read()

# Une seule transaction : si le COPY échoue, l'ancienne table reste intacte
with psycopg.connect(conninfo) as conn:
    conn.execute("""
        CREATE TABLE IF NOT EXISTS zones (
            location_id  integer PRIMARY KEY,
            borough      text,
            zone         text,
            service_zone text
        )""")
    conn.execute("TRUNCATE zones")
    with conn.cursor().copy("COPY zones FROM STDIN WITH (FORMAT csv, HEADER true)") as copy:
        copy.write(csv)
    n = conn.execute("SELECT count(*) FROM zones").fetchone()[0]

print(f"Terminé : {n} zones dans la table")
```

🔑 Le programme est **idempotent** : le relancer donne le même résultat, jamais des doublons. `TRUNCATE` puis `COPY` dans une seule transaction : si le chargement échoue au milieu, Postgres annule tout et l'ancienne table reste intacte. Un Job peut être relancé par Kubernetes à tout moment ; un programme qui n'est pas idempotent finit par doubler tes données.

## 🔑 Le Job

`mon-travail/kubernetes/k8s/job-zones.yaml` :

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: zones
spec:
  backoffLimit: 2                 # deux nouvelles tentatives au plus
  ttlSecondsAfterFinished: 3600   # le Job fini est effacé au bout d'une heure
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: ingest
        image: ingest:v1
        imagePullPolicy: Never
        envFrom:
        - configMapRef:
            name: taxi-db
        env:
        - name: PGPASSWORD
          valueFrom:
            secretKeyRef: {name: taxi-db, key: PGPASSWORD}
        resources:
          requests: {memory: "64Mi", cpu: "100m"}
          limits: {memory: "256Mi"}
```

- `envFrom` donne **toutes** les clés de la ConfigMap comme variables, d'un coup. Le mot de passe, lui, vient du Secret, clé par clé.
- `restartPolicy: Never` : un pod qui échoue n'est pas relancé sur place ; c'est le Job qui crée un **nouveau** pod, jusqu'à `backoffLimit` fois.
- `ttlSecondsAfterFinished` fait le ménage : sans lui, les Jobs finis s'accumulent.

```bash
kubectl apply -f job-zones.yaml
kubectl get jobs -w
kubectl logs job/zones
```

Un Job déjà fini ne se relance pas avec `apply` : son modèle de pod ne peut plus changer. Pour le relancer, on le supprime puis on le recrée (`kubectl delete job zones`, puis `apply`).

## Le CronJob

`mon-travail/kubernetes/k8s/cronjob-zones.yaml` :

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: zones-nuit
spec:
  schedule: "0 3 * * *"           # tous les jours à 3 h (heure UTC du cluster)
  concurrencyPolicy: Forbid       # pas de nouveau run tant que le précédent tourne
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 3
  jobTemplate:
    spec:
      backoffLimit: 2
      template:
        spec:
          restartPolicy: Never
          containers:
          - name: ingest
            image: ingest:v1
            imagePullPolicy: Never
            envFrom:
            - configMapRef:
                name: taxi-db
            env:
            - name: PGPASSWORD
              valueFrom:
                secretKeyRef: {name: taxi-db, key: PGPASSWORD}
            resources:
              requests: {memory: "64Mi", cpu: "100m"}
              limits: {memory: "256Mi"}
```

Le `jobTemplate` est **exactement** le `spec` d'un Job. Le rythme s'écrit comme dans `cron` : minute, heure, jour du mois, mois, jour de la semaine. `0 3 * * *` veut dire « à 3 h 00, tous les jours ». Le site [crontab.guru](https://crontab.guru/) traduit n'importe quelle expression en phrase.

🔑 `concurrencyPolicy: Forbid` : si le run d'hier tourne encore, celui d'aujourd'hui est sauté plutôt que lancé en parallèle. Deux ingestions en même temps sur la même table, c'est la recette des données corrompues.

Pour tester sans attendre 3 h du matin, crée un Job à partir du CronJob :

```bash
kubectl apply -f cronjob-zones.yaml
kubectl create job --from=cronjob/zones-nuit zones-test
kubectl get jobs
```

@@ brief
- 🔑 Un **Job** tourne jusqu'à réussir, avec `backoffLimit` nouvelles tentatives ; un **CronJob** crée un Job à heure fixe.
- 🔑 Un programme lancé par un Job doit être **idempotent** : Kubernetes peut le relancer.
- `concurrencyPolicy: Forbid` empêche deux runs en même temps.
- `kubectl create job --from=cronjob/...` lance un run tout de suite, pour tester.

@@ predict
Le Job a `backoffLimit: 2` et Postgres est éteint. Combien de pods le Job crée-t-il avant d'abandonner, et quel est son état final ?

@@ predict-answer
**Trois pods** : le premier essai, puis deux nouvelles tentatives (`backoffLimit: 2`). Chacun finit en `Error`. Kubernetes attend de plus en plus longtemps entre deux essais (10 s, 20 s, 40 s...). Ensuite le Job passe à `Failed` (dans `kubectl get jobs`, la colonne `STATUS`), avec la raison `BackoffLimitExceeded` dans `describe`. Les pods échoués restent là exprès : leurs logs disent pourquoi. Tu le provoques dans « casser et réparer ».

@@ breakfix
Lance un Job qui vise une mauvaise adresse, sans toucher à tes fichiers : `cp job-zones.yaml /tmp/casse.yaml`. Dans la copie, change le nom en `zones-casse`, et ajoute dans `env`, sous `PGPASSWORD`, une variable `PGHOST` qui vaut `postgresql` (avec un `l` de trop). Puis `kubectl apply -f /tmp/casse.yaml`, et observe pendant deux minutes. Combien de pods ? Quel état final ? Quelle phrase des logs donne la cause ?

@@ breakfix-hints
- `kubectl get pods -l job-name=zones-casse -w` : chaque pod d'un Job porte l'étiquette `job-name`.
- Une variable écrite dans `env` gagne toujours sur la même variable venue d'`envFrom` : c'est ta valeur fausse qui est utilisée.
- `kubectl logs` sur un des pods en `Error` : la dernière ligne parle du nom d'hôte.

@@ breakfix-answer
Le Job crée **trois pods** (un essai et deux nouvelles tentatives), espacés de plus en plus, qui finissent tous en `Error`. Puis il passe à `Failed`, et `describe job zones-casse` dit `BackoffLimitExceeded`. Les logs d'un pod finissent par `psycopg.OperationalError: [Errno -2] Name or service not known` : le nom `postgresql` ne correspond à aucun Service. Remarque que le téléchargement, lui, a réussi : l'erreur arrive à la connexion.

Le Job n'a pas abandonné dès la première erreur : c'est utile quand la panne est **passagère** (une base qui redémarre), inutile quand c'est une faute de configuration. Fais le ménage avec `kubectl delete job zones-casse` : supprimer un Job supprime aussi ses pods.
