# Helm : empaqueter tes manifestes

Tu as maintenant six fichiers YAML. Imagine que tu doives les déployer en **dev** et en **prod**, avec un disque plus grand et une ingestion plus tôt en prod : tu copierais tout, et tu oublierais de changer une ligne. **Helm** règle ça : c'est le gestionnaire de paquets de Kubernetes.

- Un **chart** est un dossier de manifestes avec des **trous** (des *templates*), et un fichier `values.yaml` qui remplit les trous.
- Une **release** est un chart installé dans un cluster, sous un nom. Helm garde l'historique de chaque release, et sait revenir en arrière.

Tu t'en serviras de deux façons : pour **installer** des logiciels tout faits (le chart officiel d'Airflow, de Spark, de Kafka...), et pour **empaqueter** tes propres applications.

## Installer Helm

```bash
cd ~/bin
curl -L https://get.helm.sh/helm-v3.19.0-linux-amd64.tar.gz | tar xz
mv linux-amd64/helm . && rm -r linux-amd64
helm version
```

## 🔑 Un chart, c'est trois choses

```
mon-travail/kubernetes/helm/taxi/
├── Chart.yaml        # le nom et la version du chart
├── values.yaml       # les valeurs par défaut
└── templates/        # les manifestes, avec des {{ trous }}
```

`Chart.yaml` :

```yaml
apiVersion: v2
name: taxi
description: Postgres et l'ingestion nocturne des zones de taxi
version: 0.1.0
```

`values.yaml` :

```yaml
# Les réglages qui changent d'un environnement à l'autre
base:
  nom: taxi
  disque: 1Gi
ingestion:
  image: ingest:v1
  rythme: "0 3 * * *"
  memoire: 256Mi
```

Dans les templates, `{{ .Values.ingestion.rythme }}` est remplacé par la valeur de `values.yaml`, et `{{ .Release.Name }}` par le nom de la release. Exemple, `templates/cronjob.yaml` :

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: {{ .Release.Name }}-zones
spec:
  schedule: {{ .Values.ingestion.rythme | quote }}
  concurrencyPolicy: Forbid
  jobTemplate:
    spec:
      backoffLimit: 2
      template:
        spec:
          restartPolicy: Never
          containers:
          - name: ingest
            image: {{ .Values.ingestion.image }}
            imagePullPolicy: Never
            envFrom:
            - configMapRef:
                name: {{ .Release.Name }}-db
            env:
            - name: PGPASSWORD
              valueFrom:
                secretKeyRef: {name: {{ .Release.Name }}-db, key: PGPASSWORD}
            resources:
              limits: {memory: {{ .Values.ingestion.memoire }}}
```

Préfixer chaque nom par `{{ .Release.Name }}` permet d'installer **deux fois** le même chart dans le même cluster (`dev` et `essai`, par exemple) sans conflit. `| quote` met la valeur entre guillemets : sans eux, YAML lirait mal `0 3 * * *`.

## Les commandes

| Commande | Ce qu'elle fait |
| --- | --- |
| `helm lint taxi` | Vérifie le chart |
| `helm template dev taxi` | Affiche les manifestes produits, **sans rien installer** : le meilleur moyen de comprendre |
| `helm install dev taxi` | Installe la release `dev` |
| `helm upgrade dev taxi --set ingestion.rythme="0 5 * * *"` | Met à jour, en changeant une valeur |
| `helm install prod taxi -f prod.yaml` | Installe avec un fichier de valeurs en plus |
| `helm list`, `helm history dev` | Les releases, et l'historique d'une release |
| `helm rollback dev 1` | Revient à la révision 1 |
| `helm uninstall dev` | Supprime tout ce que la release a créé |

Le Secret reste **hors** du chart : tu le crées toujours par commande, ici sous le nom `dev-db` pour la release `dev`.

@@ brief
- 🔑 Un **chart** = des templates + `values.yaml` ; une **release** = un chart installé sous un nom, avec un historique.
- `helm template` montre ce qui sera créé, sans rien installer.
- 🔑 `helm upgrade` repart des valeurs par défaut : redonne tes `--set`, ou garde-les dans un fichier `-f`.

@@ verified
- Le chart de cette leçon testé avec Helm 3.19 sur un vrai serveur d'API Kubernetes 1.34.1 : `lint`, `template`, `install`, `upgrade`, `history`, `rollback` et `uninstall`. Le piège de la prédiction a été vérifié : après `upgrade` sans le `--set` d'origine, le rythme était revenu à `0 3 * * *`.
- **Pas testé ici** : le téléchargement de Helm depuis `get.helm.sh` (bloqué sur ma machine) et les pods dans kind.

@@ predict
Tu installes avec `helm install dev taxi --set ingestion.rythme="0 5 * * *"`. Une semaine plus tard, tu changes seulement la mémoire : `helm upgrade dev taxi --set ingestion.memoire=384Mi`. Quel est le rythme du CronJob après l'upgrade ?

@@ predict-answer
**`0 3 * * *`**, la valeur par défaut : `helm upgrade` recalcule tout depuis `values.yaml` plus les `--set` de **cette** commande. Ton `--set` de l'installation est oublié. C'est un piège fréquent, et c'est pour ça qu'en entreprise on met les valeurs de chaque environnement dans un fichier (`dev.yaml`, `prod.yaml`), versionné dans Git, et qu'on passe toujours `-f`. Tu le vois dans l'exercice.

@@ practice
**Objectif** : transformer ton Postgres et ton CronJob des leçons 7 et 8 en un chart `taxi`, puis l'installer deux fois, en `dev` et en `prod`, avec des réglages différents.

**Tu pars de** : ton image `ingest:v1` dans le cluster, et tes manifestes `postgres.yaml` et `cronjob-zones.yaml`. Ton chart : `mon-travail/kubernetes/helm/taxi/`. Pour libérer la mémoire, supprime d'abord ce que tu as créé à la main : `kubectl delete -f postgres.yaml -f cronjob-zones.yaml -f job-zones.yaml` depuis `k8s/`.

@@ constraints
- `helm lint taxi` ne signale aucune erreur
- `helm list` montre deux releases, `dev` et `prod`, à l'état `deployed`
- `kubectl get cronjob` montre `dev-zones` à `0 3 * * *` et `prod-zones` à `0 1 * * *`, et le PVC `prod-postgres` demande `2Gi`
- Les réglages de prod sont dans un fichier `prod.yaml` à côté du chart, pas seulement dans une commande `--set`
- Après `kubectl create job --from=cronjob/dev-zones essai`, la table `zones` de la base `dev` a 265 lignes

@@ hints
- Commence par `helm template dev taxi` et compare la sortie avec tes fichiers de la leçon 7 : tant que ça ne ressemble pas, n'installe rien.
- `CreateContainerConfigError` sur `prod-postgres` : le Secret `prod-db` manque. Chaque release a le sien.
- `prod.yaml` ne contient que ce qui change : `base.disque` et `ingestion.rythme`.
- `kubectl exec deploy/dev-postgres -- psql -U taxi taxi -c "SELECT count(*) FROM zones"`.

@@ solution
Les fichiers du chart sont ceux de la leçon, plus `templates/configmap.yaml` et `templates/postgres.yaml` :

~~~yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: {{ .Release.Name }}-db
data:
  PGDATABASE: {{ .Values.base.nom }}
  PGUSER: {{ .Values.base.nom }}
  PGHOST: {{ .Release.Name }}-postgres
~~~

~~~yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: {{ .Release.Name }}-postgres
spec:
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: {{ .Values.base.disque }}
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}-postgres
spec:
  replicas: 1
  strategy:
    type: Recreate
  selector:
    matchLabels:
      app: {{ .Release.Name }}-postgres
  template:
    metadata:
      labels:
        app: {{ .Release.Name }}-postgres
    spec:
      containers:
      - name: postgres
        image: postgres:17
        env:
        - name: POSTGRES_DB
          value: {{ .Values.base.nom }}
        - name: POSTGRES_USER
          value: {{ .Values.base.nom }}
        - name: POSTGRES_PASSWORD
          valueFrom:
            secretKeyRef: {name: {{ .Release.Name }}-db, key: PGPASSWORD}
        - name: PGDATA
          value: /var/lib/postgresql/data/pgdata
        volumeMounts:
        - name: data
          mountPath: /var/lib/postgresql/data
        readinessProbe:
          exec:
            command: ["pg_isready", "-U", "{{ .Values.base.nom }}"]
          periodSeconds: 5
        resources:
          requests: {memory: "256Mi", cpu: "100m"}
          limits: {memory: "512Mi"}
      volumes:
      - name: data
        persistentVolumeClaim:
          claimName: {{ .Release.Name }}-postgres
---
apiVersion: v1
kind: Service
metadata:
  name: {{ .Release.Name }}-postgres
spec:
  selector:
    app: {{ .Release.Name }}-postgres
  ports:
  - port: 5432
~~~

`mon-travail/kubernetes/helm/prod.yaml` :

~~~yaml
base:
  disque: 2Gi
ingestion:
  rythme: "0 1 * * *"
~~~

~~~bash
cd /workspaces/data-engineering-zoomcamp/mon-travail/kubernetes/helm
helm lint taxi
helm template dev taxi | less                     # relis avant d'installer ; q pour quitter

kubectl create secret generic dev-db --from-literal=PGPASSWORD=mot-de-passe-dev
kubectl create secret generic prod-db --from-literal=PGPASSWORD=mot-de-passe-prod
helm install dev taxi
helm install prod taxi -f prod.yaml
helm list                                         # dev et prod, deployed
kubectl get cronjob                               # dev-zones 0 3 * * *, prod-zones 0 1 * * *
kubectl get pvc prod-postgres                     # 2Gi

kubectl create job --from=cronjob/dev-zones essai
kubectl get jobs -w                               # essai Complete ; Ctrl+C
kubectl exec deploy/dev-postgres -- psql -U taxi taxi -c "SELECT count(*) FROM zones"   # 265
~~~

Pour finir ta séance : `helm uninstall dev prod`. Les PVC sont supprimés avec la release, donc les données aussi.
