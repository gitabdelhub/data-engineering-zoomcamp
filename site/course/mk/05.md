# Mettre à jour, revenir en arrière, déboguer

Une application change tout le temps. Ici, tu apprends à passer à une nouvelle version sans coupure, à revenir en arrière en une commande quand elle est cassée, et surtout à **trouver pourquoi un pod ne marche pas**. C'est la compétence Kubernetes qu'on attend vraiment d'un junior.

## 🔑 Une mise à jour, c'est un nouveau tag

```bash
cd /workspaces/data-engineering-zoomcamp/mon-travail/kubernetes/service
docker build -t clothing-classifier:v2 .
kind load docker-image clothing-classifier:v2 --name zoomcamp
kubectl set image deployment/clothing-classifier clothing-classifier=clothing-classifier:v2
kubectl rollout status deployment/clothing-classifier
```

Dans `set image`, le premier `clothing-classifier` est le nom du Deployment, le second celui du **conteneur** dans le manifeste. `rollout status` attend la fin de la mise à jour et te rend la main.

`set image` est pratique pour essayer, mais ton fichier dit encore `v1`. La bonne habitude : **changer le tag dans `deployment.yaml` puis `kubectl apply`**. Ce qui tourne correspond alors à ce qui est dans Git.

## Revenir en arrière

```bash
kubectl rollout history deployment/clothing-classifier
kubectl rollout undo deployment/clothing-classifier
```

Kubernetes garde les anciennes versions du modèle de pod (les *ReplicaSets*). `undo` repasse à la précédente, avec la même prudence pod par pod.

Pour relancer tous les pods sans rien changer (par exemple après un nouveau `kind load` du même tag) :

```bash
kubectl rollout restart deployment/clothing-classifier
```

## 🔑 La méthode de débogage

Quand un pod ne marche pas, suis toujours le même ordre :

| Étape | Commande | Ce que tu cherches |
| --- | --- | --- |
| 1. L'état | `kubectl get pods` | La colonne `STATUS` et le nombre de `RESTARTS` |
| 2. Les événements | `kubectl describe pod <nom>` | La section `Events` tout en bas : image introuvable, sonde qui échoue, pas assez de mémoire... |
| 3. Les logs | `kubectl logs <nom>` | L'erreur de **ton** programme |
| 4. Les logs d'avant | `kubectl logs <nom> --previous` | Ce qu'a écrit le conteneur **qui a planté**, quand il a déjà été relancé |
| 5. L'intérieur | `kubectl exec -it <nom> -- bash` | Un terminal dans le conteneur, pour vérifier un fichier ou une variable |

Les états que tu verras le plus souvent :

| État | Ce qu'il veut dire | Où regarder |
| --- | --- | --- |
| `Pending` | Aucun nœud ne peut accueillir le pod (trop de ressources demandées, disque introuvable) | `describe` |
| `ErrImagePull`, `ImagePullBackOff`, `ErrImageNeverPull` | L'image est introuvable : nom, tag, registre | `describe` |
| `CreateContainerConfigError` | Une ConfigMap ou un Secret manque, ou une de leurs clés | `describe` |
| `CrashLoopBackOff` | Le conteneur démarre puis plante, encore et encore. Kubernetes attend de plus en plus longtemps entre deux essais | `logs --previous` |
| `OOMKilled` | Le conteneur a dépassé sa limite de mémoire | `describe`, champ `Last State` |

Et pour tout le cluster, les derniers événements par ordre chronologique :

```bash
kubectl get events --sort-by=.lastTimestamp
```

@@ predict
Tu passes à une image `v2` qui plante au démarrage. Le Deployment a 3 copies. Combien de pods `v1` restent en vie, et l'API répond-elle encore ?

@@ predict-answer
Les **trois** pods `v1` restent en vie et l'API répond. Comme au « casser et réparer » de la leçon 4, Kubernetes n'arrête un ancien pod que quand un nouveau est **prêt**. Le pod `v2` part en `CrashLoopBackOff`, `rollout status` ne finit jamais, et c'est le signal pour faire `kubectl rollout undo`. Cette protection ne marche que si tes **sondes** sont bien réglées : sans sonde de disponibilité, Kubernetes croirait le pod prêt dès son lancement.

@@ practice
**Objectif** : publier une version `v2` du service qui annonce sa version, la déployer sans coupure, puis revenir à `v1` et revenir encore à `v2`.

**Tu pars de** : ton Deployment de 3 copies en `v1` (leçon 4) et ton dossier `mon-travail/kubernetes/service/`.

@@ constraints
- `curl http://localhost:30080/` (par le tunnel) renvoie un message qui contient `"version": "v2"`
- `kubectl rollout history deployment/clothing-classifier` montre au moins trois révisions
- `deployment.yaml` dit `clothing-classifier:v2` à la fin, et `kubectl get deployment clothing-classifier -o jsonpath='{.spec.template.spec.containers[0].image}'` affiche la même chose
- Pendant le passage à `v2`, une boucle de `curl` sur `/health` ne montre aucune erreur

@@ guide
### 1. La version dans l'API

Dans `app.py`, la route `/` renvoie un dictionnaire. Ajoute-lui une clé `version`. Teste d'abord avec `uv run uvicorn ... --reload`, comme à la leçon 3.

### 2. L'image et le cluster

`docker build` avec le tag `v2`, puis `kind load` avec ce tag.

### 3. Une boucle qui surveille

Dans un terminal, le tunnel. Dans un deuxième, une boucle qui interroge l'API chaque seconde :

~~~bash
while true; do curl -s -o /dev/null -w "%{http_code}\n" http://localhost:30080/health; sleep 1; done
~~~

`-w "%{http_code}"` affiche seulement le code HTTP : `200` si tout va bien.

### 4. La mise à jour, puis les retours

Dans un troisième terminal : change le tag dans `deployment.yaml`, `kubectl apply`, `rollout status`. Puis `rollout undo`, vérifie `/`, et refais `apply` pour revenir à `v2`.

@@ hints
- La boucle affiche `000` : c'est le **tunnel** qui s'est coupé (son pod a été remplacé), pas l'API. Relance `port-forward`. Pour un vrai test sans tunnel, lance la boucle depuis un pod du cluster : `kubectl run test --rm -it --image=busybox:1.37 -- sh`, puis `wget -qO- http://clothing-classifier:8080/health`.
- `rollout history` ne montre que deux révisions : `apply` d'un fichier inchangé ne crée pas de révision. Seul un changement du modèle de pod en crée une.

@@ solution
Dans `app.py` :

~~~python
@app.get("/")
def root():
    return {"message": "Clothing Classification Service", "version": "v2"}
~~~

~~~bash
cd /workspaces/data-engineering-zoomcamp/mon-travail/kubernetes/service
docker build -t clothing-classifier:v2 .
kind load docker-image clothing-classifier:v2 --name zoomcamp

cd ../k8s
sed -i 's/clothing-classifier:v1/clothing-classifier:v2/' deployment.yaml
kubectl apply -f deployment.yaml
kubectl rollout status deployment/clothing-classifier   # successfully rolled out
curl http://localhost:30080/                            # "version":"v2" (relance le tunnel s'il s'est coupé)

kubectl rollout undo deployment/clothing-classifier     # retour à v1 : la route / n'a plus de version
kubectl apply -f deployment.yaml                        # de nouveau v2, comme dans Git
kubectl rollout history deployment/clothing-classifier  # trois révisions ou plus
~~~

Remarque : après `undo`, le cluster ne correspond plus à ton fichier. C'est pour ça qu'en entreprise, un retour en arrière se fait le plus souvent **dans Git** (on annule le commit, puis on applique).

@@ breakfix
Dans `deployment.yaml`, sous `image:` du conteneur, ajoute une ligne `command: ["uvicorn", "appli:app", "--host", "0.0.0.0", "--port", "8080"]` (avec la même indentation qu'`image`), puis applique. Suis la méthode de débogage : quel état, quels événements, quels logs ? Retrouve la phrase qui dit la cause exacte, puis répare.

@@ breakfix-hints
- `kubectl get pods` : regarde la colonne `RESTARTS` grimper.
- `kubectl logs <nom>` peut être vide si le conteneur vient de redémarrer : essaie `--previous`.
- Compare `appli:app` avec le nom de ton fichier Python.

@@ breakfix-answer
Le nouveau pod passe en **`CrashLoopBackOff`**, avec des `RESTARTS` qui augmentent. `describe` montre seulement `Back-off restarting failed container` : les événements disent **que** ça plante, pas **pourquoi**. Ce sont les logs qui le disent : `kubectl logs <nom> --previous` affiche l'erreur d'uvicorn, `Error loading ASGI app. Could not import module "appli"`. Le fichier s'appelle `app.py`, donc le module est `app`.

`command` remplace l'`ENTRYPOINT` de l'image : une faute ici casse un conteneur qui marchait très bien dans Docker. Supprime la ligne et applique, ou fais `kubectl rollout undo`. Les anciens pods n'ont jamais arrêté de répondre.
