# Recharger sans doublons : replace, merge et incrémental

À la leçon 1, ton deuxième lancement a tout mis en double, et `replace` a réglé le problème en rechargeant **tout**. Avec 500 livres, c'est sans importance. Avec 10 millions de lignes, ou une API qui limite le nombre de requêtes, tu veux charger **seulement ce qui a changé**. dlt a deux outils pour ça, qui se combinent.

## Les trois façons d'écrire : `write_disposition`

| Valeur | Ce que fait le chargement | Quand l'utiliser |
| --- | --- | --- |
| `append` (par défaut) | **ajoute** les lignes | des événements qui ne changent jamais : des clics, des mesures |
| `replace` | **remplace** toute la table | une petite table qu'on recharge en entier |
| `merge` | **met à jour** les lignes qui existent, **ajoute** les autres | des enregistrements qui changent : des clients, des commandes |

Pour `merge`, dlt doit savoir quelle colonne identifie un enregistrement : la **clé primaire**, `primary_key`. Si une ligne arrive avec un `id` déjà présent, elle **remplace** l'ancienne. Sinon, elle s'ajoute.

## Le chargement incrémental

`merge` évite les doublons, mais dlt lit quand même toutes les données. Le **chargement incrémental** ne garde que les lignes **plus récentes** que le dernier chargement. Il a besoin d'une colonne qui avance avec le temps, le **curseur**, et dlt retient sa plus grande valeur d'un lancement à l'autre, dans son **état** (la table `_dlt_pipeline_state`).

Un exemple : les relevés de stations de vélos, que tu reçois toujours en entier.

```python
import dlt

@dlt.resource(primary_key="id", write_disposition="merge")
def releves(maj=dlt.sources.incremental("maj", initial_value="2026-01-01T00:00:00")):
    print(f"Dernière valeur vue : {maj.last_value}")
    yield [
        {"id": 1, "nom": "Bastille", "velos": 12, "maj": "2026-03-01T08:00:00"},
        {"id": 2, "nom": "Nation", "velos": 4, "maj": "2026-03-01T08:00:00"},
    ]

pipeline = dlt.pipeline(pipeline_name="velos", destination="duckdb", dataset_name="stations")
pipeline.run(releves())
print(pipeline.last_trace.last_normalize_info.row_counts)
```

- `dlt.sources.incremental("maj", ...)` : le curseur est la colonne `maj`. `initial_value` sert seulement au tout premier lancement.
- Au premier lancement, tout est chargé. Au deuxième, sans changement, **rien** : dlt filtre les lignes déjà vues.
- `pipeline.last_trace.last_normalize_info.row_counts` donne le nombre de lignes du dernier lancement, table par table.

Avec une vraie API, c'est encore mieux : la valeur du curseur part **dans la requête** (par exemple `?depuis=2026-03-01T08:00:00`), et l'API ne renvoie que les nouveautés. La source REST API le fait avec `"type": "incremental"` dans `params`.

@@ brief
- `write_disposition` : `append` ajoute, `replace` remplace tout, `merge` met à jour grâce à la **clé primaire**.
- L'**incrémental** ne charge que ce qui est plus récent que le dernier lancement. dlt retient la valeur du **curseur** dans son état.
- Le curseur doit changer **chaque fois qu'un enregistrement change** : une date de modification, pas une date de création.
- `merge` + incrémental : peu de données lues, aucun doublon, et les corrections arrivent.

@@ practice
Écris `depenses.py`, qui charge un carnet de dépenses depuis un fichier JSON, en ne chargeant à chaque lancement que les dépenses **nouvelles ou corrigées**.

@@ constraints
- Un fichier `depenses.json` avec au moins 5 dépenses, chacune avec un `id`, une `date`, un `libelle`, un `montant` et un `modifie_le` (date et heure de la dernière modification)
- Une ressource `depenses` en `merge` sur `id`, avec un curseur incrémental sur `modifie_le`
- Le pipeline s'appelle `mes_depenses`, le dataset `budget`, et le script affiche combien de lignes il vient de charger, puis toute la table
- Trois lancements : le premier charge tout ; le deuxième, sans changement, charge **0** ligne ; avant le troisième, tu corriges le montant d'une ancienne dépense et tu en ajoutes une, et il charge **2** lignes
- Après le troisième, la table a une ligne de plus qu'au départ, et la dépense corrigée a son **nouveau** montant

@@ guide
### 1. Le fichier de données

`code depenses.json`, une liste JSON de 5 dépenses. Les dates en texte, au format ISO : `"2026-03-02"` pour la date, `"2026-03-02T09:00:00"` pour `modifie_le`. Au départ, `modifie_le` est le jour de la dépense.

### 2. La ressource

Reprends l'exemple des vélos, avec trois changements :

- le nom du curseur : `modifie_le` ;
- au lieu d'une liste écrite dans le code, la fonction lit le fichier : `with open("depenses.json") as f:`, puis `yield json.load(f)` (pense à `import json`) ;
- un `initial_value` plus ancien que toutes tes dépenses.

### 3. Le pipeline et l'affichage

`dlt.pipeline(...)` avec les noms de la consigne. Après `run`, affiche le nombre de lignes chargées pour la table `depenses` (le dictionnaire de l'exemple, avec `.get("depenses", 0)` : la clé est absente quand rien n'est chargé), puis la table triée par `id`.

### 4. Les trois lancements

~~~bash
uv run python depenses.py      # 1 : tout
uv run python depenses.py      # 2 : rien
~~~

Avant le troisième, dans `depenses.json` : change le `montant` d'une des premières dépenses **et** son `modifie_le` (mets une heure plus récente que toutes les autres), puis ajoute une sixième dépense. Puis :

~~~bash
uv run python depenses.py      # 3 : la correction et la nouvelle
~~~

@@ hints
- `dlt.sources.incremental("modifie_le", initial_value="2026-01-01")` : le texte ISO se compare correctement, car `"2026-03-07T10:00:00"` est « plus grand » que `"2026-03-06"`.
- Si le deuxième lancement recharge tout, ton curseur n'est pas un argument **par défaut** de la fonction : il doit être écrit dans `def depenses(curseur=dlt.sources.incremental(...))`.
- Si la correction n'arrive pas au troisième lancement, as-tu bien changé `modifie_le` en plus du montant ?
- Pour recommencer depuis le début : supprime `mes_depenses.duckdb` et le dossier `~/.dlt/pipelines/mes_depenses`.

@@ solution
`depenses.py` :

~~~python
import json

import dlt


# merge sur id : une dépense déjà connue est remplacée, une nouvelle est ajoutée
@dlt.resource(primary_key="id", write_disposition="merge")
def depenses(curseur=dlt.sources.incremental("modifie_le", initial_value="2026-01-01")):
    # Le fichier contient toujours tout : dlt ne garde que ce qui est plus récent que le dernier chargement
    print(f"Déjà chargé jusqu'à : {curseur.last_value}")
    with open("depenses.json") as f:
        yield json.load(f)


pipeline = dlt.pipeline(pipeline_name="mes_depenses", destination="duckdb", dataset_name="budget")
pipeline.run(depenses())
print("Lignes chargées :", pipeline.last_trace.last_normalize_info.row_counts.get("depenses", 0))
print(pipeline.dataset()("SELECT id, libelle, montant FROM depenses ORDER BY id").fetchall())
~~~

Avec 5 dépenses, puis le montant de la dépense 2 corrigé (de 32 à 23) et une sixième ajoutée :

@@ breakfix-answer
La nouvelle dépense arrive, mais la **correction est perdue** : la dépense 2 garde son montant de 32. Le curseur `date` est la date à laquelle la dépense a eu lieu, et elle ne change jamais. La dépense 2 date du 3 mars, avant le dernier curseur retenu (le 6 mars) : dlt la considère comme déjà chargée et l'écarte, sans aucun message.

Le curseur doit être une colonne qui change **à chaque modification** de l'enregistrement : `modifie_le`, `updated_at`, `last_modified`. Remets `modifie_le`, supprime la base et l'état, et relance depuis le début. Ce bug est silencieux et fréquent dans les vrais pipelines : les nouveautés arrivent, les corrections jamais.
