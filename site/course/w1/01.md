# Ce que fait dlt

Jusqu'ici, pour charger des données, tu écrivais tout toi-même : télécharger le fichier, le lire avec pandas, choisir les types, créer la table, insérer les lignes. Au module 2, ton DAG le faisait étape par étape. **dlt** (*data load tool*) est une bibliothèque Python qui fait cette partie répétitive pour toi : tu lui donnes des données, il crée les tables et les remplit.

## Trois étapes

Chaque fois que tu lances un pipeline dlt, il fait toujours la même chose, dans cet ordre :

1. **Extraire** (*extract*) : il lit les données que tu lui donnes, une liste Python, une API ou un fichier.
2. **Normaliser** (*normalize*) : il devine le **schéma**, c'est-à-dire les colonnes et leurs types, et il aplatit ce qui est imbriqué.
3. **Charger** (*load*) : il crée les tables dans la **destination** et y écrit les lignes. Ici, la destination est **DuckDB**, une base de données qui tient dans un seul fichier, sans serveur.

## Trois mots à connaître

- Une **ressource** (*resource*) est une fonction Python qui **donne** des données avec `yield`. Chaque ressource devient une table.
- Un **pipeline** relie tes ressources à une destination. Il a un nom, et il range les tables dans un **dataset** (un schéma, dans DuckDB).
- `pipeline.run(...)` lance les trois étapes d'un coup.

Un exemple, avec des films :

```python
import dlt

films = [
    {"titre": "Amélie", "annee": 2001, "acteurs": ["Audrey Tautou", "Mathieu Kassovitz"]},
    {"titre": "Intouchables", "annee": 2011, "acteurs": ["Omar Sy", "François Cluzet"]},
]

@dlt.resource(name="films")
def mes_films():
    yield films

pipeline = dlt.pipeline(pipeline_name="cinema", destination="duckdb", dataset_name="catalogue")
print(pipeline.run(mes_films()))
```

## Ce qui est imbriqué devient une table enfant

Une table ne peut pas ranger une liste dans une case. Alors dlt range `acteurs` dans une **deuxième table**, `films__acteurs` (deux tirets bas : « les acteurs de films »), avec une ligne par acteur. Pour relier les deux, dlt ajoute ses propres colonnes :

- `_dlt_id` : l'identifiant unique de chaque ligne, dans chaque table ;
- `_dlt_parent_id` : dans la table enfant, le `_dlt_id` de la ligne parente ;
- `_dlt_list_idx` : la position dans la liste (0 pour le premier acteur) ;
- `_dlt_load_id` : le chargement qui a écrit la ligne.

Un dictionnaire imbriqué, lui, ne crée pas de table : `{"realisateur": {"nom": "Jeunet"}}` devient une colonne `realisateur__nom`.

## Où vont les données

Le fichier DuckDB s'appelle comme le pipeline : `cinema.duckdb`, dans le dossier d'où tu lances le script. dlt garde aussi des tables à lui dans le dataset : `_dlt_loads` (l'historique des chargements), `_dlt_version` (les versions du schéma) et `_dlt_pipeline_state` (sa mémoire, tu la verras à la leçon 4).

Pour relire les données depuis Python, `pipeline.dataset()` te donne le dataset, et chaque table devient un attribut :

```python
ds = pipeline.dataset()
print(ds.row_counts().df())     # le nombre de lignes de chaque table
print(ds.films.df())            # la table films, en DataFrame pandas
print(ds("SELECT titre FROM films WHERE annee > 2005").df())   # du SQL
```

@@ brief
- **dlt** charge des données dans une base à ta place : il **extrait**, il **normalise** (il devine les colonnes et leurs types), puis il **charge**.
- Une **ressource** est une fonction qui donne des données avec `yield`. Un **pipeline** les envoie vers une **destination**, ici DuckDB, dans un **dataset**.
- Une liste imbriquée devient une **table enfant** au nom en `parent__liste`, reliée au parent par `_dlt_parent_id`.

@@ hints
- `yield modules` suffit : dlt accepte une liste entière d'un coup, il n'y a pas besoin de boucle.
- Si tu vois `ModuleNotFoundError: No module named 'dlt'`, tu as lancé `python` sans `uv run`, ou depuis un autre dossier.
- La table enfant s'appelle `modules__outils`, avec **deux** tirets bas. Ses colonnes : `value`, `_dlt_parent_id`, `_dlt_list_idx`, `_dlt_id`.
- Un module sans le champ en plus aura simplement une case vide (`<NA>`) dans cette colonne : dlt crée la colonne dès qu'un seul dictionnaire l'a.

@@ solution
~~~python
import dlt

# Mes données : une liste de dictionnaires, avec une liste imbriquée (outils)
modules = [
    {"id": "01", "titre": "Docker et Terraform", "outils": ["Docker", "Terraform", "Postgres"]},
    {"id": "02", "titre": "Orchestration", "outils": ["Airflow"]},
    {"id": "03", "titre": "Data warehouse", "outils": ["BigQuery", "GCS"]},
    {"id": "W1", "titre": "Workshop ingestion", "outils": ["dlt", "DuckDB"], "facultatif": False},
]


@dlt.resource(name="modules")      # le nom de la ressource devient le nom de la table
def mes_modules():
    yield modules                  # dlt accepte la liste entière d'un coup


# Le fichier s'appellera premier_pipeline.duckdb, les tables seront dans le schéma zoomcamp
pipeline = dlt.pipeline(pipeline_name="premier_pipeline", destination="duckdb", dataset_name="zoomcamp")
info = pipeline.run(mes_modules())  # extraire, normaliser, charger
print(info)

ds = pipeline.dataset()
print(ds.row_counts().df())
# La table enfant garde dans _dlt_parent_id le _dlt_id de son module
print(ds("""
    SELECT m.titre, o.value AS outil
    FROM modules m
    JOIN modules__outils o ON o._dlt_parent_id = m._dlt_id
""").df())
~~~

@@ breakfix-hints
- Deuxième lancement : 8 modules et 16 outils. dlt n'a rien remplacé, il a **ajouté**. Cherche `write_disposition` dans la documentation des ressources.
- `@dlt.resource(name="modules", write_disposition="replace")` vide la table avant chaque chargement.
- Pour le nom : DuckDB appelle la base comme le fichier, donc `zoomcamp`. Et le dataset aussi s'appelle `zoomcamp`. Lis le mot `Ambiguous` dans l'erreur.

@@ breakfix-answer
Au deuxième lancement, tout est en double : `modules 8`, `modules__outils 16`. Par défaut, une ressource dlt est en **append** : chaque chargement **ajoute** ses lignes à la table. Avec `write_disposition="replace"`, dlt remplace la table à chaque fois, et ton script devient **idempotent** : le lancer deux fois donne le même résultat qu'une fois. Pour repartir de zéro après la réparation, supprime `premier_pipeline.duckdb` et relance.

Le deuxième script échoue dès le chargement :

~~~text
dlt cannot update tables [...] in the dataset of schema `zoomcamp`. Cause: Binder Error: Ambiguous reference to catalog or schema "zoomcamp" - use a fully qualified path like 'zoomcamp.zoomcamp'.
~~~

Le fichier `zoomcamp.duckdb` donne une base nommée `zoomcamp`, qui contient un schéma (le dataset) nommé `zoomcamp` : quand dlt écrit `zoomcamp.modules`, DuckDB ne sait pas lequel des deux tu veux dire. Donne au pipeline et au dataset des noms **différents**. Puis supprime `test_nom.py` et `zoomcamp.duckdb`.
