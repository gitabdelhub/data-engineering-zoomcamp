@@ brief
- **Redpanda** parle le protocole de Kafka, en un seul programme (C++), sans ZooKeeper : il démarre en quelques secondes. Toute bibliothèque Kafka marche avec lui.
- Un **topic** est un journal d'événements nommé, découpé en **partitions**. Chaque message y reçoit un numéro croissant, son **offset**. Les messages restent dans le topic après leur lecture.
- **`rpk`** est l'outil en ligne de commande de Redpanda : `rpk topic create`, `rpk topic list`, `rpk topic produce`, `rpk topic consume`.
- Redpanda écoute sur **deux adresses** : `redpanda:29092` pour les autres conteneurs, `localhost:9092` pour ton terminal. Un client Kafka demande d'abord où se connecter, puis va à l'adresse **annoncée** (*advertised*).

@@ predict
Un consommateur lit les 10 messages d'un topic. Un second consommateur, d'une autre équipe, lit le même topic juste après. Combien de messages trouve-t-il : 0 ou 10 ? Et que contient le topic après les deux lectures ?

@@ predict-answer
**10**, et le topic contient toujours ses 10 messages. Contrairement à une file d'attente classique, Kafka ne supprime pas un message lu : il le garde jusqu'à la fin de sa **rétention** (une semaine par défaut). Chaque consommateur retient lui-même jusqu'où il a lu (son offset). C'est ce qui permet à plusieurs équipes de lire les mêmes événements, et de relire le passé après une panne.

### 2. Démarrer

`docker compose up redpanda -d`, puis `docker compose ps`.

### 3. rpk

~~~bash
docker compose exec redpanda rpk topic create essais -p 3
docker compose exec redpanda rpk topic describe essais
~~~

Pour produire : `docker compose exec redpanda rpk topic produce essais` attend tes messages au clavier, un par ligne, puis `Ctrl+D`. Pour lire : `rpk topic consume essais --num 3`, de la même façon.

@@ hints
- Si `docker compose ps` est vide, `docker compose logs redpanda` dit pourquoi.
- `-p 3` crée 3 partitions. `rpk topic describe` montre l'offset de fin de chaque partition.
- `rpk topic consume` montre pour chaque message sa partition et son offset : regarde-les.
- Pour les deux adresses : qui se connecte depuis où ? Ton terminal, ou un autre conteneur ?

@@ solution
`docker-compose.yml` :

~~~yaml
services:
  redpanda:
    image: redpandadata/redpanda:v25.3.9
    command:
      - redpanda
      - start
      - --smp
      - '1'
      - --reserve-memory
      - 0M
      - --overprovisioned
      - --node-id
      - '1'
      - --kafka-addr
      - PLAINTEXT://0.0.0.0:29092,OUTSIDE://0.0.0.0:9092
      - --advertise-kafka-addr
      - PLAINTEXT://redpanda:29092,OUTSIDE://localhost:9092
      - --pandaproxy-addr
      - PLAINTEXT://0.0.0.0:28082,OUTSIDE://0.0.0.0:8082
      - --advertise-pandaproxy-addr
      - PLAINTEXT://redpanda:28082,OUTSIDE://localhost:8082
      - --rpc-addr
      - 0.0.0.0:33145
      - --advertise-rpc-addr
      - redpanda:33145
    ports:
      - 8082:8082
      - 9092:9092
      - 28082:28082
      - 29092:29092
~~~

Les commandes :

~~~bash
docker compose up redpanda -d
docker compose exec redpanda rpk version
docker compose exec redpanda rpk topic create essais -p 3
docker compose exec redpanda rpk topic produce essais     # trois lignes, puis Ctrl+D
docker compose exec redpanda rpk topic consume essais --num 3
~~~

Relu deux fois, le topic rend les mêmes trois messages : la lecture ne les efface pas.

@@ breakfix
Écris un petit script Python qui produit un message avec `kafka-python`, mais avec `bootstrap_servers=["localhost:29092"]` (le port est bien publié dans ton fichier). Lance-le depuis ton terminal. Que se passe-t-il, après combien de temps, et pourquoi, alors que le port 29092 est ouvert ?

@@ breakfix-hints
- `uv run --with kafka-python python ton_script.py` suffit pour l'essai.
- Le client réussit la première étape. C'est la deuxième qui échoue.
- Quelle adresse Redpanda annonce-t-il sur l'écoute 29092 ? Ton terminal connaît-il ce nom ?

@@ breakfix-answer
~~~text
kafka.errors.KafkaTimeoutError: KafkaTimeoutError: Failed to update metadata after 60.0 secs.
~~~

(60 secondes par défaut ; moins si tu as réglé `max_block_ms`.) Le client se connecte bien à `localhost:29092`, demande les métadonnées, et Redpanda répond : « pour ce listener, connecte-toi à `redpanda:29092` ». Ton terminal ne connaît pas le nom `redpanda`, qui n'existe que dans le réseau Docker. Réparation : `localhost:9092` depuis ton terminal, `redpanda:29092` depuis un conteneur. Le même piège existe avec n'importe quel Kafka dans Docker : quand un client se connecte mais n'envoie rien, regarde l'adresse annoncée.
