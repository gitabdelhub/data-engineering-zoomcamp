@@ brief
- Un job PyFlink déclare ses tables en SQL : une table **source** avec `'connector' = 'kafka'` (le topic, l'adresse `redpanda:29092`, le format `json`), une table **sink** avec `'connector' = 'jdbc'` vers Postgres. Puis un `INSERT INTO sink SELECT ... FROM source`.
- Ces tables ne stockent rien dans Flink : ce sont des **descriptions** de l'endroit où lire et écrire.
- `scan.startup.mode` dit où commencer : `latest-offset` (seulement les nouveaux messages) ou `earliest-offset` (tout le topic). Chaque relance d'un job en `earliest` relit tout.
- On envoie le job avec `docker compose exec jobmanager ./bin/flink run -py /opt/src/job/ton_job.py --pyFiles /opt/src -d`. Le job tourne ensuite **en continu**, jusqu'à ce qu'on l'annule.

@@ codespaces
- Le job tourne dans les conteneurs : il parle à `redpanda:29092` et à `postgres:5432`, les adresses **internes**, pas `localhost`.
- L'interface du port 8081 montre les jobs en cours, leur graphe, et un bouton **Cancel Job**.

@@ verified
- Testé avec Flink 2.2.0 : le job pass-through du cours, en `latest-offset`, n'a écrit dans `processed_events` que les messages envoyés **après** son lancement (1 000 par envoi), pas les 1 000 déjà dans le topic.

@@ guide
### 1. La source

Un exemple sur des commandes, à adapter :

~~~python
t_env.execute_sql("""
    CREATE TABLE orders (
        shop_id INTEGER,
        amount DOUBLE,
        ordered_at BIGINT
    ) WITH (
        'connector' = 'kafka',
        'properties.bootstrap.servers' = 'redpanda:29092',
        'topic' = 'orders',
        'scan.startup.mode' = 'latest-offset',
        'format' = 'json'
    )
""")
~~~

### 2. Le sink

La même chose avec `'connector' = 'jdbc'` : l'URL `jdbc:postgresql://postgres:5432/postgres`, le nom de la table, l'utilisateur et le mot de passe. La table Postgres doit exister.

### 3. L'insertion

`INSERT INTO sink SELECT ..., TO_TIMESTAMP_LTZ(ms, 3) AS pickup_datetime FROM source`. Le `3` dit « millisecondes ».

### 4. Lancer, et reprendre la main

~~~bash
docker compose exec jobmanager ./bin/flink run -py /opt/src/job/pass_through_job.py --pyFiles /opt/src -d
~~~

Quand la ligne `Job has been submitted with JobID ...` apparaît, ou si rien ne bouge après 30 secondes, `Ctrl+C`. Vérifie dans le port 8081 que le job est toujours `RUNNING`.

@@ hints
- `ValidationException ... Could not find any factory for identifier 'kafka'` : ton image n'a pas son connecteur (leçon 6).
- Si le job échoue tout de suite, l'onglet **Exceptions** du job, dans le port 8081, donne la vraie erreur.
- Les noms de colonnes de la source doivent être exactement les clés du JSON envoyé par ton producteur.
- Pour annuler : le bouton **Cancel Job**, ou `docker compose exec jobmanager ./bin/flink cancel <JobID>`.

@@ solution
`07-streaming/code/src/job/pass_through_job.py` de ton fork est la référence. Le cœur :

~~~sql
CREATE TABLE events (
    PULocationID INTEGER,
    DOLocationID INTEGER,
    trip_distance DOUBLE,
    total_amount DOUBLE,
    tpep_pickup_datetime BIGINT
) WITH (
    'connector' = 'kafka',
    'properties.bootstrap.servers' = 'redpanda:29092',
    'topic' = 'rides',
    'scan.startup.mode' = 'latest-offset',
    'format' = 'json'
);

INSERT INTO processed_events
SELECT PULocationID, DOLocationID, trip_distance, total_amount,
       TO_TIMESTAMP_LTZ(tpep_pickup_datetime, 3) AS pickup_datetime
FROM events;
~~~

En `earliest-offset`, le job relit **tout** le topic : chaque envoi passé de ton producteur, d'où un nombre de lignes égal à l'offset de fin du topic (`rpk topic describe rides -p`).

@@ breakfix
Dans la source de ton job, remplace `redpanda:29092` par `localhost:9092`, l'adresse qui marche si bien pour ton producteur. Annule l'ancien job, envoie le nouveau, puis ton producteur. Que montre l'interface du port 8081 ? Que contient la table ? Explique avec la leçon 2.

@@ breakfix-hints
- Regarde l'état du job, puis l'onglet **Exceptions**.
- Le job tourne dans un conteneur. Qui est `localhost` pour lui ?
- La réponse est dans les deux adresses de Redpanda.

@@ breakfix-answer
Le job ne lit rien : il reste bloqué puis passe en échec ou en redémarrage, avec des erreurs de connexion ou de délai dans l'onglet **Exceptions**, et la table ne bouge pas. Dans un conteneur, `localhost` est **le conteneur lui-même** : il n'y a pas de Redpanda dans le conteneur du JobManager. C'est l'inverse exact du breakfix de la leçon 2 : `localhost:9092` depuis ton terminal, `redpanda:29092` depuis un conteneur. Remets l'adresse interne et renvoie le job.
