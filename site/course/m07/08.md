@@ brief
- Une **fenêtre** découpe le temps en morceaux pour agréger : `TUMBLE(TABLE events, DESCRIPTOR(event_timestamp), INTERVAL '1' HOUR)` crée des fenêtres d'une heure, fixes, sans chevauchement. Chaque ligne y gagne les colonnes `window_start` et `window_end`.
- Le **temps de l'événement** (*event time*) est l'heure écrite dans le message (la prise en charge), pas l'heure où Flink le reçoit. On le déclare comme colonne calculée, avec un **watermark** : `WATERMARK FOR event_timestamp AS event_timestamp - INTERVAL '5' SECOND`.
- Le watermark dit à Flink : « je ne verrai plus d'événement plus vieux que ça ». Quand il dépasse la fin d'une fenêtre, Flink **publie** le résultat de cette fenêtre, puis l'oublie.
- **Piège vérifié** : la requête du cours groupe par `window_start` seulement. Flink n'y reconnaît pas une agrégation par fenêtre, et en fait un `GROUP BY` ordinaire, mis à jour à chaque événement. Pour une vraie fenêtre, il faut grouper par `window_start, window_end`.

@@ verified
- Testé avec Flink 2.2.0 sur 3 000 trajets. Le job du cours, groupé par `window_start` seul, apparaît dans le plan comme `GroupAggregate` : il remplit **toutes** les heures, y compris la dernière, qui n'est pourtant pas finie, et accepte un événement en retard d'un jour.
- Groupé par `window_start, window_end` avec un parallélisme de 1, le plan montre `GlobalWindowAggregate` : 521 lignes, la dernière heure **manque** (elle attend le watermark), et l'événement en retard d'un jour est ignoré.
- Le même job correct avec un parallélisme de **3** n'a rien écrit du tout : 0 ligne. C'est le breakfix.

### 2. Le temps de l'événement

Un exemple sur des commandes :

~~~sql
CREATE TABLE orders (
    shop_id INTEGER,
    amount DOUBLE,
    ordered_at BIGINT,
    order_time AS TO_TIMESTAMP_LTZ(ordered_at, 3),
    WATERMARK FOR order_time AS order_time - INTERVAL '5' SECOND
) WITH (...)
~~~

### 3. La vraie fenêtre

~~~sql
SELECT window_start, shop_id, COUNT(*) AS num_orders
FROM TABLE(TUMBLE(TABLE orders, DESCRIPTOR(order_time), INTERVAL '1' HOUR))
GROUP BY window_start, window_end, shop_id
~~~

`window_end` est dans le `GROUP BY` sans être dans le `SELECT` : c'est permis, et c'est ce qui fait la différence.

### 4. Lire le plan

Dans le port 8081, ouvre chaque job : le graphe nomme ses opérateurs. Cherche `GroupAggregate` ou `WindowAggregate`.

@@ solution
Dans ton job, seules trois choses changent par rapport à celui du cours :

~~~python
env.set_parallelism(1)  # le topic a une seule partition
~~~

~~~sql
INSERT INTO fenetres_horaires
SELECT window_start, PULocationID, COUNT(*) AS num_trips, SUM(total_amount) AS total_revenue
FROM TABLE(TUMBLE(TABLE events, DESCRIPTOR(event_timestamp), INTERVAL '1' HOUR))
GROUP BY window_start, window_end, PULocationID;
~~~

et le nom de la table sink. Les deux jobs donnent les mêmes nombres pour toutes les heures **finies**. La différence est dans le comportement : le job du cours garde un état qui grandit sans fin et met à jour ses lignes à chaque événement ; le tien publie chaque heure une fois, quand le watermark la dépasse, puis libère sa mémoire.

@@ breakfix
Garde ton job correct, mais remets `env.set_parallelism(3)`, comme dans le cours. Vide sa table, relance-le, attends une minute. Combien de lignes ? Pourquoi, alors que la requête est juste ? Répare.

@@ breakfix-hints
- Avec 3 tâches et 1 partition, combien de tâches reçoivent des messages ?
- Le watermark d'un opérateur est le **minimum** des watermarks de ses entrées.
- Une tâche qui ne reçoit rien n'avance jamais son watermark.

@@ breakfix-answer
**0 ligne.** Avec un parallélisme de 3, Flink lance trois lecteurs pour une seule partition : un seul reçoit des messages, les deux autres sont au repos. Le watermark de l'agrégation est le minimum de ses trois entrées, et deux d'entre elles n'avancent jamais : aucune fenêtre ne se ferme. Réparation : `set_parallelism(1)`, autant que de partitions. Le homework le rappelle aussi. Flink a une option pour ignorer les entrées au repos (`table.exec.source.idle-timeout`), mais elle n'a pas été testée ici. Le job du cours ne montre pas ce problème pour une seule raison : il n'utilise pas le watermark du tout.
