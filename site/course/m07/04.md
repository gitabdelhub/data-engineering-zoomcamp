@@ brief
- Un **consommateur** lit un topic avec `KafkaConsumer(topic, bootstrap_servers=[...], group_id=..., auto_offset_reset=..., value_deserializer=...)`, puis une boucle `for message in consumer`.
- Le **désérialiseur** fait l'inverse du sérialiseur : octets → JSON → dictionnaire → `Ride`.
- Un **groupe de consommateurs** (`group_id`) retient son **offset** : le numéro du prochain message à lire. Relancé, le consommateur reprend où son groupe s'était arrêté.
- `auto_offset_reset` ne sert que quand le groupe n'a **pas encore** d'offset : `earliest` commence au début du topic, `latest` n'attend que les nouveaux messages.

@@ codespaces
- Lance le consommateur dans un second terminal, pendant que le producteur tourne dans le premier : tu vois les messages arriver.
- `docker compose exec redpanda rpk group list` et `rpk group describe <groupe>` montrent les groupes et leurs offsets.

@@ verified

@@ predict-answer
Les messages **11 à 20**. Le groupe a enregistré son offset (10) dans Redpanda. `earliest` ne joue qu'à la première lecture d'un groupe, quand il n'a encore rien enregistré. Avec un **nouveau** `group_id`, le groupe n'a pas d'offset : `earliest` s'applique, et il repart du message 1. Changer de groupe, c'est la façon simple de « tout relire ».

@@ guide
### 1. Le désérialiseur

Dans `models.py`, une fonction qui reçoit des `bytes` : `decode("utf-8")`, `json.loads`, puis `Ride(**dictionnaire)`.

### 2. Le consommateur

Un exemple sur les commandes :

~~~python
from kafka import KafkaConsumer

consumer = KafkaConsumer(
    "orders",
    bootstrap_servers=["localhost:9092"],
    group_id="orders-console",
    auto_offset_reset="earliest",
    value_deserializer=order_deserializer,
)
for message in consumer:
    print(message.offset, message.value)
~~~

### 3. La date

`datetime.fromtimestamp(ms / 1000)` transforme des millisecondes en date lisible.

### 4. Les groupes

~~~bash
docker compose exec redpanda rpk group list
docker compose exec redpanda rpk group describe rides-console
~~~

@@ hints
- `message.offset` et `message.partition` existent sur chaque message : affiche-les pour comprendre.
- Pour s'arrêter après 10 messages : un compteur et un `break`, puis `consumer.close()`.
- `close()` enregistre l'offset du groupe. Sans lui, le groupe enregistre quand même, toutes les 5 secondes.
- `rpk group describe` montre `CURRENT-OFFSET` et `LAG` : le lag, c'est ce qui reste à lire.

@@ solution
`src/consumers/consumer.py` du cours, dans `07-streaming/code/src/consumers/` de ton fork, est la référence. Le cœur :

~~~python
consumer = KafkaConsumer(
    "rides",
    bootstrap_servers=["localhost:9092"],
    auto_offset_reset="earliest",
    group_id="rides-console",
    value_deserializer=ride_deserializer,
)
count = 0
for message in consumer:
    ride = message.value
    pickup_dt = datetime.fromtimestamp(ride.tpep_pickup_datetime / 1000)
    print(f"Received: PU={ride.PULocationID}, amount=${ride.total_amount:.2f}, pickup={pickup_dt}")
    count += 1
    if count >= 10:
        break
consumer.close()
~~~

Premier lancement : messages d'offset 0 à 9. Deuxième : 10 à 19. Nouveau groupe : de nouveau 0 à 9. Un nouveau groupe en `latest` n'affiche **rien** tant que le producteur ne renvoie pas de messages.

@@ breakfix
Un collègue veut « tout relire depuis le début » et passe `auto_offset_reset` de `latest` à `earliest`, sans toucher au `group_id`. Il relance : rien ne change, il ne voit que les nouveaux messages. Reproduis-le avec ton consommateur, explique-le, et donne deux façons de vraiment tout relire.

@@ breakfix-hints
- Le groupe a déjà un offset enregistré. Quand `auto_offset_reset` joue-t-il ?
- `rpk group` a une commande pour déplacer l'offset d'un groupe.
- L'autre façon ne touche pas à Redpanda.

@@ breakfix-answer
Le groupe a déjà un offset : `auto_offset_reset` ne joue **que** pour un groupe sans offset, ou dont l'offset n'existe plus. Le changer ne fait donc rien. Pour tout relire : un nouveau `group_id` (le plus simple), ou remettre l'offset du groupe au début, consommateur arrêté : `docker compose exec redpanda rpk group seek rides-console --to start`. En production, on préfère le second : le nom du groupe a souvent un sens pour la surveillance.
