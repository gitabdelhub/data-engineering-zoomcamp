@@ brief
- **Flink** est un moteur de traitement de flux : il lit un topic en continu, garde un **état** (des compteurs par fenêtre, par zone), et le sauvegarde régulièrement (*checkpoints*) pour reprendre après une panne sans tout recalculer.
- Un cluster Flink a un **JobManager** (il reçoit les jobs, les planifie, et sert l'interface web sur le port **8081**) et un ou plusieurs **TaskManagers** (ils exécutent le travail, dans des **slots**).
- Le cours écrit ses jobs en **PyFlink**, avec du SQL. L'image Docker part de l'image officielle `flink:2.2.0`, ajoute Python 3.12 et `apache-flink` avec uv, puis télécharge des **connecteurs** (`.jar`) : Kafka, JDBC, PostgreSQL. Sans eux, Flink ne sait parler ni à Redpanda ni à Postgres.
- Ton dossier `src/` est **monté** dans les conteneurs, en `/opt/src` : tu modifies un job dans VS Code, Flink voit le changement tout de suite.

@@ codespaces
- La construction de l'image prend quelques minutes la première fois (Python, `apache-flink`, les connecteurs). Les fois suivantes, Docker réutilise ses couches.
- Les deux services Flink demandent environ 3,5 Go de mémoire à eux deux. Un Codespace de base (8 Go) suffit, à condition d'arrêter les services des modules précédents (`docker ps`).

@@ verified
- Testé avec `flink:2.2.0-scala_2.12-java17` : l'interface du port 8081 montre 1 TaskManager et 15 slots.
- **Piège 1** : le texte officiel télécharge les fichiers depuis `.../07-streaming/workshop/...`. Ce dossier n'existe plus, l'adresse répond **404** : les fichiers sont dans `07-streaming/code/` de ton fork. Copie-les de là.
- **Piège 2**, vécu pendant mes tests : le `RUN wget ...; wget ...` du Dockerfile sépare les téléchargements par des `;`. Le serveur Maven a répondu `ERROR 429: Too Many Requests` pour deux connecteurs, et **l'image s'est construite quand même**. Le job a échoué plus tard avec `Could not find any factory for identifier 'kafka'`. C'est le breakfix.

@@ predict
Le Dockerfile télécharge cinq fichiers `.jar` dans une seule instruction `RUN`, séparés par des `;`. Le deuxième téléchargement échoue. `docker compose build` s'arrête-t-il en erreur ? Quand vas-tu découvrir le problème ?

@@ predict-answer
Non, la construction **réussit**. Avec `;`, le shell enchaîne les commandes quoi qu'il arrive, et Docker ne regarde que le code de retour de la **dernière**. Tu découvres le problème bien plus tard, au lancement d'un job, avec une erreur qui ne parle pas de téléchargement : `Could not find any factory for identifier 'kafka'`. Avec `&&`, la construction se serait arrêtée tout de suite, sur la bonne ligne. Règle : une erreur doit casser le plus tôt possible.

### 2. Le `&&`

Remplace les `;` de l'instruction `RUN wget ...` par des `&&`, et ajoute `-q` à chaque `wget` pour un journal plus court.

### 3. Les services

Les blocs `jobmanager` et `taskmanager` sont dans le `docker-compose.yml` du cours. Recopie-les en les lisant : l'image construite, le port 8081, les volumes, les `FLINK_PROPERTIES`.

### 4. Construire et démarrer

~~~bash

docker compose up -d
docker compose ps
docker compose exec jobmanager ls /opt/flink/lib
~~~

Puis ouvre le port 8081 dans l'onglet **Ports**.

@@ solution
L'instruction de téléchargement, avec des `&&` :

~~~dockerfile
WORKDIR /opt/flink/lib
RUN wget -q https://repo1.maven.org/maven2/org/apache/flink/flink-sql-connector-kafka/4.0.1-2.0/flink-sql-connector-kafka-4.0.1-2.0.jar && \
    wget -q https://repo.maven.apache.org/maven2/org/apache/flink/flink-connector-jdbc-core/4.0.0-2.0/flink-connector-jdbc-core-4.0.0-2.0.jar && \
    wget -q https://repo.maven.apache.org/maven2/org/apache/flink/flink-connector-jdbc-postgres/4.0.0-2.0/flink-connector-jdbc-postgres-4.0.0-2.0.jar && \
    wget -q https://repo1.maven.org/maven2/org/postgresql/postgresql/42.7.10/postgresql-42.7.10.jar
~~~

Les services : ceux du `docker-compose.yml` du cours, à l'identique. `ls /opt/flink/lib` doit montrer, entre autres :

~~~text
flink-connector-jdbc-core-4.0.0-2.0.jar
flink-connector-jdbc-postgres-4.0.0-2.0.jar
flink-json-2.2.0.jar
flink-sql-connector-kafka-4.0.1-2.0.jar
postgresql-42.7.10.jar
~~~

@@ breakfix
Reproduis le piège que j'ai vécu. Dans une copie de ton Dockerfile (`Dockerfile.casse`), remets les `;`, et change le numéro de version du connecteur Kafka en `4.0.9-2.0`, qui n'existe pas. Construis avec `docker build -f Dockerfile.casse -t flink-casse .`. Le build réussit-il ? Qu'affiche `ls /opt/flink/lib` dans cette image (`docker run --rm flink-casse ls /opt/flink/lib`) ? Quelle erreur aurait un job Kafka ?

@@ breakfix-hints
- Cherche `ERROR 404` dans le journal de construction : il défile sans arrêter rien.
- La dernière commande de la ligne `RUN` réussit : c'est elle que Docker regarde.
- L'erreur du job ne parle pas de téléchargement, mais d'une « factory ».

@@ breakfix-answer
Le build **réussit** : `wget` affiche `ERROR 404: Not Found` pour le connecteur Kafka, mais le `wget` suivant réussit, et Docker ne voit que le code de retour de la dernière commande. L'image n'a pas de connecteur Kafka, et un job qui déclare `'connector' = 'kafka'` échoue au lancement :

~~~text
org.apache.flink.table.api.ValidationException: Could not find any factory for identifier 'kafka' that implements 'org.apache.flink.table.factories.DynamicTableFactory' in the classpath.
~~~

Avec `&&`, la construction s'arrête sur le `wget` fautif, avec le nom du fichier. Dans mes tests, la cause n'était pas une faute de frappe mais un serveur saturé (`429 Too Many Requests`) : relancer `docker compose build` suffisait. Supprime l'image de test ensuite : `docker rmi flink-casse`.
