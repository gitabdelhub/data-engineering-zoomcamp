@@ brief
- Un consommateur peut **écrire** ce qu'il lit : chaque message devient une ligne `INSERT` dans PostgreSQL, avec `psycopg2`.
- La table doit exister **avant** : le consommateur ne la crée pas. Ici, `processed_events`, avec une vraie colonne `TIMESTAMP` pour la date.
- `conn.autocommit = True` valide chaque `INSERT` tout de suite. Sans lui, rien n'est visible tant qu'on n'appelle pas `conn.commit()`.
- Ce consommateur est simple, mais il montre la limite des scripts maison : pas de fenêtres, pas d'agrégats, et chaque panne demande du code pour reprendre proprement. C'est la raison de Flink, à la leçon 6.

@@ codespaces
- PostgreSQL rejoint ton `docker-compose.yml`, comme service `postgres` (port 5432). Pour l'interroger : `docker compose exec postgres psql -U postgres -d postgres`, ou `uvx pgcli -h localhost -U postgres -d postgres`.
- Ne lance pas un autre Postgres sur le port 5432 en même temps (celui du module 1, par exemple) : le second ne démarre pas.

@@ verified
- Testé avec `postgres:18` et `psycopg2-binary` : après un producteur de 1 000 trajets, le consommateur insère 1 000 lignes et affiche `Inserted 1000 rows...` en passant.
- Avec un ancien conteneur qui tenait déjà le port 5432, `docker compose up` a refusé : `Bind for 0.0.0.0:5432 failed: port is already allocated`.

@@ predict
Ton consommateur Postgres a le `group_id` `rides-to-postgres`, qui n'a jamais lu le topic, avec `earliest`. Le topic contient déjà 1 000 trajets. Tu le lances. Combien de lignes dans la table après quelques secondes ? Et si tu l'arrêtes et le relances ?

@@ predict-answer
**1 000** au premier lancement : nouveau groupe, donc `earliest`, donc tout le topic. Relancé, **toujours 1 000** : le groupe reprend à son offset, et il n'y a rien de nouveau. Mais attention : `kafka-python` enregistre l'offset **tout seul**, toutes les 5 secondes (`enable_auto_commit=True` par défaut), sans attendre tes `INSERT`, et il lit les messages par paquets. Après un plantage, il peut donc relire des messages déjà insérés (des doublons) ou sauter des messages jamais insérés (des pertes). Ce consommateur ne garantit ni « au moins une fois », ni « exactement une fois ». Pour « au moins une fois » : `enable_auto_commit=False`, et `consumer.commit()` seulement **après** l'`INSERT` validé.

@@ practice
Ajoute PostgreSQL à ton projet, crée la table des trajets, et écris un consommateur qui y range chaque message.

@@ constraints
- `docker-compose.yml` a un service `postgres` (image `postgres:18`, utilisateur, mot de passe et base `postgres`, port 5432)
- La table `processed_events` a les deux zones, la distance, le montant et `pickup_datetime` en `TIMESTAMP`
- `src/consumers/consumer_postgres.py` insère chaque trajet, avec un groupe à lui
- `SELECT COUNT(*) FROM processed_events` donne 1 000 après un seul envoi
- Tu as relancé le producteur pendant que le consommateur tournait, et vu le nombre de lignes monter

@@ guide
### 1. Le service

Le bloc `postgres` est dans le texte de la leçon officielle, plus bas. Puis `docker compose up postgres -d`.

### 2. La table

Ouvre `psql` dans le conteneur, et écris le `CREATE TABLE` toi-même : cinq colonnes, avec les types de PostgreSQL (`INTEGER`, `DOUBLE PRECISION`, `TIMESTAMP`).

### 3. Le consommateur

`uv add psycopg2-binary`, puis repars de ton consommateur de la leçon 4. Un exemple d'insertion, sur les commandes :

~~~python
import psycopg2

conn = psycopg2.connect(host="localhost", port=5432, database="postgres", user="postgres", password="postgres")
conn.autocommit = True
cur = conn.cursor()
cur.execute("INSERT INTO orders (shop_id, amount) VALUES (%s, %s)", (order.shop_id, order.amount))
~~~

Ce consommateur ne s'arrête pas après 10 messages : il tourne jusqu'au `Ctrl+C`.

### 4. En direct

Terminal 1 : le consommateur. Terminal 2 : le producteur. Terminal 3 : `SELECT COUNT(*)` de temps en temps.

@@ hints
- Les `%s` de `psycopg2` sont des paramètres, pas du formatage Python : n'utilise jamais un f-string dans une requête SQL.
- `connection refused` sur 5432 : `docker compose ps` dit si Postgres tourne, `docker compose logs postgres` pourquoi.
- La date : `datetime.fromtimestamp(ms / 1000)`, comme à la leçon 4 ; `psycopg2` sait insérer un `datetime`.
- Si tu as 2 000 lignes, ton consommateur a lu deux fois, ou ton topic contient deux envois.

@@ solution
La table :

~~~sql
CREATE TABLE processed_events (
    PULocationID INTEGER,
    DOLocationID INTEGER,
    trip_distance DOUBLE PRECISION,
    total_amount DOUBLE PRECISION,
    pickup_datetime TIMESTAMP
);
~~~

Le consommateur : `07-streaming/code/src/consumers/consumer_postgres.py` de ton fork. Le cœur de la boucle :

~~~python
for message in consumer:
    ride = message.value
    pickup_dt = datetime.fromtimestamp(ride.tpep_pickup_datetime / 1000)
    cur.execute(
        """INSERT INTO processed_events
           (PULocationID, DOLocationID, trip_distance, total_amount, pickup_datetime)
           VALUES (%s, %s, %s, %s, %s)""",
        (ride.PULocationID, ride.DOLocationID, ride.trip_distance, ride.total_amount, pickup_dt),
    )
~~~

@@ breakfix
Commente la ligne `conn.autocommit = True` et relance un nouveau groupe. Le consommateur affiche bien `Inserted 100 rows...`, puis `Inserted 200 rows...`. Mais `SELECT COUNT(*)` dans un autre terminal reste à zéro. Pourquoi ? Que se passe-t-il à l'arrêt du script ? Répare de deux façons.

@@ breakfix-hints
- Sans `autocommit`, `psycopg2` ouvre une transaction au premier `execute`.
- Les autres sessions ne voient pas une transaction pas encore validée.
- Une réparation remet la ligne, l'autre appelle une méthode régulièrement.

@@ breakfix-answer
Sans `autocommit`, tous les `INSERT` vivent dans **une seule transaction** jamais validée : ton script les voit, les autres sessions non. À l'arrêt par `Ctrl+C`, la connexion se ferme sans `commit` : PostgreSQL annule tout, et la table reste vide. Pire : relance avec le **même** groupe et `autocommit` réparé, la table reste vide. Pendant que tes `INSERT` attendaient, `kafka-python` a enregistré les offsets des messages lus : pour Redpanda, ils sont traités. Ces trajets sont perdus pour ce groupe (testé : 1 000 messages, arrêt après 500, relance, 0 ligne). Réparations : remettre `conn.autocommit = True` (un commit par ligne, simple mais plus lent), ou appeler `conn.commit()` tous les N messages (plus rapide, mais il faut choisir quoi faire des N derniers en cas de panne). C'est le même compromis que le `flush()` du producteur : la vitesse contre la garantie. Et pour ne rien perdre, l'offset ne doit avancer qu'après le `commit` de Postgres : `enable_auto_commit=False`, puis `conn.commit()` suivi de `consumer.commit()`.
