@@ brief
- **Colossus** stocke les données, **Dremel** exécute les requêtes, et **Jupiter**, un réseau d'environ 1 To par seconde, les relie. Stockage et calcul sont séparés : stocker coûte peu, lire coûte.
- Le stockage est **en colonnes** : chaque colonne est rangée à part. Une requête qui cite 2 colonnes sur 20 ne touche pas aux 18 autres.
- Dremel découpe une requête en **arbre** : la racine répartit le travail entre des mélangeurs (*mixers*), qui le répartissent entre des feuilles. Les feuilles lisent les données, et les résultats partiels remontent en s'additionnant.
- C'est pour ça que BigQuery reste rapide quand les données grossissent : il ajoute des feuilles.

@@ guide
### 1. La règle de calcul

Pour une requête sans filtre, BigQuery estime : pour chaque colonne citée, **nombre de valeurs non vides × taille d'une valeur**. Un `INT64`, un `FLOAT64` ou un `TIMESTAMP` pèse 8 octets. Un `STRING` pèse 2 octets plus le nombre de caractères. Une valeur vide ne pèse rien.

### 2. Les nombres dont tu as besoin

`COUNT(colonne)` compte les valeurs **non vides** d'une colonne, alors que `COUNT(*)` compte les lignes :

~~~sql
SELECT COUNT(*) AS lignes, COUNT(store_and_fwd_flag) AS flags_remplis
FROM dez_dataset.green_2019_2020;
~~~

`store_and_fwd_flag` vaut toujours `N` ou `Y` : un seul caractère.

### 3. Calcule, puis vérifie

Fais les deux multiplications. La console écrit « MB » mais divise par 1 024 × 1 024 : divise ton résultat en octets par 1 048 576. Puis colle chaque requête dans l'éditeur, sans la lancer, et compare avec l'estimation.

### 4. Le script DuckDB

Télécharge le fichier de janvier 2019 dans ton dossier (`curl -sSLO` et l'adresse de la leçon 1), puis écris `colonnes.py`. Les pièces dont tu as besoin, sur un fichier de ventes :

~~~python
import duckdb

con = duckdb.connect()   # une base en mémoire, rien sur le disque
# Une requête SQL qui lit un CSV et écrit un Parquet
con.execute("COPY (SELECT * FROM read_csv('ventes.csv.gz')) TO 'ventes.parquet' (FORMAT parquet)")
# Un résultat à afficher : print() d'une requête dessine un tableau
print(con.sql("SELECT * FROM parquet_metadata('ventes.parquet') LIMIT 3"))
# Une seule valeur : execute(...).fetchone()[0]
n = con.execute("SELECT count(*) FROM 'ventes.parquet'").fetchone()[0]
~~~

- `parquet_metadata(...)` donne une ligne par colonne **et par morceau** du fichier (*row group*). La colonne s'appelle `path_in_schema`, sa taille compressée `total_compressed_size`, en octets. Additionne par colonne avec `GROUP BY`, et trie.
- Pour chronométrer : `time.perf_counter()` avant et après, puis la différence.
- La requête à chronométrer sur les deux fichiers : le nombre de zones de départ distinctes, `count(DISTINCT PULocationID)`.

`mon-travail/module-03/colonnes.py` :

~~~python
import time

import duckdb

CSV = "green_tripdata_2019-01.csv.gz"
PARQUET = "green_tripdata_2019-01.parquet"

con = duckdb.connect()
# DuckDB lit le CSV compressé et écrit un Parquet : une seule requête SQL
con.execute(f"COPY (SELECT * FROM read_csv('{CSV}')) TO '{PARQUET}' (FORMAT parquet)")

# La taille de chaque colonne dans le Parquet, additionnée sur tous ses morceaux (row groups)
print(con.sql(f"""
    SELECT path_in_schema AS colonne, round(sum(total_compressed_size) / 1024) AS ko
    FROM parquet_metadata('{PARQUET}')
    GROUP BY colonne
    ORDER BY ko DESC
"""))

# Même question aux deux fichiers : on chronomètre
for fichier in [CSV, PARQUET]:
    debut = time.perf_counter()
    n = con.execute(f"SELECT count(DISTINCT PULocationID) FROM '{fichier}'").fetchone()[0]
    print(f"{fichier} : {n} zones en {time.perf_counter() - debut:.2f} s")
~~~

La fin de la sortie, à quelques centièmes près :

~~~text
green_tripdata_2019-01.csv.gz : 256 zones en 0.41 s
green_tripdata_2019-01.parquet : 256 zones en 0.00 s
~~~

Le CSV doit être lu **en entier**, ligne par ligne, et décompressé, pour en sortir une seule colonne. Le Parquet range chaque colonne à part : DuckDB ne lit que `PULocationID`, comme BigQuery.

@@ breakfix-hints

@@ breakfix-answer
DuckDB répond `Binder Error: No function matches the given name and argument types 'sum(VARCHAR)'`. Pour deviner les types, il lit un échantillon du début du fichier, et en janvier 2019, `congestion_surcharge` y est toujours vide : faute d'indice, il choisit le texte. `ehail_fee` subit le même sort. Un `CAST` dans la requête contournerait le problème une fois, mais le Parquet resterait faux pour tous ceux qui le liront. La vraie réparation est à la source : `read_csv('{CSV}', types={'congestion_surcharge': 'DOUBLE', 'ehail_fee': 'DOUBLE'})`, puis relancer le script. La somme vaut alors `2.75` : un seul trajet de janvier 2019 a payé cette taxe. C'est exactement pour ça que ta table externe de la leçon 1 a ses types écrits à la main.
