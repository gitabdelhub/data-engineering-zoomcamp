@@ brief
- **BigQuery ML** entraîne des modèles de machine learning **en SQL**, sans sortir les données de l'entrepôt.
- 🔑 Les étapes : choisir les **variables** (*features*) et ce qu'on veut prédire (le *label*), préparer une table, `CREATE MODEL`, puis `ML.EVALUATE`, `ML.PREDICT` et `ML.EXPLAIN_PREDICT`.
- BigQuery prépare les variables tout seul : il **standardise** les nombres et **encode** chaque texte comme une catégorie (*one-hot*).
- 🔑 Un identifiant écrit comme un nombre (une zone, un mode de paiement) n'est pas une quantité : il faut le transformer en `STRING` pour qu'il soit traité comme une catégorie.
- `CREATE MODEL` est facturé à part, avec 10 Go gratuits par mois. Regarde toujours la taille de ta table avant d'entraîner.

@@ predict
Avant de prédire les pourboires, regarde les données. Le pourboire moyen d'un trajet payé **par carte** en 2019 est d'environ 1,85 $. Et celui d'un trajet payé **en espèces** ?

@@ predict-answer
**0 $**, sur près de 2,4 millions de trajets. Les clients donnent bien des pourboires en espèces, mais le taximètre ne les voit pas : seuls les pourboires payés par carte sont enregistrés. Si tu gardais les trajets en espèces, ton modèle apprendrait que « payer en espèces » fait disparaître le pourboire, ce qui est faux. On entraîne donc seulement sur les paiements par carte (`payment_type = 1`). Regarder les données avant d'entraîner évite d'apprendre un artefact.

@@ constraints

@@ guide
### 1. Regarde les pourboires

Avant tout, vérifie la prédiction de cette leçon : le nombre de trajets et le pourboire moyen par `payment_type`, sur 2019. Ta table `green_part` exige un filtre sur la date depuis la leçon 3 : `WHERE DATE(lpep_pickup_datetime) BETWEEN '2019-01-01' AND '2019-12-31'`.

### 2. La table d'entraînement

La leçon crée sa table avec la liste des colonnes et leurs types, puis un `SELECT`. Une forme plus courte suffit, avec `CAST(... AS STRING)` directement dans le `SELECT` et un nom pour chaque colonne transformée :

~~~sql
CREATE OR REPLACE TABLE dez_dataset.ventes_ml AS
SELECT quantite, prix, CAST(id_magasin AS STRING) AS id_magasin, remise
FROM dez_dataset.ventes
WHERE annee = 2019 AND prix > 0;
~~~

Ici : les sept colonnes de la consigne, à partir de `green_part`, avec trois conditions dans le `WHERE` (l'année, la carte, la course positive). Avant de lancer, lis l'estimation. Après, regarde la taille de la table dans **Détails**.

### 3. Le modèle

Reprends le `CREATE MODEL` de la leçon, avec tes noms. `input_label_cols` donne la colonne à prédire, `DATA_SPLIT_METHOD = 'AUTO_SPLIT'` laisse BigQuery mettre de côté des lignes pour l'évaluation. Toutes les autres colonnes du `SELECT` deviennent des variables : ne sélectionne que celles que tu veux.

### 4. Regarde ce que BigQuery a compris

`ML.FEATURE_INFO` : une ligne par variable. Les nombres ont un minimum, un maximum et une moyenne. Les catégories ont un nombre de valeurs distinctes (`category_count`).

### 5. Évalue et explique

`ML.EVALUATE` sur la table d'entraînement, puis `ML.EXPLAIN_PREDICT` avec `STRUCT(3 AS top_k_features)` et un `LIMIT 5` à la fin. Pour chaque ligne, regarde quelles variables pèsent le plus dans la prédiction.

@@ hints
- Le `WHERE` de la table : `DATE(lpep_pickup_datetime) BETWEEN '2019-01-01' AND '2019-12-31' AND payment_type = 1 AND fare_amount > 0`.
- `ML.EVALUATE(MODEL dez_dataset.tip_model, (SELECT * FROM dez_dataset.green_tips_2019))` : le mot `MODEL` est obligatoire devant le nom.
- `mean_absolute_error` est l'erreur moyenne en dollars. `r2_score` va de 0 (le modèle ne fait pas mieux que la moyenne) à 1 (parfait).

@@ solution
`mon-travail/module-03/sql/05_ml.sql` :

~~~sql
-- Les pourboires selon le paiement : seule la carte enregistre un pourboire
SELECT payment_type, COUNT(*) AS trips, ROUND(AVG(tip_amount), 2) AS avg_tip
FROM dez_dataset.green_part
WHERE DATE(lpep_pickup_datetime) BETWEEN '2019-01-01' AND '2019-12-31'
GROUP BY payment_type
ORDER BY payment_type;

-- La table d'entraînement : 2019, carte, course positive. Les zones deviennent des catégories
CREATE OR REPLACE TABLE dez_dataset.green_tips_2019 AS
SELECT
  passenger_count,
  trip_distance,
  CAST(PULocationID AS STRING) AS PULocationID,
  CAST(DOLocationID AS STRING) AS DOLocationID,
  fare_amount,
  tolls_amount,
  tip_amount
FROM dez_dataset.green_part
WHERE DATE(lpep_pickup_datetime) BETWEEN '2019-01-01' AND '2019-12-31'
  AND payment_type = 1
  AND fare_amount > 0;

-- Le modèle : une régression linéaire qui prédit tip_amount à partir des 6 autres colonnes
CREATE OR REPLACE MODEL dez_dataset.tip_model
OPTIONS (
  model_type = 'linear_reg',
  input_label_cols = ['tip_amount'],
  DATA_SPLIT_METHOD = 'AUTO_SPLIT'
) AS
SELECT * FROM dez_dataset.green_tips_2019
WHERE tip_amount IS NOT NULL;

-- Ce que BigQuery a fait de chaque variable
SELECT * FROM ML.FEATURE_INFO(MODEL dez_dataset.tip_model);

-- Les erreurs du modèle
SELECT * FROM ML.EVALUATE(MODEL dez_dataset.tip_model,
  (SELECT * FROM dez_dataset.green_tips_2019 WHERE tip_amount IS NOT NULL));

-- Les 3 variables qui pèsent le plus dans chaque prédiction
SELECT * FROM ML.EXPLAIN_PREDICT(MODEL dez_dataset.tip_model,
  (SELECT * FROM dez_dataset.green_tips_2019 WHERE tip_amount IS NOT NULL),
  STRUCT(3 AS top_k_features))
LIMIT 5;
~~~

On sélectionne `payment_type` pour filtrer, mais on ne le garde pas comme variable : il vaut toujours 1 dans cette table, il n'apprendrait rien au modèle.

@@ breakfix
Entraîne un deuxième modèle, `tip_model_nombres`, sur une table où tu as **oublié** les `CAST` : les zones restent des `INT64`. Compare `ML.FEATURE_INFO` et `ML.EVALUATE` des deux modèles. Rien n'échoue : trouve ce qui ne va pas, et explique pourquoi.

@@ breakfix-hints
- Pas de message d'erreur ici : c'est le plus dangereux. Il faut comparer.
- Dans `ML.FEATURE_INFO`, regarde la ligne `PULocationID` des deux modèles : une moyenne de zone, qu'est-ce que ça veut dire ?
- Pour une variable numérique, le modèle apprend un seul nombre : « chaque zone de plus ajoute tant de dollars ». La zone 75 vaut-elle « un peu plus » que la zone 74 ?

@@ breakfix-answer
Les deux modèles s'entraînent sans erreur, mais `tip_model_nombres` traite les zones comme des **quantités** : `ML.FEATURE_INFO` leur donne une moyenne (environ 110 pour la zone de départ), et le modèle apprend un seul coefficient par zone, comme si la zone 200 était « deux fois » la zone 100. Il perd presque toute l'information des lieux. Son `ML.EVALUATE` est nettement plus mauvais : une erreur moyenne autour de 1,5 $ au lieu de 1,1 $, et un `r2_score` proche de 0. Avec `CAST(... AS STRING)`, chaque zone devient une catégorie avec son propre poids : un trajet vers l'aéroport et un trajet de quartier ne sont plus confondus. Supprime ensuite ce modèle et sa table, pour ne pas les payer en stockage.
