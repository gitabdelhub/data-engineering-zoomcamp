@@ brief
- Un **Dockerfile** est la recette d'une image : `FROM` (image de base), `RUN` (commande au moment de la construction), `WORKDIR`, `COPY`, `ENTRYPOINT` (programme lancé au démarrage).
- `docker build -t nom:tag .` construit l'image. `docker run nom:tag argument` la lance en passant l'argument au script.
- Avec uv, on copie `pyproject.toml` et `uv.lock` **avant** le code, puis `uv sync --locked`. Docker peut ainsi réutiliser cette étape tant que les dépendances ne changent pas : c'est le **cache des couches**.

@@ predict
Dans le Dockerfile avec uv, pourquoi copie-t-on `pyproject.toml` et `uv.lock` **avant** `pipeline.py` ? Au deuxième `docker build`, si tu as seulement modifié `pipeline.py`, quelles étapes sont refaites ?

@@ predict-answer
Docker construit l'image **couche par couche** et garde chaque couche en cache. Si les fichiers copiés à une étape n'ont pas changé, il réutilise le cache de cette étape. Comme les dépendances sont copiées et installées avant le code, modifier seulement `pipeline.py` ne refait que le dernier `COPY` : la longue étape `uv sync` affiche `CACHED`. Si on copiait tout d'un coup au début, chaque modification du code réinstallerait toutes les dépendances.

@@ guide
### 1. Fais écrire ton script dans out/

Le conteneur doit déposer son fichier dans un dossier que tu monteras ensuite en volume. Dans `pipeline.py`, ajoute `from pathlib import Path` en haut, puis, avant d'écrire le fichier :

~~~python
Path("out").mkdir(exist_ok=True)
~~~

`exist_ok=True` évite une erreur si le dossier existe déjà. Écris ensuite le fichier dans `out/`, en ajoutant `out/` au début du nom. Vérifie que ça marche encore sans Docker : `uv run python pipeline.py 3`, puis `ls out`.

### 2. Lis le Dockerfile de la leçon, instruction par instruction

| Instruction | Ce qu'elle fait |
| --- | --- |
| `FROM python:3.13-slim` | l'image de départ |
| `COPY --from=ghcr.io/astral-sh/uv:latest /uv /bin/` | récupère le programme `uv` depuis l'image officielle de uv |
| `WORKDIR /app` | le dossier de travail dans l'image, créé s'il n'existe pas |
| `ENV PATH="/app/.venv/bin:$PATH"` | pour que `python` soit celui de l'environnement du projet |
| `COPY pyproject.toml uv.lock .python-version ./` | copie d'abord **seulement** les fichiers qui décrivent les dépendances |
| `RUN uv sync --locked` | installe les versions exactes de `uv.lock` |
| `COPY pipeline.py pipeline.py` | copie ton code, **après** les dépendances |
| `ENTRYPOINT ["python", "pipeline.py"]` | la commande lancée au démarrage ; les arguments de `docker run` s'ajoutent à la fin |

L'ordre compte : Docker garde en **cache** chaque étape tant que les fichiers copiés avant n'ont pas changé. Si ton code est copié après l'installation, modifier `pipeline.py` ne relance pas l'installation.

### 3. Écris ton Dockerfile

Dans `mon-travail/module-01/pipeline/`, crée un fichier nommé exactement `Dockerfile`, sans extension, en reprenant ces instructions.

### 4. Construis l'image

`docker build -t <nom>:<version> .` construit une image. Le `.` final veut dire « avec les fichiers du dossier courant ». Ton image s'appelle `month-pipeline:v1`.

### 5. Lance-la avec un volume

Combine avec la leçon 1 : ton dossier `out` monté sur `/app/out`, et le mois ajouté **après** le nom de l'image, par exemple `7`. Puis `ls out/` dans ton Codespace : le fichier du mois 7 est arrivé.

### 6. Vérifie le cache

Change un détail dans `pipeline.py`, par exemple le texte d'un `print`, puis reconstruis. Dans la sortie du build, l'étape `RUN uv sync --locked` affiche `CACHED` : elle n'a pas été refaite.

@@ hints
- Pars du Dockerfile « with uv » de la leçon. Le binaire uv se copie depuis l'image officielle `ghcr.io/astral-sh/uv`.
- Pour récupérer le fichier, combine avec la leçon 1 : un volume monté sur le dossier où le script écrit, par exemple `/app/out`.
- Ton script écrit dans le dossier courant. Soit tu lui fais écrire dans `out/`, soit tu changes le `WORKDIR`.

@@ solution
~~~dockerfile
FROM python:3.13-slim
COPY --from=ghcr.io/astral-sh/uv:latest /uv /bin/

WORKDIR /app
ENV PATH="/app/.venv/bin:$PATH"

COPY pyproject.toml uv.lock .python-version ./
RUN uv sync --locked

COPY pipeline.py pipeline.py
ENTRYPOINT ["python", "pipeline.py"]
~~~
Dans `pipeline.py`, écris dans `out/` : `df.to_parquet(f"out/output_month_{month}.parquet")` (et `Path("out").mkdir(exist_ok=True)`).
~~~bash
# Construire l'image à partir du Dockerfile du dossier courant (le « . »)
docker build -t month-pipeline:v1 .

# La lancer : out/ du Codespace monté sur /app/out, et 7 passé au script
docker run --rm -v $(pwd)/out:/app/out month-pipeline:v1 7
ls out/          # output_month_7.parquet

# Après avoir modifié seulement pipeline.py :
docker build -t month-pipeline:v1 .   # « RUN uv sync --locked » affiche CACHED
~~~

@@ breakfix

@@ breakfix-hints
- Le build réussit. Pourquoi Docker ne vérifie-t-il pas que le fichier existe ?
- Relis la différence entre `RUN` et `ENTRYPOINT` dans le résumé.
- Le message d'erreur au lancement vient de Python, pas de Docker.

@@ breakfix-answer
Le build réussit, parce que l'`ENTRYPOINT` n'est **pas exécuté** pendant la construction : il est seulement enregistré dans l'image. L'erreur apparaît au `docker run` : `python: can't open file '/app/pipline.py'`. À l'inverse, une erreur dans un `RUN` fait échouer le build. Retenir quelle erreur arrive quand t'aide à chercher au bon endroit.

@@ git
Quand ton image marche, **commite** ton Dockerfile. Puis fais un essai dedans (par exemple, ajoute `ENV MODE=essai`), sans le commiter. Sans perdre cet essai, reviens à la version commitée et reconstruis l'image qui marche. Enfin, récupère ton essai, et garde la version que tu préfères.

@@ git-hints
- Git peut **mettre de côté** des changements pas encore commités, puis les ressortir plus tard : regarde `git stash`.
- `git stash list` montre ce qui est de côté, et `git stash pop` le ressort.
- Pour abandonner ton essai à la fin, `git restore Dockerfile` remet le fichier comme au dernier commit.
