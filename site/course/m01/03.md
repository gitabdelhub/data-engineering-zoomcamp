@@ brief
- Un **Dockerfile** est la recette d'une image : `FROM` (image de base), `RUN` (commande au moment de la construction), `WORKDIR`, `COPY`, `ENTRYPOINT` (programme lancé au démarrage).
- `docker build -t nom:tag .` construit l'image. `docker run nom:tag argument` la lance en passant l'argument au script.
- Avec uv, on copie `pyproject.toml` et `uv.lock` **avant** le code, puis `uv sync --locked`. Docker peut ainsi réutiliser cette étape tant que les dépendances ne changent pas : c'est le **cache des couches**.

@@ predict
Dans le Dockerfile avec uv, pourquoi copie-t-on `pyproject.toml` et `uv.lock` **avant** `pipeline.py` ? Au deuxième `docker build`, si tu as seulement modifié `pipeline.py`, quelles étapes sont refaites ?

@@ predict-answer
Docker construit l'image **couche par couche** et garde chaque couche en cache. Si les fichiers copiés à une étape n'ont pas changé, il réutilise le cache de cette étape. Comme les dépendances sont copiées et installées avant le code, modifier seulement `pipeline.py` ne refait que le dernier `COPY` : la longue étape `uv sync` affiche `CACHED`. Si on copiait tout d'un coup au début, chaque modification du code réinstallerait toutes les dépendances.

@@ practice
Dockerise **ton** pipeline de la leçon 2 avec uv, et récupère son résultat dans ton Codespace.

@@ constraints
- L'image s'appelle `month-pipeline:v1`, basée sur `python:3.13-slim`, et installe les dépendances depuis `uv.lock`
- Le mois est passé en argument à `docker run`
- Le fichier Parquet produit par le conteneur arrive dans `mon-travail/module-01/pipeline/out/` de ton Codespace
- Au deuxième build, après avoir modifié seulement `pipeline.py`, l'étape d'installation des dépendances est en cache

@@ hints
- Pars du Dockerfile « with uv » de la leçon. Le binaire uv se copie depuis l'image officielle `ghcr.io/astral-sh/uv`.
- Pour récupérer le fichier, combine avec la leçon 1 : un volume monté sur le dossier où le script écrit, par exemple `/app/out`.
- Ton script écrit dans le dossier courant. Soit tu lui fais écrire dans `out/`, soit tu changes le `WORKDIR`.

@@ solution
~~~dockerfile
FROM python:3.13-slim
COPY --from=ghcr.io/astral-sh/uv:latest /uv /bin/

WORKDIR /app
ENV PATH="/app/.venv/bin:$PATH"

COPY pyproject.toml uv.lock .python-version ./
RUN uv sync --locked

COPY pipeline.py pipeline.py
ENTRYPOINT ["python", "pipeline.py"]
~~~
Dans `pipeline.py`, écris dans `out/` : `df.to_parquet(f"out/output_month_{month}.parquet")` (et `Path("out").mkdir(exist_ok=True)`).
~~~bash
docker build -t month-pipeline:v1 .
docker run --rm -v $(pwd)/out:/app/out month-pipeline:v1 7
ls out/
~~~

@@ breakfix-hints
- Le build réussit. Pourquoi Docker ne vérifie-t-il pas que le fichier existe ?
- Relis la différence entre `RUN` et `ENTRYPOINT` dans le résumé.
- Le message d'erreur au lancement vient de Python, pas de Docker.

@@ breakfix-answer
Le build réussit, parce que l'`ENTRYPOINT` n'est **pas exécuté** pendant la construction : il est seulement enregistré dans l'image. L'erreur apparaît au `docker run` : `python: can't open file '/app/pipline.py'`. À l'inverse, une erreur dans un `RUN` fait échouer le build. Retenir quelle erreur arrive quand t'aide à chercher au bon endroit.
