@@ brief
- Postgres tourne dans un conteneur, sans rien installer : l'image `postgres:18` se configure avec des **variables d'environnement** (`-e POSTGRES_USER`…).
- Un **volume** garde les données quand le conteneur s'arrête. Avec Postgres 18, on le monte sur `/var/lib/postgresql`.
- **Volume nommé** (`nom:/chemin`) : géré par Docker. **Bind mount** (`/chemin/hôte:/chemin`) : ton propre dossier.
- `-p 5432:5432` publie le port : **à gauche le port de ton Codespace, à droite celui du conteneur**.
- `pgcli` est un client SQL en ligne de commande, installé comme dépendance de développement (`uv add --dev`).

@@ codespaces
- Postgres occupe le premier terminal : ouvre un **deuxième terminal** (bouton `+`) pour pgcli.
- Installe pgcli dans ton projet `mon-travail/module-01/pipeline/`, et lance-le depuis ce dossier.

@@ verified
- Avec Postgres 18, les données sont sous `/var/lib/postgresql/18/docker`, d'où le montage sur `/var/lib/postgresql`. Beaucoup de tutos plus anciens montent `/var/lib/postgresql/data` : ne les suis pas pour cette version.

@@ predict
Tu lances Postgres **sans** l'option `-v`, tu crées une table, tu arrêtes le conteneur et tu en relances un nouveau avec la même commande. Ta table existe-t-elle encore ? Pourquoi ?

@@ predict-answer
**Non.** Sans volume nommé, les données sont écrites dans le conteneur (ou dans un volume anonyme créé pour lui). Un nouveau conteneur repart d'une base vide. C'est la même règle qu'à la leçon 1 : un conteneur oublie tout, sauf ce qui passe par un volume que tu réutilises.

@@ practice
Lance une base Postgres **différente de celle de la leçon**, qui survit à son conteneur.

@@ constraints
- Utilisateur `dez`, mot de passe `dez`, base `ny_taxi`
- Le conteneur s'appelle `pg` et tourne **en arrière-plan** : ton terminal reste libre
- Port 5432 publié, et un volume nommé `dez_pgdata`
- Avec pgcli, tu crées une table `essai` et tu y insères une ligne
- Tu supprimes le conteneur, tu en relances un avec le même volume, et la ligne est toujours là

@@ hints
- L'option pour l'arrière-plan est `-d` (detached). Les logs restent visibles avec `docker logs pg`.
- `--name` donne un nom au conteneur. Pour le supprimer : `docker stop pg` puis `docker rm pg`.
- pgcli : `uv run pgcli -h localhost -p 5432 -u dez -d ny_taxi`. Dans pgcli, `\dt` liste les tables.

@@ solution
~~~bash
docker run -d \
  --name pg \
  -e POSTGRES_USER="dez" \
  -e POSTGRES_PASSWORD="dez" \
  -e POSTGRES_DB="ny_taxi" \
  -v dez_pgdata:/var/lib/postgresql \
  -p 5432:5432 \
  postgres:18

uv run pgcli -h localhost -p 5432 -u dez -d ny_taxi
# CREATE TABLE essai (id INTEGER, txt VARCHAR(50));
# INSERT INTO essai VALUES (1, 'je survis');
# \q

docker stop pg && docker rm pg
# relancer la même commande docker run, puis :
uv run pgcli -h localhost -p 5432 -u dez -d ny_taxi
# SELECT * FROM essai;
~~~

@@ selfcheck
- Après la recréation du conteneur, `SELECT * FROM essai;` renvoie ma ligne
- `docker volume ls` montre `dez_pgdata`
- À la fin, j'ai arrêté et supprimé `pg` pour libérer le port 5432 pour la suite

@@ breakfix
Relance le conteneur avec `-p 5433:5432`, puis connecte-toi avec pgcli exactement comme avant (`-p 5432`). La connexion échoue. Trouve pourquoi, et répare **sans toucher au conteneur**.

@@ breakfix-hints
- Lis le message d'erreur : la connexion est refusée **sur quel port** ?
- Dans `-p A:B`, lequel des deux est le port de ton Codespace ?
- `docker ps` affiche les ports publiés dans la colonne PORTS.

@@ breakfix-answer
Avec `-p 5433:5432`, Postgres écoute toujours sur **5432 dans le conteneur**, mais Docker le publie sur **5433 dans ton Codespace**. Personne n'écoute sur 5432 de ton côté, donc la connexion est refusée. La réparation : `uv run pgcli -h localhost -p 5433 -u dez -d ny_taxi`. Tu en auras besoin au homework (question 2).
