@@ brief
- Le cours utilise Google Cloud (GCP) : **Cloud Storage** (GCS) comme lac de données, **BigQuery** comme entrepôt de données.
- Il faut un compte GCP (essai gratuit avec des crédits), un **projet**, et un **compte de service** : une identité pour les programmes, avec des **rôles** (Storage Admin, BigQuery Admin…).
- La clé du compte de service est un fichier JSON. La variable `GOOGLE_APPLICATION_CREDENTIALS` indique son chemin aux outils.
- Le dossier `terraform/` du module crée un bucket et un dataset BigQuery avec Terraform.

@@ codespaces
- **La clé ne doit jamais être dans le repo.** Dans GitHub : Settings, Codespaces, Secrets, New secret. Nomme-le `GCP_SA_KEY`, colle tout le contenu du JSON, et donne l'accès à ton fork. Le Codespace le reçoit comme variable d'environnement après un redémarrage.
- Dans le Codespace, écris la clé **hors du repo** : `mkdir -p ~/.gcp && echo "$GCP_SA_KEY" > ~/.gcp/key.json`, puis `export GOOGLE_APPLICATION_CREDENTIALS=~/.gcp/key.json`.
- `gcloud auth application-default login` essaie d'ouvrir un navigateur : ajoute `--no-launch-browser` et suis le lien affiché.

@@ verified
- La leçon renvoie vers `week_1_basics_n_setup/1_terraform_gcp/terraform`, un ancien chemin. Les fichiers sont dans [01-docker-terraform/terraform](https://github.com/DataTalksClub/data-engineering-zoomcamp/tree/main/01-docker-terraform/terraform).
- L'essai gratuit de Google Cloud demande une carte bancaire, mais un bucket et un dataset vides ne coûtent quasiment rien. Fais quand même `terraform destroy` si tu fais une longue pause.

@@ predict
Le nom d'un bucket Cloud Storage doit être unique : dans ton projet, ou dans le monde entier ? Comment choisir un nom qui ne sera jamais pris ?

@@ predict-answer
**Dans le monde entier** : les noms de buckets sont partagés par tous les utilisateurs de Google Cloud. Un nom comme `test` ou `data` est déjà pris. L'astuce courante est de préfixer avec l'identifiant de ton projet, lui aussi unique : `<project-id>-dez-lake`.

@@ practice
Crée ton infrastructure Google Cloud avec Terraform, **sans jamais exposer ta clé**.

@@ constraints
- Un bucket `<project-id>-dez-lake` et un dataset BigQuery `dez_dataset`, au même emplacement (`EU` ou `US`)
- Toutes les valeurs (projet, région, emplacement, noms, chemin de la clé) sont des **variables** dans `variables.tf`. Rien n'est écrit en dur dans `main.tf`
- La clé est dans un secret Codespaces et sur le disque **hors du repo**
- `git status` ne montre ni clé, ni state, ni dossier `.terraform/`
- Le bucket et le dataset apparaissent dans la console Google Cloud

@@ guide
### 1. Crée ton projet Google Cloud

Sur [console.cloud.google.com](https://console.cloud.google.com), crée un compte (l'essai gratuit demande une carte bancaire, mais ce module ne coûte quasiment rien). En haut de la page, le sélecteur de projet : **Nouveau projet**. Note son **ID** (pas son nom) : par exemple `dez-zoomcamp-123456`. L'interface de Google change souvent : si un bouton n'a pas exactement le même nom, cherche le plus proche.

### 2. Crée le compte de service et sa clé

Menu **IAM et administration → Comptes de service → Créer un compte de service**. Donne-lui un nom, par exemple `terraform`. À l'étape des rôles, ajoute **Storage Admin** et **BigQuery Admin**. Ensuite, sur la ligne du compte : **Gérer les clés → Ajouter une clé → Créer une clé → JSON**. Un fichier `.json` se télécharge sur ton PC : c'est la clé. Ne l'envoie à personne.

### 3. Range la clé dans un secret, jamais dans le repo

Sur GitHub : ta photo → **Settings → Codespaces → Secrets → New secret**. Nom : `GCP_SA_KEY`. Valeur : ouvre le fichier `.json` avec le Bloc-notes, copie **tout** et colle. Dans « Repository access », choisis ton fork. Arrête puis relance ton Codespace pour qu'il reçoive le secret.

### 4. Écris la clé hors du repo

Dans le terminal du Codespace :

~~~bash
mkdir -p ~/.gcp
echo "$GCP_SA_KEY" > ~/.gcp/key.json
~~~

`~` est ton dossier personnel, en dehors de `/workspaces` : Git ne peut pas le voir. Vérifie avec `head -c 40 ~/.gcp/key.json` : le début doit ressembler à `{ "type": "service_account"`. Si le fichier est vide, le Codespace n'a pas encore reçu le secret : redémarre-le.

### 5. Copie le Terraform du cours

~~~bash
cd /workspaces/data-engineering-zoomcamp/mon-travail/module-01
cp -r ../../01-docker-terraform/terraform/terraform_with_variables terraform-gcp
cd terraform-gcp
ls
~~~

Lis `main.tf` et `variables.tf` : tu y retrouves la forme de la leçon 12, avec le provider `google`.

### 6. Tout en variables

Dans `variables.tf`, déclare une variable par valeur de la consigne : le projet (sans valeur par défaut, tu la donneras avec `-var`), le chemin de la clé, la région, l'emplacement, le nom du dataset. Dans `main.tf`, remplace chaque valeur écrite en dur par `var.…`. Le nom du bucket se construit à partir du projet : `"${var.project}-dez-lake"`.

Pour la clé, `file()` lit un fichier mais ne comprend pas `~`. `pathexpand()` le transforme en chemin complet : `file(pathexpand(var.credentials))`.

### 7. Vérifie Git avant tout

Ajoute au `.gitignore` du dossier `.terraform/` et `*.tfstate*`. `git status` ne doit montrer **aucun** `.json`, ni state, ni `.terraform/`.

### 8. Crée l'infrastructure

~~~bash
terraform init
terraform plan -var="project=<ton-project-id>"
terraform apply -var="project=<ton-project-id>"
~~~

Lis le plan : 2 resources à créer. Après `yes`, ouvre la console Google Cloud : ton bucket est dans **Cloud Storage → Buckets**, ton dataset dans **BigQuery**. Si tu fais une longue pause, `terraform destroy` avec le même `-var` supprime tout.

@@ hints
- Pars de `01-docker-terraform/terraform/terraform_with_variables/` : copie-le dans `mon-travail/module-01/terraform-gcp/`, puis remplace les valeurs par défaut.
- Le provider `google` peut lire la clé avec `credentials = file(var.credentials)`. La valeur par défaut de `credentials` peut être `"~/.gcp/key.json"`… mais `file()` ne comprend pas `~` : utilise un chemin absolu ou `pathexpand()`.
- Un nom de variable peut servir à en construire un autre : `"${var.project}-dez-lake"`.

@@ solution
`variables.tf` (extrait) :
~~~hcl
variable "project"     { description = "ID du projet GCP" }
variable "credentials" { default = "~/.gcp/key.json" }
variable "region"      { default = "europe-west1" }
variable "location"    { default = "EU" }
variable "bq_dataset_name" { default = "dez_dataset" }
~~~
`main.tf` (extrait) :
~~~hcl
provider "google" {
  # pathexpand transforme ~ en chemin complet, que file() sait lire
  credentials = file(pathexpand(var.credentials))
  project     = var.project
  region      = var.region
}

resource "google_storage_bucket" "lake" {
  name          = "${var.project}-dez-lake"   # construit à partir du projet
  location      = var.location
  force_destroy = true                         # destroy marche même si le bucket contient des fichiers
}

resource "google_bigquery_dataset" "dataset" {
  dataset_id = var.bq_dataset_name
  location   = var.location
}
~~~
~~~bash
terraform init
terraform plan -var="project=<ton-project-id>"
terraform apply -var="project=<ton-project-id>"
~~~

@@ breakfix
Commite ta configuration qui marche. Puis change le nom du bucket en `test-bucket`, et **commite aussi ce changement**, comme s'il était déjà poussé et partagé. Lance `terraform apply` et lis l'erreur de Google Cloud. Répare avec Git, sans retaper l'ancien nom à la main : l'historique doit garder l'erreur **et** sa correction.

@@ breakfix-hints
- L'erreur vient de l'API de Google Cloud, pas de Terraform lui-même : Terraform te transmet sa réponse.
- Le code HTTP de l'erreur (409) veut dire « conflit ».
- Relis la prédiction de cette leçon.
- Pour annuler un commit déjà partagé sans réécrire l'historique, Git a une commande qui crée un commit « inverse » : regarde `git revert`.

@@ breakfix-answer
Google Cloud répond **409** : le nom `test-bucket` appartient déjà à quelqu'un d'autre, ailleurs dans le monde. Terraform ne peut rien y faire. Tu remets le nom basé sur ton identifiant de projet avec `git revert HEAD` : Git crée un nouveau commit qui fait l'inverse du précédent, puis `terraform apply` revient au bon bucket. Pourquoi pas `git reset` ? Parce qu'un commit déjà poussé est peut-être chez tes collègues : on ne réécrit pas un historique partagé, on ajoute sa correction. Les erreurs du cloud arrivent souvent ainsi : Terraform relaie le message de l'API, et c'est ce message qu'il faut lire.
