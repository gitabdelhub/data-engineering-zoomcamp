@@ brief
- Docker isole un programme et tout ce dont il a besoin dans un **conteneur**, plus léger qu'une machine virtuelle.
- Une **image** est le modèle, un **conteneur** est une copie qui tourne. `docker run` crée un nouveau conteneur à chaque fois.
- Les conteneurs n'ont pas de mémoire : ce que tu changes dedans disparaît quand tu en relances un nouveau.
- `-it` pour taper dedans, `--rm` pour le supprimer à la sortie, `--entrypoint` pour changer le programme lancé au démarrage.
- Un **volume** (`-v dossier_hôte:dossier_conteneur`) partage des fichiers entre ton Codespace et le conteneur.

@@ codespaces
- Docker est déjà installé dans ton Codespace : tu n'as pas besoin de Docker Desktop.
- Travaille dans `mon-travail/module-01/` : fais `cd` dedans avant de créer le dossier `test`.
- La vidéo utilise `python:3.9.16`. Utilise plutôt `python:3.13-slim`, la version du reste du cours.

@@ predict
Tu lances `docker run -it ubuntu`, tu installes `python3` avec `apt`, tu tapes `exit`, puis tu relances **exactement** la même commande. `python3` est-il encore installé ? Et l'ancien conteneur, il est où ?

@@ predict-answer
`python3` **n'est plus là** : chaque `docker run` crée un **nouveau** conteneur à partir de l'image `ubuntu`, qui ne contient pas Python. L'ancien conteneur existe toujours, arrêté : `docker ps -a` le montre. C'est pour ça qu'on ajoute `--rm`, pour ne pas les accumuler.

@@ practice
Prouve par l'expérience qu'un conteneur oublie tout, sauf ce qui passe par un volume.

@@ constraints
- Image `python:3.13-slim`, avec `bash` comme programme de démarrage, et le conteneur supprimé à la sortie
- Ton dossier `mon-travail/module-01/test` est monté dans le conteneur sur `/data` (pas `/app/test` comme dans la vidéo)
- Depuis le conteneur, tu crées `/data/depuis_conteneur.txt` **et** `/tmp/perdu.txt`
- Après être sorti, tu montres depuis ton Codespace lequel des deux fichiers existe encore, et pourquoi

@@ hints
- Les options de la leçon suffisent : `-it`, `--rm`, `--entrypoint` et `-v`.
- Avec `-v`, le chemin côté Codespace doit être **absolu**. `$(pwd)` donne le dossier courant.
- `/tmp/perdu.txt` est dans le conteneur, pas dans le volume : relance un nouveau conteneur et cherche-le.

@@ solution
~~~bash
cd /workspaces/data-engineering-zoomcamp/mon-travail/module-01
mkdir -p test
docker run -it --rm \
  -v $(pwd)/test:/data \
  --entrypoint=bash \
  python:3.13-slim

# dans le conteneur :
echo "bonjour" > /data/depuis_conteneur.txt
echo "adieu" > /tmp/perdu.txt
exit

# dans ton Codespace :
ls -la test      # depuis_conteneur.txt est là
~~~
Remarque : le fichier créé par le conteneur appartient à `root`. C'est normal, le conteneur tourne en `root` par défaut. Tu le verras avec `ls -la`.

@@ selfcheck
- `test/depuis_conteneur.txt` existe dans mon Codespace
- Dans un nouveau conteneur, `/tmp/perdu.txt` n'existe pas
- `docker ps -a` ne montre pas de conteneur arrêté, grâce à `--rm`

@@ breakfix
Lance `docker run -it --rm -v test:/data --entrypoint=bash python:3.13-slim`. Remarque : `test` est écrit **sans** `$(pwd)/`. Crée un fichier dans `/data` et sors. Le fichier n'est pas dans ton dossier `test/`. Où est-il passé ? Trouve-le avec une commande Docker.

@@ breakfix-hints
- Quand le côté gauche de `-v` n'est pas un chemin (pas de `/`), Docker le comprend autrement.
- La leçon 4 parle de deux sortes de volumes. Il existe une commande `docker volume` pour les lister.
- `docker volume inspect test` te dit où Docker range ce volume.

@@ breakfix-answer
Sans `/`, `test` est le nom d'un **volume nommé** que Docker crée et gère lui-même, loin de ton dossier. `docker volume ls` le montre, et `docker volume rm test` le supprime. Avec un chemin absolu, c'est un **bind mount** : ton vrai dossier. Cette différence reviendra à la leçon 4 avec Postgres.
