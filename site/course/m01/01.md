@@ brief
- Docker isole un programme et tout ce dont il a besoin dans un **conteneur**, plus léger qu'une machine virtuelle.
- 🔑 Une **image** est le modèle, un **conteneur** est une copie qui tourne. `docker run` crée un nouveau conteneur à chaque fois.
- Les conteneurs n'ont pas de mémoire : ce que tu changes dedans disparaît quand tu en relances un nouveau.
- 🔑 `-it` pour taper dedans, `--rm` pour le supprimer à la sortie, `--entrypoint` pour changer le programme lancé au démarrage.
- 🔑 Un **volume** (`-v dossier_hôte:dossier_conteneur`) partage des fichiers entre ton Codespace et le conteneur.

### 1. Prépare le dossier

Dans le terminal, va dans ton dossier du module 1 et crée le dossier `test` :

~~~bash
cd /workspaces/data-engineering-zoomcamp/mon-travail/module-01
mkdir -p test
~~~

### 2. Lis une commande docker run morceau par morceau

Voici une commande qui ouvre un terminal dans un conteneur Debian, avec un dossier `notes` partagé :

~~~bash
docker run -it --rm -v $(pwd)/notes:/mesnotes --entrypoint=bash debian:12
~~~

| Morceau | Ce qu'il fait |
| --- | --- |
| `docker run` | crée et démarre un conteneur |
| `-it` | te donne un terminal interactif dans le conteneur |
| `--rm` | supprime le conteneur quand tu en sors |
| `-v $(pwd)/notes:/mesnotes` | un **volume** : le dossier `notes` de ton Codespace apparaît dans le conteneur sous `/mesnotes`. `$(pwd)` est remplacé par le dossier où tu es, car Docker veut un chemin complet |
| `--entrypoint=bash` | le programme lancé au démarrage : ici, un terminal `bash` |
| `debian:12` | l'image de départ, toujours en dernier |

@@ solution
~~~bash
# Se placer dans le dossier du module et créer le dossier à partager
cd /workspaces/data-engineering-zoomcamp/mon-travail/module-01
mkdir -p test

# Le conteneur : terminal interactif (-it), supprimé à la sortie (--rm),
# test/ monté sur /data, bash comme programme de démarrage.
# Le \ en fin de ligne veut dire « la commande continue à la ligne suivante ».
docker run -it --rm \
  -v $(pwd)/test:/data \
  --entrypoint=bash \
  python:3.13-slim

# Dans le conteneur :
echo "bonjour" > /data/depuis_conteneur.txt   # dans le volume : écrit aussi dans test/
echo "adieu" > /tmp/perdu.txt                  # seulement dans le conteneur
exit                                           # le conteneur est supprimé

# Dans ton Codespace :
ls -la test      # depuis_conteneur.txt est là, perdu.txt n'existe nulle part
~~~

Pourquoi : `/data` est un **volume**, un dossier de ton Codespace prêté au conteneur. Ce qui y est écrit reste sur ton disque. `/tmp` appartient au conteneur lui-même, et `--rm` l'a supprimé à la sortie avec tout son contenu.
Remarque : le fichier créé par le conteneur appartient à `root`. C'est normal, le conteneur tourne en `root` par défaut. Tu le verras avec `ls -la`.

@@ zoom
### Image ou conteneur ?

Une **image** est un modèle figé : un système de fichiers en lecture seule (Debian, Python, tes bibliothèques…) et le nom d'un programme à lancer. Un **conteneur** est une copie de l'image qui tourne, avec une couche à lui par-dessus, où il peut écrire. Chaque `docker run` crée un **nouveau** conteneur, avec une couche neuve et vide. L'image, elle, ne change jamais.

Essaie, puis regarde ce que chaque commande affiche :

~~~bash
docker run debian:12 bash -c 'echo bonjour > /tmp/f.txt'   # un conteneur écrit un fichier, puis s'arrête
docker ps -a                    # il est toujours là, arrêté (Exited)
docker diff <son_id>            # « A /tmp/f.txt » : le fichier existe encore, dans CE conteneur
docker run debian:12 ls /tmp    # un NOUVEAU conteneur : /tmp est vide
~~~

C'est ça, « un conteneur n'a pas de mémoire » : ton fichier n'est pas perdu tout de suite, il reste dans l'ancien conteneur arrêté. Mais tu n'y reviens jamais, puisque chaque `docker run` repart de l'image.

### `-it` : pouvoir taper dans le conteneur

Deux options collées : `-i` (interactive) envoie ce que tu tapes au programme du conteneur, et `-t` (tty) lui donne un vrai terminal, avec l'invite `root@3f2a1b:/#`.

| Commande | Ce qui se passe |
| --- | --- |
| `docker run debian:12 bash` | Rien ne s'affiche : bash démarre, personne ne lui parle, il s'arrête aussitôt |
| `docker run -i debian:12 bash` | Pas d'invite, mais tes commandes marchent : tape `ls`, puis `exit` |
| `docker run -it debian:12 bash` | Un vrai terminal, avec l'invite `root@…:/#` |

La règle : `-it` quand **tu** veux taper dans le conteneur (bash, Python, pgcli). Pas besoin pour un programme qui travaille seul, comme ton script d'ingestion à la leçon 8.

### `--rm` : ne pas accumuler les conteneurs

Sans `--rm`, chaque conteneur arrêté reste sur le disque : lance trois fois `docker run debian:12 true`, puis `docker ps -a`, tu en vois trois. Ils prennent de la place dans ton Codespace, et tu les supprimeras à la leçon 11. Avec `--rm`, le conteneur est supprimé dès qu'il s'arrête, avec sa couche : tout ce qui n'est pas dans un volume disparaît pour de bon.

C'est voulu : un conteneur est jetable, et ce qui compte doit vivre ailleurs. À la leçon 4, Postgres tourne avec `--rm`, et c'est son **volume** qui garde ta base.

### `--entrypoint` : changer le programme lancé au démarrage

Chaque image a un programme par défaut. Tu peux le voir avec `docker inspect` :

~~~bash
docker inspect python:3.13-slim --format '{{.Config.Entrypoint}} {{.Config.Cmd}}'
# [] [python3]   →  sans rien préciser, tu tombes dans Python (>>>)
docker inspect debian:12 --format '{{.Config.Entrypoint}} {{.Config.Cmd}}'
# [] [bash]
~~~

Une image a deux réglages : `ENTRYPOINT`, le programme, et `CMD`, ses arguments par défaut. Deux façons de les changer au lancement :

- **Ce que tu écris après le nom de l'image remplace `CMD`** : `docker run --rm python:3.13-slim python -c 'print(1+1)'` affiche `2`.
- **`--entrypoint` remplace le programme lui-même** : `docker run -it --rm --entrypoint=bash python:3.13-slim` ouvre un terminal au lieu de Python.

Tu t'en resserviras à la leçon 3 : ton Dockerfile fixe `ENTRYPOINT` sur ton script, et ce que tu écris après le nom de l'image devient ses arguments (`docker run mon-image 3`).

### Les volumes : `-v dossier_hôte:dossier_conteneur`

À gauche, un chemin **de ton Codespace**. À droite, où il apparaît **dans le conteneur**. Ce n'est pas une copie : c'est le même dossier, vu des deux côtés. Écris un fichier d'un côté, il est aussitôt de l'autre.

Trois pièges :

1. **À gauche, un chemin complet.** `$(pwd)/test` est remplacé par le chemin du dossier où tu es. Sans `/`, `test` devient un **volume nommé**, rangé ailleurs par Docker : c'est le casse-et-répare de cette leçon.
2. **Crée le dossier avant.** S'il n'existe pas, Docker le crée lui-même, au nom de `root`, et tu ne pourras pas écrire dedans depuis ton Codespace sans `sudo`. D'où le `mkdir -p test` de l'étape 1.
3. **Les options avant l'image.** Tout ce qui suit le nom de l'image part au programme du conteneur. `docker run debian:12 -it` ne marche pas : `-it` est envoyé à bash, pas à Docker.
