@@ brief
- À la fin d'un atelier, on libère l'espace disque : conteneurs arrêtés, images, volumes, réseaux.
- Pour chaque type : une commande pour **lister** (`docker ps -a`, `docker images`, `docker volume ls`, `docker network ls`), une pour **supprimer** un élément, et une pour supprimer tout ce qui est inutilisé (`prune`).
- `docker system prune -a --volumes` supprime d'un coup tout ce qui ne sert pas à un conteneur en marche : à utiliser avec prudence.

@@ codespaces
- Ton Codespace a un stockage limité (32 Go de disque par machine, et 15 Go de stockage gratuit par mois sur ton compte). Les images Docker prennent vite de la place.
- **Ne supprime pas** le volume `ny_taxi_postgres_data` : le homework du module en a besoin.

@@ verified
- La leçon utilise `docker-compose down` avec un tiret : dans ton Codespace, c'est `docker compose down`.

@@ predict
Postgres est arrêté. Tu lances `docker system prune -a --volumes`, que la leçon présente comme « supprime tout ». Fais la liste de ce que tu perds. Ta base `ny_taxi`, dans le volume nommé `ny_taxi_postgres_data`, survit-elle ?

@@ predict-answer
Tu perds tous les conteneurs arrêtés, tous les réseaux inutilisés, **toutes les images** qui ne servent pas à un conteneur en marche (ton `taxi_ingest` et ton `month-pipeline` sont à reconstruire) et les volumes **anonymes**. Mais ta base **survit** : depuis Docker 23, `--volumes` ne supprime plus les volumes **nommés**. Il faudrait `docker volume prune -a` pour les effacer, et là, tes heures d'ingestion partiraient. Vérifie avec `docker version` et `docker volume ls`. Deux leçons à retenir : on nettoie avec des commandes ciblées, et une doc peut être en retard sur l'outil, alors on vérifie.

@@ practice
Libère de l'espace dans ton Codespace avec des commandes **ciblées**, sans perdre tes données.

@@ constraints
- Avant et après, tu mesures l'espace utilisé par Docker
- Tu supprimes les conteneurs arrêtés, et seulement les images **orphelines** (sans nom)
- Tu supprimes les réseaux `pg-network` et `dez-net` s'ils existent
- Le volume `ny_taxi_postgres_data` est toujours là à la fin
- Tu arrêtes ton Codespace depuis VS Code à la fin de la séance

@@ hints
- `docker system df` montre l'espace utilisé par type, et ce qui peut être récupéré.
- `docker image prune` **sans** `-a` ne supprime que les images orphelines. Avec `-a`, il supprime toutes les images inutilisées.
- Pour arrêter le Codespace : palette de commandes, puis « Codespaces: Stop Current Codespace ».

@@ solution
~~~bash
docker system df
docker container prune
docker image prune
docker network rm pg-network dez-net
docker volume ls          # ny_taxi_postgres_data doit être là
docker system df
~~~
Puis **Ctrl + Shift + P**, « Codespaces: Stop Current Codespace ».

@@ selfcheck
- `docker system df` montre moins d'espace utilisé qu'au départ
- `docker volume ls` montre toujours `ny_taxi_postgres_data`

@@ breakfix
Lance Postgres en arrière-plan, puis essaie de supprimer son image avec `docker rmi postgres:18`. Lis le refus de Docker. Que faut-il faire avant de pouvoir supprimer une image ?

@@ breakfix-hints
- Docker refuse de supprimer une image utilisée par un conteneur, même arrêté.
- Le message cite l'identifiant du conteneur qui l'utilise.
- Il existe une option `-f`, mais elle laisse un conteneur sans image : ne l'utilise pas ici.

@@ breakfix-answer
Docker refuse avec un message qui commence par `conflict: unable to remove` et qui cite le conteneur qui utilise l'image. Il faut d'abord arrêter **et supprimer** le conteneur, puis l'image. Docker protège ce qui est en cours d'utilisation, ce qui rend `prune` sans danger pour un conteneur **qui tourne**, mais pas pour un conteneur arrêté.

@@ explain
Pourquoi le nettoyage compte dans un Codespace ? Et pourquoi préférer des commandes ciblées à `docker system prune -a --volumes` ?
