@@ brief
- **Terraform** décrit ton infrastructure (buckets, bases, machines…) dans des fichiers `.tf` : c'est l'**infrastructure en code**.
- Un **provider** sait parler à une plateforme (Google Cloud, AWS…). Une **resource** est un élément à créer.
- Le **state** (`terraform.tfstate`) garde la correspondance entre tes fichiers et ce qui existe vraiment.
- Le cycle : `terraform init` (installe les providers), `plan` (montre ce qui va changer), `apply` (applique), `destroy` (supprime tout).
- Les `variable` rendent la configuration réutilisable.

@@ codespaces
- Terraform doit être installé : c'est ton `.devcontainer` du module 0 qui s'en charge. Vérifie avec `terraform -version`.
- Cette leçon se fait **sans Google Cloud** : tu utilises un provider qui crée des fichiers sur ton Codespace. Le cloud arrive à la leçon 13.

@@ predict
`terraform plan` crée-t-il quelque chose ? Et si tu supprimes `terraform.tfstate` après un `apply`, que proposera le `plan` suivant ?

@@ predict-answer
`plan` ne crée **rien** : il compare tes fichiers avec le state et la réalité, et affiche ce qu'`apply` ferait. Sans state, Terraform a **oublié** ce qu'il a créé : le plan suivant propose de tout recréer. Avec des fichiers locaux, il les écrase. Dans le cloud, `apply` échoue souvent avec « already exists ». Le state est précieux : on ne le supprime pas, et on ne le commite pas non plus, car il peut contenir des secrets.

@@ practice
Fais le cycle complet de Terraform **en local**, avec le provider `hashicorp/local`.

@@ constraints
- Dossier `mon-travail/module-01/terraform-local/`, avec `main.tf` et `variables.tf`
- La version du provider `hashicorp/local` est fixée
- Une resource `local_file` crée `out/bonjour.txt`, avec un texte qui contient ton prénom, passé par une **variable** `prenom`
- Un `output` affiche le chemin du fichier créé
- Tu passes par `init`, `plan`, `apply`, puis tu changes le prénom avec `-var` et tu lis le plan, puis `destroy`
- `.terraform/` et les fichiers `*.tfstate*` sont ignorés par Git

@@ hints
- La documentation du provider est sur le registre Terraform : cherche « hashicorp/local » et la resource `local_file`.
- Une variable se déclare avec un bloc `variable "prenom" {}` et s'utilise avec `var.prenom`. Dans un texte : `"Bonjour ${var.prenom}"`.
- `terraform apply -var="prenom=Test"` change la valeur pour une seule commande.

@@ solution
`main.tf` :
~~~hcl
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

resource "local_file" "bonjour" {
  filename = "${path.module}/out/bonjour.txt"
  content  = "Bonjour ${var.prenom}, bienvenue dans Terraform !\n"
}

output "fichier" {
  value = local_file.bonjour.filename
}
~~~
`variables.tf` :
~~~hcl
variable "prenom" {
  description = "Ton prénom"
  type        = string
  default     = "AB"
}
~~~
~~~bash
terraform init
terraform plan
terraform apply
terraform plan -var="prenom=Test"     # remplacement prévu
terraform destroy
~~~

@@ selfcheck
- `out/bonjour.txt` contient mon prénom après `apply`, et n'existe plus après `destroy`
- Le plan avec `-var="prenom=Test"` annonce un remplacement (`-/+`)
- `git status` ne montre ni `.terraform/` ni `terraform.tfstate`

@@ breakfix
Après un `apply`, modifie **à la main** le contenu de `out/bonjour.txt`, puis lance `terraform plan`. Que remarque Terraform ? Remets les choses en ordre avec Terraform, pas à la main.

@@ breakfix-hints
- Au début d'un `plan`, Terraform relit l'état réel de chaque resource (« Refreshing state »).
- La réalité ne correspond plus à ta configuration : comment s'appelle cet écart ?
- Le plan te dit quoi faire : un `apply` remet la réalité en accord avec ton code.

@@ breakfix-answer
Terraform détecte que le fichier ne correspond plus à ce qu'il a créé, et propose de le **recréer**. Cet écart entre le code et la réalité s'appelle le **drift**. Un `terraform apply` remet tout en ordre. En entreprise, c'est la raison pour laquelle on ne modifie jamais l'infrastructure à la main : le code doit rester la seule source de vérité.
