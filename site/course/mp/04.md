@@ brief
- Le **warehouse** (BigQuery) lit ton lake : une **table externe** sur les fichiers du bucket, puis une table native, chargée par ton DAG.
- 4 points si les tables sont **partitionnées et clusterisées** pour les requêtes du tableau de bord, **avec une explication** dans le README : pourquoi cette colonne de partition, pourquoi ce cluster.
- 4 points pour des **transformations** avec dbt ou Spark. dbt est le choix naturel en batch : staging, puis tables finales (marts) pour le tableau de bord, avec des **tests**.
- Les marts sont faits pour le tableau de bord : une ligne par jour et par catégorie, déjà agrégée, au lieu de millions de lignes brutes à chaque affichage.

@@ predict
Ton tableau de bord affiche les trajets des 30 derniers jours, par station. Tu hésites entre partitionner par `station_id` ou par `date`, et clusteriser par l'autre. Lequel, et pourquoi ?

@@ predict-answer
**Partition par date, cluster par station.** Le filtre de chaque requête porte sur une période : avec une partition par jour, BigQuery ne lit que 30 partitions. Une partition par station ne servirait pas ce filtre, et BigQuery limite le nombre de partitions d'une table. Le cluster par station range ensuite les lignes d'une même station ensemble à l'intérieur de chaque jour : les `GROUP BY station` lisent moins. C'est le raisonnement que la grille veut **lire** dans ton README.

@@ practice
Charge ton lake dans BigQuery, écris les transformations dbt jusqu'aux tables du tableau de bord, et explique tes partitions.

@@ hints
- Une table externe ne se partitionne pas comme une table native : la grille parle des tables que lisent tes requêtes.
- `dbt deps` doit tourner quelque part si tu utilises `dbt_utils` : les relecteurs le signalent souvent.
- Vérifie le gain : la même requête, avec et sans filtre sur la partition, et compare les octets lus dans BigQuery.
- Un mart par graphique garde le tableau de bord rapide et simple.

@@ solution
Les marts du projet des vélos, pour comparer la forme :

~~~sql
-- models/marts/trajets_par_jour.sql : le graphique dans le temps
{{ config(materialized="table", partition_by={"field": "jour", "data_type": "date"}) }}
select date(depart_at) as jour, count(*) as trajets
from {{ ref("stg_trajets") }}
group by 1

-- models/marts/stations_desequilibrees.sql : le graphique par catégorie
{{ config(materialized="table", cluster_by=["station_id"]) }}
select station_id, countif(sens = "depart") - countif(sens = "arrivee") as solde
from {{ ref("stg_mouvements") }}
group by 1
~~~

> **Partitions et clusters.** `trajets` est partitionnée par jour de départ, parce que toutes les requêtes du tableau de bord filtrent une période, et clusterisée par station, parce qu'elles groupent par station. Sur 30 jours, la requête du graphique lit 1,2 Go au lieu de 41 Go.

@@ breakfix
Mesure ce que ta partition rapporte vraiment. Lance la requête de ton premier graphique deux fois dans la console BigQuery : une fois avec le filtre sur la date, une fois sans. Note les octets traités de chaque requête, avant de la lancer (la console les annonce). Si les deux nombres sont égaux, ta partition ne sert à rien : trouve pourquoi.

@@ breakfix-hints
- La console affiche « Cette requête traitera X » en haut à droite, avant le lancement.
- Un filtre sur une **expression** de la colonne (par exemple `format_date(...)`) peut empêcher l'élagage des partitions.
- La requête lit-elle la table partitionnée, ou une table externe ou une vue au-dessus ?

@@ breakfix-answer
Avec une partition utile, la requête filtrée annonce beaucoup moins d'octets que la requête sans filtre. Si les deux sont égales, trois causes fréquentes : la requête lit une autre table que celle que tu as partitionnée (une table externe, un modèle intermédiaire) ; le filtre transforme la colonne de partition au lieu de la comparer directement (`where jour >= date_sub(current_date(), interval 30 day)` élague, une conversion en texte non) ; ou la table est si petite que BigQuery facture le minimum dans les deux cas. Mets les deux nombres dans ton README : c'est la meilleure explication possible pour le critère du warehouse.
