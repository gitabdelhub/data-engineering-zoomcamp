@@ brief
- 4 points pour la **reproductibilité** : des instructions claires, et un code qui marche **chez quelqu'un d'autre**. C'est le critère le plus souvent perdu.
- Le vrai test : **cloner ton dépôt ailleurs** et suivre ton README à la lettre. Tout fichier oublié dans Git, tout chemin écrit en dur, tout identifiant de projet personnel apparaît tout de suite.
- Le rendu se fait sur le site de DataTalksClub, pendant une **tentative** ouverte (deux par cohorte). Pour que ton projet compte, tu dois **relire trois projets** d'autres participants (3 points chacun).
- Pas de date ici : rends-le quand il est prêt, pendant une tentative de la cohorte que tu suis.

@@ codespaces
- Un nouveau Codespace sur ton dépôt est le « clone propre » idéal : il part de ce qui est dans Git, rien d'autre.
- Le script de relecture du site lit ton dépôt. Le Codespace de ton projet n'a pas ton fork du cours : télécharge le script et lance-le en une ligne, depuis la racine du projet : `curl -sL https://raw.githubusercontent.com/gitabdelhub/data-engineering-zoomcamp/main/site/checks/projet-final.py | python3 - .`

@@ verified
- `site/checks/projet-final.py` a été testé sur un faux projet : il repère un README trop court, un dépôt sans Terraform, sans Action de déploiement, sans orchestrateur, sans dbt ni Spark, sans partition ni cluster, une clé commitée et des fichiers non commités.
- Il ne dit pas si ton projet est **bon** : seulement si chaque critère a de quoi être noté.

@@ predict
Ton projet tourne parfaitement dans ton Codespace. Un relecteur le clone, suit le README, et `terraform apply` échoue : `variables.tf` contient `default = "mon-projet-ab-123"`, un projet Google qui n'existe pas chez lui. Combien de points perds-tu, et sur quels critères ?

@@ predict-answer
Le critère de **reproductibilité** surtout (4 points), et souvent ceux qu'il n'a pas pu vérifier ensuite : le cloud, l'ingestion, le warehouse, s'il ne voit rien tourner. Un identifiant écrit en dur est le premier conseil des relecteurs de la cohorte : « Don't hardcode local paths or personal cloud project IDs. Use environment variables instead. » Un `.env.example` avec des valeurs factices, et des variables partout.

@@ practice
Rends ton projet reproductible, vérifie-le avec un clone propre et le script de relecture, puis rends-le et relis trois projets.

@@ constraints
- Le README a une section « Lancer le projet » : prérequis, variables à définir, commandes dans l'ordre, et ce qu'on doit voir à la fin
- Un `.env.example` donne chaque variable avec une valeur factice, et aucun vrai secret n'est dans Git
- Le script `projet-final.py` affiche tous ses critères en vert
- Tu as suivi ton README dans un **nouveau** Codespace (ou un clone dans `/tmp`), et corrigé tout ce qui manquait
- Le projet est rendu pendant une tentative ouverte, et tu as relu trois projets

@@ guide
### 1. Le README de lancement

Écris-le pour quelqu'un qui a fait le cours, mais pas ton projet : chaque commande, dans l'ordre, et ce qu'elle doit afficher.

### 2. Les variables

Tout ce qui t'est personnel (projet Google, nom du bucket, région) vient d'une variable. `.env` est ignoré par Git ; `.env.example` est commité.

### 3. Le script de relecture

Depuis la racine de ton projet, dans son Codespace :

~~~bash
curl -sL https://raw.githubusercontent.com/gitabdelhub/data-engineering-zoomcamp/main/site/checks/projet-final.py | python3 - .
~~~

(`python3 -` lit le script sur l'entrée standard, et `.` est le dossier à relire.)

### 4. Le clone propre

~~~bash
git clone https://github.com/<toi>/<ton-projet>.git /tmp/test-projet
cd /tmp/test-projet
~~~

Puis suis ton README, ligne par ligne, sans rien deviner. Note chaque endroit où tu as dû improviser.

### 5. Le rendu et les relectures

Les liens de la tentative en cours sont dans le texte officiel, plus bas. Après la date de rendu, la page des relectures te donne trois projets : un formulaire par projet.

@@ hints
- `git status` doit être vide avant le clone propre : sinon, ce qui n'est pas commité manquera.
- `docker compose up` au moins une fois depuis le clone : un relecteur a trouvé une erreur de syntaxe qui empêchait tout de démarrer.
- Un `Makefile` avec `make setup`, `make up`, `make run` rend le lancement plus court, et la grille le cite comme « bonus ».
- Relire les autres t'apprend autant que ton projet : regarde comment ils ont écrit leur README.
- Mets à jour ton **nom de certificat** sur le site du cours (le lien est dans le texte officiel).

@@ solution
Une section de lancement, pour les vélos :

~~~markdown
## Lancer le projet

Prérequis : un compte Google Cloud, un compte de service avec les rôles Storage Admin et BigQuery Admin, Docker, uv, Terraform.

1. Copie `.env.example` en `.env`, et remplis `GCP_PROJECT_ID`, `GCP_REGION` et `GOOGLE_APPLICATION_CREDENTIALS`.
2. Crée le bucket de l'état Terraform : `gcloud storage buckets create gs://$GCP_PROJECT_ID-tfstate`.
3. L'infrastructure : `make infra` (Terraform init, plan, apply).
4. Airflow : `make up`, puis ouvre le port 8080 (admin / admin).
5. Lance le backfill de mars 2026 : `make backfill`.
6. Les transformations : `make dbt` (dbt deps, puis dbt build).
7. Le tableau de bord : le lien plus haut, ou `make dashboard` pour la version Streamlit.

Tu dois voir 31 fichiers dans le bucket, la table `velos.trajets` partitionnée par jour, et les deux marts.
~~~

@@ selfcheck
- Un clone propre de mon dépôt se lance avec mon seul README
- Aucun secret, aucun chemin personnel n'est dans Git
- Je sais où rendre mon projet, et que je dois relire trois projets

@@ breakfix
Fais le clone propre pour de vrai, dans `/tmp`, et note **chaque** difficulté, même petite. Combien en as-tu trouvé ? Corrige-les toutes, commite, puis refais un clone propre. Recommence jusqu'à zéro.

@@ breakfix-hints
- Les classiques : un `requirements.txt` ou un `pyproject.toml` au mauvais endroit, un dossier de configuration jamais commité, un volume Docker vers un dossier qui n'existe pas.
- Une commande qui marche chez toi parce qu'une variable est déjà dans ton terminal.
- Un `dbt deps` oublié.

@@ breakfix-answer
Presque tout le monde trouve quelque chose au premier clone propre, et c'est le but : les relecteurs de la cohorte décrivent exactement ces erreurs (fichiers jamais commités, chemins écrits en dur, `docker compose up` jamais lancé, README qui ne correspond plus au code, `dbt deps` oublié). Chaque difficulté que tu trouves toi-même est un point que ton relecteur ne t'enlèvera pas. Zéro difficulté au deuxième ou troisième essai : ton projet est prêt.

@@ explain
Pourquoi le cours oblige-t-il à relire trois projets pour valider le sien ? Qu'est-ce qu'une relecture apprend, que ton propre projet ne t'apprend pas ?

@@ team
C'est la répétition générale de ton PFE. Avant le rendu, demande à un camarade (ou à quelqu'un de la communauté DataTalksClub sur Slack) de faire ton clone propre à ta place, pendant que tu regardes sans aider : chaque question qu'il pose est une ligne qui manque au README. Ouvre une **issue** dans ton dépôt pour chaque problème trouvé, corrige-les par des pull requests liées (`Fixes #3`), et garde ces issues fermées : elles montrent à un recruteur que tu sais travailler comme une équipe. Enfin, publie la version rendue : `git tag -a v1.0.0 -m "Projet final"`, et une release GitHub avec ses notes.
