@@ brief
- La grille donne 4 points au **cloud avec infrastructure en code** : ton bucket (le data lake) et ton dataset BigQuery (le warehouse) sont décrits dans Terraform, comme au module 1.
- Un pas de plus, demandé par la puce « Terraform en CD » : c'est une **Action GitHub** qui applique Terraform, pas ton terminal. `terraform plan` à chaque pull request, pour relire le changement ; `terraform apply` à chaque fusion sur `main`.
- Pour qu'une Action et ton Codespace partagent la même infrastructure, l'**état** Terraform (`.tfstate`) ne peut pas rester sur ton disque : il va dans un bucket, avec un `backend "gcs"`.
- La clé de service passe par un **secret** du dépôt (`GCP_SA_KEY`), jamais par un fichier commité.

@@ codespaces
- Le bucket de l'état se crée **une fois, à la main** (`gcloud storage buckets create gs://<projet>-tfstate`) : Terraform ne peut pas créer le bucket où il range son propre état.
- Dans ton Codespace, `terraform init` lit le même backend que l'Action : vous voyez la même infrastructure.

@@ predict

@@ predict-answer
Chacun croit être seul. Ton état local ne connaît pas le bucket créé par l'Action (et inversement) : Terraform essaie de le **recréer**, et Google répond qu'il existe déjà (`409 ... already exists`), ou pire, l'un des deux détruit ce que l'autre a créé. @@ practice

@@ constraints
- `terraform/` contient le provider, les variables (projet, région) et tes deux ressources, sans identifiant de projet écrit en dur
- Le backend est `gcs`, dans un bucket créé une fois à la main
- `.gitignore` ignore `.terraform/`, `*.tfstate*` et `*.tfvars` qui contiennent des valeurs personnelles
- `.github/workflows/terraform.yml` fait `fmt -check`, `validate` et `plan` sur chaque pull request, et `apply` sur `main`
- Ta première pull request montre un `plan` vert, et après fusion le bucket et le dataset existent dans la console

@@ guide
### 1. Les ressources

Repars de tes fichiers du module 1. Un bucket avec une règle de cycle de vie, un dataset dans la même région.

### 2. Le backend

~~~hcl
terraform {
  backend "gcs" {
    prefix = "terraform/state"
  }
}
~~~

Le nom du bucket n'est pas écrit dans le fichier : tu le donnes à l'init, `terraform init -backend-config="bucket=<ton-bucket-tfstate>"`, dans ton Codespace comme dans l'Action.

### 3. Les secrets du dépôt

Dans **Settings > Secrets and variables > Actions** : `GCP_SA_KEY` (le contenu de ta clé), et une **variable** `GCP_PROJECT_ID`. Ton compte de service doit pouvoir gérer le stockage et BigQuery.

### 4. L'Action

Les étapes, dans l'ordre : `actions/checkout`, `google-github-actions/auth` avec `credentials_json: ${{ secrets.GCP_SA_KEY }}`, `hashicorp/setup-terraform`, puis `init`, `fmt -check`, `validate`, `plan`. L'`apply` seulement si `github.ref == 'refs/heads/main'` et que l'événement est un `push`.

@@ hints
- `TF_VAR_project_id` dans l'environnement de l'Action remplit la variable `project_id` sans fichier `.tfvars`.
- `-input=false` empêche Terraform d'attendre une réponse au clavier dans l'Action.
- Un `apply` en CD a besoin de `-auto-approve` : c'est le `plan` relu dans la pull request qui sert d'approbation.
- Si l'Action échoue à l'authentification, le log de l'étape `auth` dit quel champ manque.

@@ solution
Un exemple sur le projet des vélos. `terraform/main.tf` :

~~~hcl
terraform {
  required_providers {
    google = {
      source  = "hashicorp/google"
      version = "~> 6.0"
    }
  }
  backend "gcs" {
    prefix = "terraform/state"
  }
}

provider "google" {
  project = var.project_id
  region  = var.region
}

variable "project_id" {
  description = "Ton projet Google Cloud"
  type        = string
}

variable "region" {
  description = "La région des ressources"
  type        = string
  default     = "europe-west1"
}

resource "google_storage_bucket" "lake" {
  name                        = "${var.project_id}-velos-lake"
  location                    = var.region
  force_destroy               = false # le lake garde ton historique : Terraform refuse de supprimer un bucket plein
  uniform_bucket_level_access = true

  lifecycle_rule {
    condition {
      age            = 30
      matches_prefix = ["tmp/"] # seulement les fichiers temporaires : raw/ reste, pour les backfills
    }
    action {
      type = "Delete"
    }
  }
}

resource "google_bigquery_dataset" "warehouse" {
  dataset_id = "velos"
  location   = var.region
}
~~~

`.github/workflows/terraform.yml` :

~~~yaml
name: terraform
on:
  pull_request:
    paths: ["terraform/**"]
  push:
    branches: [main]
    paths: ["terraform/**"]

jobs:
  terraform:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: terraform
    env:
      TF_VAR_project_id: ${{ vars.GCP_PROJECT_ID }}
    steps:
      - uses: actions/checkout@v4
      - uses: google-github-actions/auth@v2
        with:
          credentials_json: ${{ secrets.GCP_SA_KEY }}
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init -input=false -backend-config="bucket=${{ vars.GCP_PROJECT_ID }}-tfstate"
      - run: terraform fmt -check
      - run: terraform validate
      - run: terraform plan -input=false
      - if: github.event_name == 'push' && github.ref == 'refs/heads/main'
        run: terraform apply -input=false -auto-approve
~~~

@@ breakfix
Avant ta première fusion, fais l'essai sur une branche : ajoute dans `main.tf` un second bucket avec le **même** nom que le premier. Ouvre la pull request. Le `plan` est-il vert ? Pourquoi ? Que se passerait-il à l'`apply` ? Puis ferme la pull request sans la fusionner.

@@ breakfix-hints
- `plan` vérifie ta configuration et la compare à l'état ; il ne demande pas à Google si un nom est libre.
- Les noms de buckets sont uniques **dans le monde entier**.
- C'est exactement pour ça que la pull request montre le plan avant l'apply.

@@ breakfix-answer
Le `plan` est probablement **vert** : il annonce deux créations, sans demander à Google si les noms sont libres. L'erreur n'arriverait qu'à l'`apply`, après la fusion, sur `main`, avec un message du genre `409 ... already exists` ou « you already own it », et une infrastructure à moitié créée. Un plan vert prouve que la configuration est cohérente, pas que le cloud l'acceptera : relire le plan (« 2 to add » pour un seul bucket voulu) est le vrai garde-fou. Ce que le plan ne peut pas voir, un environnement de test séparé le verrait.

@@ team
C'est le cœur de la puce « Terraform en CD ». Protège `main` (**Settings > Branches**) : une pull request obligatoire, et l'Action `terraform` au vert pour fusionner. Ainsi, personne, pas même toi, ne change l'infrastructure sans un plan relu. Si tu as un camarade de promo, demande-lui de relire ta première pull request d'infrastructure, et relis la sienne.
