@@ brief
- La grille donne 4 points à une ingestion **orchestrée de bout en bout** : un DAG à plusieurs étapes, qui télécharge et dépose les données dans le **data lake** (ton bucket), sans étape à la main.
- En batch, ton outil est **Airflow** (module 2) ; Bruin (module 5) ou dlt (workshop) peuvent faire l'ingestion à l'intérieur d'une tâche. En streaming, un producteur et un job Flink qui écrit dans le lake (module 7).
- Un bon DAG est **idempotent** : relancé pour le même jour, il produit le même résultat, sans doublon. C'est ce qui rend le backfill possible.
- Le DAG gère les pannes de la source : une adresse en 404 ou en 500 doit faire échouer la tâche proprement, avec des relances, pas créer un fichier vide (le piège de la leçon 5 du module 6).

@@ codespaces
- Airflow tourne dans ton Codespace avec Docker Compose, comme au module 2. Monte ta clé (`~/.gcp/key.json`) dans les conteneurs par un volume, jamais par un `COPY` dans une image.
- Pour un premier essai, un seul jour ou un seul mois : le backfill viendra une fois le DAG vert.

@@ verified
- Rien de ce jalon n'est testé ici : c'est ton pipeline. Les méthodes viennent des modules 2 et W1, qui, eux, sont testés.

@@ predict
Ton DAG quotidien télécharge le fichier du jour et l'envoie dans `gs://<lake>/raw/`, sous le nom `trajets.csv`. Tu fais un backfill sur 30 jours. Combien de fichiers dans le bucket à la fin ?

@@ predict-answer
**Un seul**, celui du dernier jour traité : chaque exécution a écrasé la précédente sous le même nom. Le nom d'un fichier du lake doit contenir la **date logique** de l'exécution (`raw/trajets/2026-03-14.csv`, ou mieux `raw/trajets/date=2026-03-14/...`), celle que donne Airflow, pas la date du jour où tourne la tâche. Alors le backfill remplit 30 fichiers, et relancer un jour remplace exactement ce jour.

@@ practice
Écris le DAG qui télécharge tes données et les dépose dans ton data lake, puis remplis l'historique avec un backfill.

@@ constraints
- Un DAG dans `dags/` avec au moins trois tâches : télécharger, convertir en parquet, envoyer dans le bucket
- Les chemins du lake contiennent la date logique de l'exécution
- Le DAG est idempotent : relancer un jour ne crée pas de doublon
- Une source en panne fait échouer la tâche après des relances (`retries`), sans laisser de fichier vide dans le bucket
- Le backfill d'une période (au moins un mois) est vert, et le README explique comment le relancer

@@ guide
### 1. Le squelette

Repars de ton DAG des leçons 7 et 9 du module 2 : télécharger, transformer, envoyer. Change la source et les chemins.

### 2. La date logique

Dans tes tâches, la date vient du contexte Airflow (`{{ ds }}` dans un template, ou `logical_date` en Python), jamais de `datetime.now()`.

### 3. Les pannes

`response.raise_for_status()` après un téléchargement fait échouer la tâche sur un 404 ou un 500. Écris d'abord dans un fichier temporaire, et n'envoie au bucket qu'un fichier complet.

### 4. Le backfill

`airflow backfill create --dag-id <ton_dag> --from-date ... --to-date ...`, comme à la leçon 8 du module 2.

@@ hints
- Le parquet est plus petit et typé : BigQuery le lira mieux au jalon 4.
- `default_args={"retries": 2, "retry_delay": timedelta(minutes=5)}` suffit pour une source capricieuse.
- Si ta source n'a pas de fichier par jour, choisis un rythme qui lui ressemble : `@monthly` est un rythme comme un autre.
- Garde un petit `README` dans `dags/` : quelles variables et connexions le DAG attend.

@@ breakfix
Simule une panne de ta source : change l'adresse pour une adresse qui n'existe pas, et lance le DAG sur un jour. Que montre l'interface d'Airflow ? Ton bucket a-t-il un nouveau fichier ? Si oui, tu as trouvé un bug avant ton relecteur : répare-le.

@@ breakfix-hints
- Regarde l'état de chaque tâche, et le nombre d'essais.
- `gcloud storage ls gs://<lake>/raw/...` pour le bucket.
- Un fichier vide ou une page d'erreur HTML enregistrée comme un CSV sont les deux bugs classiques.

@@ breakfix-answer
Le bon comportement : la tâche de téléchargement passe en `up_for_retry`, puis en `failed` après ses relances, les tâches suivantes en `upstream_failed`, et **rien** n'arrive dans le bucket. Si un fichier arrive quand même, c'est que le code n'a pas vérifié le code HTTP (une page d'erreur enregistrée comme données), ou a créé le fichier avant de télécharger. Les relecteurs de la cohorte le signalent souvent (« Handle external API failures ») : c'est un point facile à gagner.
